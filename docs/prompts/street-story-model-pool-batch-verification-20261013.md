## Каскад моделей: дешёвые по умолчанию, сильные только по поводу

Факты — не сверхсложная задача. Основную работу делают дешёвые быстрые модели; сильные и дорогие включаются только по конкретному поводу. Без квоты Codex сценарий обязан работать полностью.

### Схема

```
выбранный дом + якорь (город, адрес, имена)
        │
 1. ПОИСК        дешёвая модель с поиском (Gemini Lite grounding, websearch OpenCode, Live)
                 ротация среди здоровых; закрытый отказ или таймаут → другой провайдер
        │  URL
 2. ЧТЕНИЕ       host загружает и замораживает страницы — без модели
        │  frozen text
 3. ИЗВЛЕЧЕНИЕ   дешёвая модель на страницу: Live / Flash-Lite / GigaChat / Zen free
                 лёгкая схема {text, scope, quote, date, связь с домом}; ротация, параллельно в caps
        │  кандидаты
 4. ПРОВЕРКА     один пакет на результат: дешёвая модель ДРУГОГО провайдера (по умолчанию Flash-Lite)
                 явные вопросы по каждому факту: чей это субъект (дом / организация в доме /
                 памятник рядом / комплекс), план или событие, период
        │  вердикты
 5. ДОПУСК       host: цитата в frozen text, версии, fences → ledger и POI; факты видны сразу
        │
 6. ЭСКАЛАЦИЯ    только по поводу, не более одной на историю:
                 • после дешёвого круга < 3 полезных фактов, хотя источники прочитаны;
                 • проверка вернула insufficient или спор по субъекту для группы фактов;
                 • поиск не нашёл источников по двум вариантам запроса.
                 Тогда: агент с инструментами на более сильной модели (Gemini Flash, Space Bunny,
                 Codex Luna при наличии квоты) — только на недостающий участок, не весь заново.
```

### Правила выбора моделей

- Модели не фиксированы. Для каждой роли — список из конфигурации; выбор случайный с весами по измеренному успеху и задержке из существующего health-кеша, только среди здоровых и с квотой.
- В шагах 3 и 4 разные провайдеры. Модели OpenCode Zen — один провайдер.
- Одна доступная квалифицированная модель позволяет работать; её результат помечается как меньшая независимость.
- Сильные модели (Gemini Flash, Space Bunny, Codex Luna или Sol) — только в шаге 6. Codex — необязательный резерв при действующем согласии владельца и квоте. `native_quota.py` сейчас привязан к Luna: не выдавай это за поддержку Sol.
- GigaChat-2 не ставить проверяющим, пока он не возвращает валидный вердикт; как извлекатель и агент он полезен.
- Лимиты параллельности, токенов, времени и квот сохраняются.

## Одна смысловая проверка результата исследователя

По завершении каждого исследователя (или каждой страницы извлечения) запускай пакетную проверку его кандидатов дешёвой быстрой моделью другого провайдера — по умолчанию семейство Gemini Flash-Lite. Вопросы проверяющему явные и по каждому факту: чей это субъект, план или событие, период. Не запускай модель отдельно на каждый факт. Примерно 20 кандидатов на часть — ориентир контекстного бюджета, а не потолок исследования или числа полезных фактов. Деление не должно терять хвост результата.

Передай выбранный объект и устойчивый ID каждого кандидата, текст утверждения, его scope, заголовок и дату источника при наличии, цитируемый фрагмент с абзацами до и после. Контекст берётся из неизменяемой сохранённой версии источника. Если локального окна мало для определения субъекта, времени или связи с домом, разреши расширить контекст из той же версии. Не заменяй её незаметно свежей страницей.

Проверяющий возвращает вердикт по каждому ID, краткое основание и ссылки на использованные frozen chunks. Он оценивает субъект утверждения, связь с выбранным объектом, дом против организации/памятника/комплекса, период и модальность, дубли и противоречия. Некорректная строка, спорная дата или недостающий вердикт не отменяют остальные пригодные строки. Сохраняй принятые результаты и понятную причину непринятия каждого оставшегося кандидата.

Механическая проверка источника, цитирования, версий, прав и fences остаётся. Совпадение цитаты подтверждает наличие текста, но не идентичность объекта. Отсутствие дословной подстроки само по себе не означает ложность: допустимое перефразирование требует проверяемого смыслового основания в сохранённых chunks, а не обхода проверки источника.

Не наращивай список адресных запретов и контрольных формулировок. Дай исследователю разумную свободу искать, читать и объяснять связь сведений с объектом. Уточни компактный общий контракт результата и доказательства вместо очередного набора специальных правил.

## Когда независимого проверяющего нет

Не блокируй весь сценарий. Принять факт с честной меткой «проверен одной моделью» допустимо лишь тогда, когда сам исследователь уже предоставил полное смысловое основание: субъект, связь с выбранным объектом, scope, период/модальность и подтверждающие frozen chunks. Совпадения адреса, ссылки и цитаты для этого недостаточно.

Текущая [CANDIDATE_SCHEMA](https://github.com/onedayonemasterpiece/street-story/blob/06d652016171e0341a43fee654ec6404745fdd12/backend/street_story/fact_agent_providers.py#L21-L30) содержит только text, subject_scope, url, quote, source_date. Она не несёт такого основания. Минимально расширь существующий контракт либо сохрани результат как непроверенные кандидаты до смысловой проверки. Не превращай mechanical-only строки в accepted facts или подтверждённую POI-память. Полезные ранее подтверждённые факты остаются доступны.

## Параллельность и восстановление

Убери story-wide asyncio lock, который в [agent_evidence.py](https://github.com/onedayonemasterpiece/street-story/blob/06d652016171e0341a43fee654ec6404745fdd12/backend/street_story/agent_evidence.py#L405-L411) охватывает ожидание источника и модели. Используй существующие короткие транзакционные commits, проверку версий и fences; перед записью сверяй актуальность выбранного объекта и согласуй дубли. Сетевые ожидания разных пакетов могут идти параллельно в пределах resource caps. Публикуй результат проверки каждого исследователя по готовности, не жди завершения всех задач.

Поиск, извлечение и проверка — операции только на чтение: у них нет внешних побочных эффектов, а запись в ledger идемпотентна и выполняется host. Поэтому:
- закрытый отказ (ошибка, квота, неотправлено) — сразу следующий провайдер;
- нет ответа дольше дедлайна роли (ориентир — p90 модели × 2) — та же работа параллельно отдаётся другому провайдеру; первый закрытый результат принимается, поздний второй объединяется идемпотентно или отбрасывается; исходная операция продолжает наблюдаться по receipts и сохраняет свой UNKNOWN;
- повторно отправлять UNKNOWN тому же провайдеру с тем же ключом нельзя;
- для операций с внешним эффектом (публикация, списание квоты с подтверждением) прежнее правило «UNKNOWN не повторять» действует без исключений. При частичном результате сохрани проверенные строки и восстанавливай только незавершённое, без повторного исследования принятого набора.
