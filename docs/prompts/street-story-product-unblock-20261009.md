# Street Story: конкретный следующий шаг после аудита9 октября

Это порядок ближайшего исправления существующей ветки, не новая система требований. Полный действующий контракт: [единая постановка](street-story-unified-photo-search-20261008.md). Доказательства: [аудит stalled product](../reports/product-recovery-validation-20261009.md). Проверенный head —3a568a7, PR246. Продолжи существующий work, сохрани11 critical requirements, Live-first, ordinary queues/receipts/UNKNOWN и общий лимит canary. Не начинай с очередного полного live прогона.

## Цель

Ближайшая проверяемая веха: cold102 на подготовленном коде автоматически выбирает правильный физический объект и даёт первый reviewed substantive fact в POI. После неё выполнить полный действующий порог и оставшиеся ограниченные canary; один факт не считать release PASS.

## 1. Исправь представление уже имеющихся свидетельств

Не ищи заново GPS и адреса102: они уже были в frozen input299. Правильный footprint381/113 имеет boundary21,1м и сектор35,6°; входы204/206 несут Житомирскую22/24 и actual membership к нему. Выбранный374/102 — Коперника21,185,4м и5,4°. Эти конкретные IDs/адреса — только offline fixture/acceptance oracle; runtime не получает их как expected answer.

В identity_source_selection.py, identity_model_context.py и существующем map context собирай одну короткую строку на physical body: neutral pointer, контур/видимая сторона, расстояние и угловой сектор, реально присоединённые адресные entries с provenance, существенные unknown. Для нескольких входов сохраняй разные номера и общий footprint; не превращай адресный entrance в выбранное здание. Модель не должна вручную соединять четыре большие таблицы, чтобы узнать адрес безымянного контура.

Полный OSM pool и широкая карта остаются доступными для расширения. Не возвращай hard nearest-top8 и не исключай tele111 из-за185–189м. Контекст конкретного решения делай компактным по области/наблюдаемым отношениям, с явным расширением; не прикрепляй каждый раз все716IDs и334 поисковые строки. Не вводи новый сервис ранжирования или обязательный многоступенчатый planner.

## 2. Исправь ложную достаточность geometry/text

В identity_discovery.py, identity_proof.py и существующей response schema различай ссылку на реальный primitive и проверяемое соответствие SOURCE. Сохранённый ответ «контур соответствует», yaw=снизу вверх, sensitivity=детализация, alternatives=[] не должен получать статус достаточной geometry лишь за заполненные строки.

Для geometry модель в том же joint call должна указать различающий наблюдаемый паттерн и реальную связь с геометрией: например, угол/две стороны, последовательность зазоров и отступов, окончание улицы, либо масштаб/видимая сторона при допустимой позе. Направление по горизонтали не путать с pitch. Существенные альтернативы брать из показанного физического контекста и прежнего conditional prior, а не только из IDs, которые модель добровольно повторила. Не требуй механически отвергнуть все объекты patch или придумать соседа, которого нет.

Host проверяет существование IDs/segments, буквальные адресные joins, рассчитанные числа и структурную полноту. Модель оценивает визуальное соответствие и выбирает объект. Не подменяй это scoring weights или сравнением с hidden expected. Не добавляй независимый paid judge. Один обязательный список alternatives не решает задачу; повторный вызов допустим только в существующем бюджете, когда он получает конкретное новое свидетельство либо исправляет установленную ошибку формата. После достаточной geometry внешнее фото не требуется.

Для текста сравнивай индивидуальную структуру: этажи/оси, форму и изменение эркера, композицию входов, угловое решение. Общие карнизы, штукатурка и арочные перемычки сами по себе не различают дома. Неизвестное/неописанное свойство не считать отрицанием; цвет после реставрации — слабый сигнал. Если текста недостаточно, сохрани неопределённость и выбери один полезный способ её снять.

## 3. Убери неправильную адресную привязку и лишнее ожидание

prepare_regional_catalogue сейчас может взять reverse road камеры и передать одну привлекательную именованную карточку. В299 это Коперника/ломбард2306; тело статьи не читалось. В045 тело2306 читалось, но правильной3875 там не было.

Предметный lookup строить по footprint/его подтверждённым address entries; при отсутствии адреса — по географии кандидата. Reverse address камеры остаётся необязательной справкой. Полнота каталога одной улицы не означает полноты всей сцены. Используй существующий Prussia adapter и реальные публичные формы; максимум1–2 полезных тела, без нового обхода сайта. Сначала воспользуйся уже переданными адресами, не делай лишний OSM запрос.

В identity_discovery.prepare_search_plan не удерживай готовую SOURCE/MAP operation безусловным await холодного каталога. Если каталог готов, включи его; если нет, geometry может решить задачу, а поздний результат доступен имеющемуся продолжению. Недостаточная geometry не должна предотвращать чтение действительно нужного текста.

## 4. Исправь размер всего адресованного входа

В299 prompt=91 977chars/98 329UTF8bytes. Отдельно старый fallback62 507chars превращался в110 579 после schema. Google compact transport уже есть; text fallback ещё получает strict schema. Native проверяет базу до schema; Live имеет24 000-byte ceiling.

В identity_discovery.py/research_adapter.py дай text-only discovery небольшой соответствующий его роли контракт, без запрещённых ему SOURCE/MAP acceptance branches и повторных огромных ID enums. В opencode_research.py/live_research.py считай полный отправляемый input после всех добавлений. Используй роли и существующие лимиты; не увеличивай лимит как исправление и не маскируй oversize под quota.

До нового canary зафиксируй только нужные размеры до/после: полный textual request в bytes, число candidate rows, images и их размеры, actual model. Provider total tokens не называй input tokens. Не создавай новую подсистему метрик ради этой проверки.

## 5. Короткая проверка и выход к продукту

Пока configured SOURCE/MAP role имеет definitive RPD not_sent, не посылай paid inference/probe. Не подставляй Lite. Время предполагаемого reset и model metadata сами по себе не являются admission. Существующие readback/UNKNOWN правила сохраняются.

Используй frozen102 без сети: адресные joins видны рядом с anonymous body; pointers не превращаются в invented OSM IDs; старый формальный generic geometry не объявляется содержательно достаточным; полные inputs укладываются в реальные transport budgets. Для положительного пути используй имеющиеся содержательные geometry/text fixtures. Эти проверки не доказывают, что новая модель распознает SOURCE; не называй их product PASS. Не добавляй десятки тестов, повторяющих поля реализации.

Когда ordinary admission разрешает configured model, один cold102 на подготовленном release candidate. Wrong physical→обычный fenced Stop. Correct physical→первый source-backed independently reviewed substantive POI fact→полный порог102≥3 чистых атомарных факта. Сохрани caps180/300/480с от upload. Затем104≥3; для111/130/132 — заранее зафиксированный порог manifest по единой постановке§11, причём один факт допустим только при заранее обоснованном малом материале. Все случаи проверять на том же release candidate; общий live список максимум5, без параллельного multi-case burn. Новый failure требует конкретного диагноза, а не немедленного общего reask.

Сохранённые source bytes/OSM/original и совместимые evidence можно переиспользовать; old successful104 не превращается в acceptance нового кода. Доказательства новой product behavior должны относиться к deployable version. После full product acceptance — тот же SHA в release, health source_sha readback, один owner-path smoke и существующий incident update. Важен результат для владельца, а не число SHA/тестов/документов.
