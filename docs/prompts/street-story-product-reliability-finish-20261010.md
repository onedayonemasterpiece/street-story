## 2. Убери общие причины, из-за которых резерв не спасает

### 2.1. Раздели результат работы и завершение учёта ресурса

`native_vision.py:578–622`: JSON проверен, `phase=completed` и результат сохранены; затем `return` проходит через `finally: await lease.finalize(...)`. Ошибка удалённого RPC способна заменить успешный возврат ошибкой. Сам результат на диске не потерян, но вызывающая цепочка получает отказ. Аналогичный риск проверь у существующих Live/OpenCode-обёрток, не создавая новую систему транспорта.

После **реально разрешённой отправки и сохранённого полного проверяемого ответа** недоступность accounting-finalize не должна блокировать использование этого ответа. Сохрани исходную незавершённую финализацию в существующем журнале операции и восстанови её по той же lease/idempotency identity. Резерв не освобождай предположением, расход не обнуляй; новые платные действия без допуска запрещены. UNKNOWN до ответа не превращается в completed. Stop/смена фото по-прежнему проверяются перед продуктовой записью.

Тест: модель завершилась, локальный receipt сохранён, finalize недоступен → результат доступен, учёт ожидает восстановления, новый inference не отправлен; после восстановления одна финализация. Отрицательный тест: допуска не было или отправка остаётся неизвестной → положительного результата нет.

### 2.2. Не держи POI-lock на сетевом ожидании

`headless_fact_review.py:422–446` держит `_COMMIT_LOCKS` вокруг подготовки, `await _run_one` и до четырёх пакетов. Независимая проверка другой истории того же POI ждёт медленный inference первой. Это воспроизведено отдельным запуском точного AST метода с fake I/O; другой POI не блокируется.

Сократи критическую секцию до необходимой подготовки/фиксации. Модельная работа выполняется вне общего POI-lock. При commit проверь версии именно затронутых утверждений, evidence и зависимостей; используй существующие fences/транзакции. Не убирай защиту дубликатов и конфликтов. Если пакет действительно устарел — переоцени затронутую часть, не запускай заново весь POI и не сериализуй все сети ради удобства.

Тест: две истории одного POI, непересекающиеся кандидаты, первый reviewer ждёт Event → второй действительно доходит до своего результата. Дополнительно пересекающиеся утверждения, поздний ответ и Stop не дают неверного commit. Используй управляемые события, не `sleep(0.05)` как доказательство готовности.

### 2.3. Разные модели не являются независимыми от общего control plane

`research_adapter.py` создаёт один Control для нескольких WorkloadAdmission. Установленный ARC-клиент совпал по SHA256 с исходниками `ai-resource-control` на `cf2792ee`; `Config.timeout_seconds=3`, `request` обёрнут в `asyncio.timeout(timeout+0.5)`, RPC имеет один повтор. Ночные 49–60 s нельзя без измерения объяснить только медленной Supabase. Возможны блокировка event loop, ожидание цепочки RPC, cleanup или override конфигурации.

Раздели время очереди, подготовки, допуска, SDK и cleanup. При повторении SIGKILL собери exit/journal/cgroup memory-events по нужному процессу; не утверждай OOM без свидетельства. Не трать всю итерацию на исторический kill, если на нормальном стенде он не воспроизводится.

Ограничь существующий допуск и попытку оставшимся временем операции, не только отдельный HTTP-запрос. Не пытайся спасать общую недоступность control plane перебором всех ключей. В этот период разрешённые локальные/cache-операции и уже полученные результаты продолжают работать. Не добавляй второй реестр квот и не используй устаревший положительный допуск как разрешение новой отправки.

Внутри identity сейчас есть последовательные маршруты; Native по умолчанию может ждать 120 s при общем пороге180. Не оставляй независимому T/REF/другому разрешённому маршруту только остаток после полного первого timeout. Выбирай полезное следующее действие по данным и оставшемуся времени, используя существующую очередь. Перекрытие допустимо только для независимой разрешённой операции со свободным ресурсом; не повторяй UNKNOWN под новым ключом. Не запускай все модели на каждый снимок.

Не устраивай новую серию аудитов, турниры моделей, общий рефакторинг тысяч строк, новый планировщик, вторую POI-базу или очистку чужих проектов. Длинные задачи запускай существующими durable jobs, читай их результат и продолжай тот же work. Сохраняй checkpoint на содержательном рубеже, не после каждой строки.
