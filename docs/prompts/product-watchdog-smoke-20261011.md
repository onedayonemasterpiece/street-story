## Выполнение

1. Прочитай свежую guidance revision 0. Зафиксируй фактическое UTC-время, blob SHA и revision. Сразу отправь в этот тред:
   `WATCHDOG_READY revision=0 observed_at=<UTC ISO8601> blob=<SHA> deadline=<UTC +5min>`
   READY — промежуточное сообщение, не финальный ответ. Если при первом чтении revision уже не 0, честно сообщи START_STATE_MISMATCH: этот запуск не измеряет live-обновление; не притворяйся, что ожидал его.
2. Оставайся активным и перечитывай свежий файл примерно каждые 30 секунд, начиная от READY, максимум 5 минут. Между чтениями используй короткое ожидание; не запускай один долгий блокирующий shell/tool call. На каждом цикле возвращай управление агенту, чтобы принять прямое сообщение владельца. Не засоряй чат одинаковыми heartbeat.
3. При revision 1 проверь, что дополнение укладывается в безопасный smoke scope. Сразу выполни его в ответе этого же треда и выведи:
   `WATCHDOG_ACK revision=1 observed_at=<UTC ISO8601> blob=<SHA> nonce=<точное значение из guidance>`
   Затем своими словами кратко повтори продуктовую цель и один следующий полезный шаг; укажи, что действие теста реально выполнено. Не начинай реализацию. Дополнение появится только после READY; не угадывай его заранее.
4. Успех — ACK новой ревизии с точным nonce и содержательным ответом. Если rev1 содержит published_at, укажи observed_at − published_at как наблюдаемую задержку с оговоркой о синхронизации часов. Watchdog отдельно сверит серверное время GitHub commit и время ACK в треде.
5. Если за 5 минут revision 1 не получена, сообщи `WATCHDOG_TIMEOUT`, последнюю revision, последнее успешное UTC-чтение и число успешных проверок. Это не успех. При отказе доступа сообщи `WATCHDOG_BLOCKED` с точным инструментом/ошибкой и не обходи ограничение. При временной ошибке сети сохраняй прежнюю revision, честно учитывай неуспешное чтение и повторяй только разрешённые короткие проверки до того же срока.

После ACK либо timeout/блокера закончи только этот smoke-тест. Ночную продуктовую работу этот короткий тест автоматически не запускает. Ни READY, ни быстрый ACK не доказывают непрерывную работу всю ночь: проверяется лишь чтение живого GitHub guidance и применение одного уточнения. Прямой steer в native thread — отдельный механизм, для этого теста он не требуется.
