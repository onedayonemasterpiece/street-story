# 1. Продуктовая цель

Владелец выбирает фото / уже имеет подтверждённый объект и говорит Мире примерно:

> «Найди интересные факты об этом месте.»

Street Story должен реально:

1. найти информацию в интернете;
2. прочитать найденные источники;
3. получить содержательно богатый набор evidence-backed фактов;
4. сохранить источники/evidence;
5. показать факты пользователю в обычном story UI;
6. дать выбрать нужные факты;
7. построить draft из выбранных фактов;
8. продолжить обычный publication flow.

**Это и есть результат задачи.**

Не benchmark, не fixture, не красивый acceptance report, не количество тестов.

Работающий продукт с несовершенным recall значительно лучше отсутствующего продукта.

# 2. Исходная архитектурная гипотеза — НЕ ПОТЕРЯТЬ

Изначальная гипотеза проекта:

- `gemini-3.8-live` доступна для нашей задачи с очень низкой / практически нулевой предельной стоимостью;
- она слабее сильных batch-моделей;
- зато можно делать **много маленьких, простых, хорошо ограниченных semantic operations**;
- за счёт итеративности, evidence и большого числа дешёвых шагов можно получить достаточные объём и качество фактов;
- отдельно тратить более дорогие модели в normal path не требуется, кроме поиска/получения источников и только явно доказанных исключений.

**Сначала докажи или опровергни эту гипотезу рабочим продуктом. Не заменяй её молча другой архитектурой.**

Если позже реальная эксплуатация покажет, что Live объективно недостаточна — это отдельное измеренное продуктово-экономическое решение.

# 3. Normal path: Live-first

Normal path должен быть максимально простым.

Концептуально:

```
Mira / Gemini 3.8 Live
    ↓
research goal
    ↓
search + fetch sources
    ↓
small source chunks
    ↓
many small Live semantic operations
    ↓
atomic fact + own evidence
    ↓
mechanical validation + persistence
    ↓
facts visible to owner
    ↓
selection → draft
```

## Live делает семантику

Live должна:
- понять research goal;
- по небольшому chunk выделить полезные факты;
- сформулировать их атомарно;
- привязать каждый тезис к собственному evidence;
- сохранить qualifiers/неуверенность;
- при необходимости сравнить небольшое количество уже найденных тезисов на semantic duplicate/conflict;
- продолжить со следующим chunk.

Не загружай Live огромными документами/пакетами/ID одновременно.

**Слабость модели компенсируй простотой и малым размером каждой операции, а не каскадом других моделей.**

## Код делает механику

Детерминистический код:
- search/fetch transport;
- URL safety;
- frozen source version;
- chunk/page cursor;
- exact spans;
- schema/reference validation;
- idempotency;
- persistence;
- resume;
- resource budget;
- telemetry;
- отображение состояний.

Regex/keyword/year/person-name правила не решают семантику.

# 4. Non-Live helper — не normal path

Сейчас в ветке уже есть non-Live semantic helper/review механика.

Не удаляй полезный код только ради чистоты, но:

**normal path не должен требовать сильную/non-Live модель для получения фактов.**

Допустимо использовать non-Live model только если:
1. есть конкретный воспроизводимый blocker Live-first path;
2. blocker измерен на обычном продуктом сценарии;
3. маленькое targeted использование helper реально исправляет его;
4. это не превращается в новый обязательный многоступенчатый pipeline.

Не надо заранее строить:
`Live → helper → repair → superseding review → Live review`.

Если Live-first уже выдаёт полезные факты — поставляй продукт и измеряй качество.

---

# 5. Repair/review не должны управлять продуктом

Сохрани уже полезные:
- frozen sources;
- evidence ledger;
- immutable observations;
- revisions;
- stale guards;
- checkpoint/resume;
- quarantine;
- selection persistence.

Но recovery-механизмы:
- `repair_research_fact`;
- superseding review;
- сложные retrospective review packets;

не должны быть обязательным этапом каждого нового исследования.

Их назначение — редкий пересмотр уже сохранённого результата.

**Новый факт должен по возможности сразу сохраняться как хороший atomic evidence-backed fact.**

Если один кандидат сомнителен:
- withhold этот кандидат;
- продолжай run;
- оставшиеся хорошие факты доступны пользователю.

Не превращай один плохой факт в FAIL всего продукта.

---

# 6. Полнота: прагматично, без новой крайности

Нет требования найти 100% всех фактов об объекте.

Нет и требования остановиться на 2, 3 или 10 фактах.

Цель — **полезный богатый набор**.

Для разработки:
- пройди найденные и выбранные для текущего research run источники/chunks достаточно полно;
- не вводи искусственный product top-N, после которого чтение прекращается;
- pagination/batch limits только технические, с continuation;
- если run прерван лимитом/временем, уже найденные хорошие факты остаются продуктовым результатом, а run может продолжиться позже.

На контрольном corpus можно измерять recall.
Ориентир порядка **~70% очевидных полезных reference facts уже является хорошим MVP-уровнем**, но это:
- quality metric;
- не жёсткий release gate;
- не требование найти ровно 70%;
- не повод блокировать рабочий продукт из-за недостающих фактов.

## Шаг B — один обычный продуктовый прогон

Возьми подтверждённый объект, например Королевские ворота.

Запрос должен быть обычным пользовательским, без названий ожидаемых фактов, internal tools и guided sequence.

Используй:
- real Internet search/fetch;
- `gemini-3.8-live`;
- normal configuration;
- без принудительного helper outage;
- без обязательного non-Live semantic helper.

Проверь результат человечески:
- факты полезные;
- фактов не символические 2–3, а нормальный набор для публикации;
- источники есть;
- evidence относится к конкретному факту;
- явная ерунда/неподтверждённое не становится selected fact;
- известные отдельные фигуры фасада не склеены в один тезис, если источник позволяет выделить их отдельно.

Не требуй совершенства.

Если из условных 15–20 потенциально интересных тезисов получили 10–15 хороших — это гораздо ближе к успеху, чем очередной FAIL всего run из-за одного спорного утверждения.

## Шаг C — продуктовый UI

На реальном результате:
- facts появляются в обычном Android/story UI;
- пользователь может увидеть источник;
- выбрать любое подмножество;
- selected facts сохраняются;
- draft создаётся из выбранных facts;
- withheld candidate не попадает в draft.

Не ограничивай найденный набор количеством фактов, выбранных в smoke test.

## Шаг D — один holdout smoke

После рабочего продукта на первом объекте проверь **один** другой POI обычным запросом, чтобы исключить hardcode под Королевские ворота.

Это smoke, не новая исследовательская программа.

# 8. Правило итераций

Не запускать десятки одинаковых прогонов.

На любой fail:
1. определить первый реальный product blocker;
2. исправить только его;
3. один повтор.

Если полезный продукт уже работает, **не блокировать поставку из-за следующего уровня качества**, который можно улучшать после релиза.

Не вводить новый framework/service/model-router/recovery layer без доказанного blocker.

# 10. Что НЕ считать причиной задерживать продукт

Само по себе не блокирует релиз:

- не найден некоторый факт;
- recall меньше идеального;
- один candidate withheld;
- benchmark не 100%;
- старая recovery ветка не идеально красива;
- есть возможность улучшить semantic dedup;
- можно сделать review ещё строже;
- можно добавить более сильную модель.

Блокирует:
- research вообще не выдаёт полезный набор;
- факты массово не имеют evidence;
- normal path требует ручного вмешательства;
- факты не видны/не выбираются;
- selected facts не доходят до draft;
- очевидно неподтверждённые факты массово проходят как подтверждённые;
- продукт не развёрнут/не запускается.
