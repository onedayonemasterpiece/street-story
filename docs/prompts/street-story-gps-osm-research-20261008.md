## 1. Что теперь доказано и что поручается агенту

В предыдущем исследовании не была доведена до конца работа с оригиналами и координатами. Это существенно: описание фасада без положения камеры привело к общим поисковым запросам, непроверенным адресным гипотезам и преждевременной остановке. В этом исследовании получены все **девять уникальных оригиналов Telegram 104–112**, извлечён их EXIF, просмотрены фотографии, получены реальные векторные данные OSM и построены карты окружения. Повторная ссылка на 109 с `?single` не является десятым изображением. **Физическая identity установлена для всех девяти случаев по реальным внешним фотографиям и пространственной привязке.** Для 105 и 108 историческое содержание остаётся ограниченным; для 111 подтверждён дом, при этом верхний фонарь не виден на найденном REF.

Продолжи существующую реализацию, устранив доказанные потери информации между original → EXIF → OSM → совместным решением модели → принятой physical identity → facts. Достаточное SOURCE + geometry соответствие само закрывает identity; внешний REF является альтернативным доказательством либо адресным уточнением нерешённой неоднозначности. Не подменяй эту работу увеличением числа моделей, общим поиском всех достопримечательностей города или новым полным прогоном после каждого изменения.

Цель — чтобы обычный путь загрузки самостоятельно нашёл физический объект на фотографии и проверенные сведения о нём. Известные исследователю адреса и подобранные фотографии ниже — **закрытые ожидаемые ответы для проверки**, а не подсказки в runtime. Запрещены ветки по Telegram ID, filename, hash, координатам этого корпуса, адресам или заранее подобранным URL. Универсальные правила извлечения геометрии, построения карт, discovery, отбора медиа и работы с источниками разрешены и необходимы.

Сохрани `.devcoveer/requirements.json`: модель выполняет семантическую интерпретацию, выбор гипотез, сопоставление изображений, извлечение и разрешение противоречий. Код читает метаданные, считает геометрию, обеспечивает транспорт, кеш, лимиты и очередь. Live-first для обычных небольших семантических операций, независимая работа backend при закрытом клиенте, общая POI-memory и бюджетные ограничения прошлого задания остаются обязательными.

### Граница доказательства

Ручное нахождение внешнего снимка не доказывает автоматический PASS текущего продукта. В ходе этой работы не запускались внешние inference-запросы через продукт, Google/Z.ai canary, массовые cold runs или deployment. Приведённые короткие маршруты — проверенные исследовательские пути и проектируемый способ сократить работу; это не выдуманная статистика latency или числа модельных вызовов production.

Полезные сведения о здании могут иметь разную глубину. Доказанная identity, архитектурное наблюдение по фотографии, история учреждения и история самого здания — разные результаты. Нельзя обещать неизвестную дату или автора только ради численного количества фактов.

## 3. Векторная основа и численный эксперимент

Получено **девять успешных локальных OSM map snapshots**: восемь прямоугольников с полуразмером 240 м и один 420 м для 111. Это bbox, а не обещание точного кругового покрытия. Для каждого сохранены URL, время, размер и SHA-256 XML. Суммарно XML занимают 10 128 062 байта; успешный запрос занимал 5,30–8,24 с по сохранённым receipts. Это размер и длительности запросов геоданных, не время продуктового распознавания. Перед рабочим endpoint была одна неудачная попытка Overpass (HTTP406); она не записывается как успешный snapshot. После получения данных все пересчёты, сборка multipolygon, карты и анализ чувствительности выполнялись из кеша без повторного сетевого запроса.

Использованный endpoint — `https://api.openstreetmap.org/api/0.6/map?bbox=west,south,east,north`. Публичный OSM API здесь служит ограниченной исследовательской проверке, а не безлимитным production backend. Для продукта сохрани предусмотренный провайдер, кеширование и его реальные лимиты; при необходимости используй свой Overpass/геосервис. Геометрия OSM была доступна через API; запасной путь получения именно этой геометрии через браузер не понадобился.

Вычислены отдельные значения: расстояние до границы, расстояние до заполненного полигона, расстояние до bbox center, центроид, угловой интервал, ближайшие рёбра, inside/on-boundary, адресные точки, принадлежность частям и территориям. На картах присутствуют улицы, их названия, неподписанные здания, входы, север и масштаб.

### Чувствительность к положению камеры

Поскольку measured GPS error отсутствует, исследованы **сценарии**, а не вероятности:49 фиксированных точек внутри каждого диска 10/30/60 м. Они не утверждают, что GPS ошибся именно на 30 м или что 49 равновероятных положений описывают реальную ошибку. Приведённые min/max относятся только к проверенным 49 позициям и полным объектам кешированного участка; это не доказанные экстремумы по непрерывному диску или всей городской карте.

Для 107 диапазон ранга по границе составляет 9–12 при 10 м, 3–18 при 30 м и 3–24 при 60 м. В 10-метровом сценарии top8 теряет объект во всех 49 положениях. По bbox диапазоны ещё шире:12–17,9–26,4–35. Для 112 при 60 м диапазон по границе 1–7, по bbox1–15. Полные результаты и методика сетки приложены отдельно.

Для 111 диапазон ранга по границе —19–22,16–25 и 12–26 соответственно; top8 не содержит дом ни в одной из 147 проверенных позиций. Дополнительно, при фиксированном контуре расстояние до него изменяется не быстрее смещения камеры. Поэтому даже при любом смещении до 20 м ближайшая граница останется дальше `188,78−20=168,78м`, за пределом 160 м. Это строгий условный вывод для всего такого диска; он не означает, что фактическая погрешность GPS измерена как 20 м.

Следствие для кода: близкие ранги не превращаются в жёсткий запрет; необязательная оценка GPS должна менять степень уверенности и набор гипотез. Нельзя автоматически закрепить за каждым отсутствующим error значение 10 м и затем считать его измеренным.

## 4. Каждый объект: identity, реальные фотографии и факты

### 104 — башня Врангеля, ул. Профессора Баранова, 2 А

**Физическая привязка:** OSM `relation/3665416`,14 связанных building:part. На SOURCE читается DER WRANGEL. Реальная фотография Музея янтаря совпала по центральной надстройке с надписью, оконным проёмам, зубцам и характерным повреждениям кирпича слева. Это проверка конкретной башни, не общего сходства с круглым фортом.

**Проверенный источник и медиа:** [Музей янтаря](https://ambermuseum.ru/about_museum/museum_buildings/wrangel_tower/), [просмотренный внешний снимок](https://www.ambermuseum.ru/upl/ckeditor/f07eedb9c8676a631be97a5a5defb80f.jpg).

**Доступные сведения:** оборонительное сооружение у Верхнего пруда; вместе с башней Дона защищало этот участок укреплений; названо в честь Фридриха Генриха Эрнста фон Врангеля. Музей датирует сооружение 1859 годом, тогда как snapshot OSM содержит start_date=1853. Сохраняй расхождение и исходный смысл дат; не превращай start_date в единственную бесспорную дату завершения строительства. Для полезного первого рассказа доступны и другие, не зависящие от этого расхождения факты.

**Короткий путь:** читаемое имя → местный именованный контур → одна музейная статья с собственным фото → точное сравнение → извлечение из уже полученной статьи. Не открывать по отдельности четырнадцать частей башни и не запускать второй discovery только из-за перехода к facts.

### 105 — дом с округлыми стеклянными выступами; подпись источника «Университетская, 3»

**Физическая привязка:** OSM `way/105154961`,39,1 м до границы, 4-й кандидат по этому расстоянию. Точное совпадение найдено на трёх реальных ракурсах Артёма Светлова: старый краснокирпичный фасад, светлые горизонтальные пояса, узкая частая раскладка двух округлых стеклянных выступов. На SOURCE виден правый выступ. Ближайший БЦ «Юбилейный» был проверен внешним снимком и исключён: это другое современное здание.

**Источник и медиа:** [Flickr, основной снимок](https://www.flickr.com/photos/trolleway/54737039379), дополнительные [ракурс 1](https://www.flickr.com/photos/trolleway/54737019228/) и [ракурс 2](https://www.flickr.com/photos/trolleway/54735967382/). Авторские фотографии сняты 2 мая 2025 года. Дата съёмки — provenance, не исторический факт о доме.

**Сведения и ограничение:** внешний источник подтверждает устройство всего фасада: два полукруглых остеклённых объёма по краям и светлые пояса между ярусами. Это больше, чем видно в тесном исходном crop. Надёжные год постройки, архитектор и первоначальное назначение в проведённом поиске не установлены. Три фотографии одного автора не являются тремя независимыми историческими источниками.

В OSM есть и другая адресная точка «Университетская 3» в соседнем длинном доме. Поэтому identity хранится как совпавший physical footprint с provenance адреса, а не как единственная строка адреса. Юридический адрес в этой проверке независимо не установлен. Для приёмки физическая identity задаётся совпавшим контуром и визуальными доказательствами; адресная подпись остаётся атрибутом конкретного источника до разрешения конфликта. Историю Альбертины, соседнего Института гигиены или дома «Алемании» переносить сюда нельзя.

**Короткий путь:** локальная карта + признаки старого кирпичного фасада → несколько адресных гипотез разных направлений → адресная фотография → один точный pair. ## 5. Какая математика действительно нужна продукту

### 5.1. Система координат и разные расстояния

На небольшом участке можно использовать локальную метрическую проекцию. Для исследовательского расчёта использовано:

```text
x = R cos(latitude0) × radians(longitude − longitude0)
y = R × radians(latitude − latitude0)
R = 6 371 008,8 м
```

Это приближение для субкилометрового окна, не геодезическая съёмка. В production допустима корректная локальная ENU/UTM-проекция. Не считать градусы евклидовыми метрами и не использовать необработанные расстояния Web Mercator как расстояния на земле.

Для камеры C и ребра A→B:

```text
t = clamp(dot(C−A, B−A) / dot(B−A, B−A), 0, 1)
Q = A + t(B−A)
boundary_distance = min ||C−Q|| по допустимым рёбрам
polygon_distance = 0, если C внутри заполненного полигона; иначе distance до него
```

Нулевые рёбра обрабатываются отдельно. Отверстия multipolygon остаются отверстиями. `representative_distance_m` сохраняется для источников с POI-точкой, но не называется расстоянием до фасада. Overpass `out center` возвращает центр bounding box, а не гарантированную точку входа или центроид. Nominatim reverse находит ближайший подходящий объект своей базы; это не алгоритм определения предмета перед камерой.

Для составных зданий нужны две иерархии: whole physical entity и observed component/facade. До того, как конкретное ребро связано с видимым фасадом, значение остаётся **расстоянием до ближайшей границы всего контура**, не до сфотографированной детали.

### 5.2. Топология, адреса и части

Сохрани тип и ID каждого OSM-элемента, версии и роли members. Собирай outer/inner rings из открытых ways по общим node ID с учётом обратного направления. Отмечай отсутствующие members, незамкнутые цепочки, неоднозначную топологию и частичную геометрию. Не дорисовывай незамкнутый multipolygon произвольной линией и не обозначай incomplete как empty. Исследовательский helper явно маркирует ограниченный `geometry_validation_scope`: часть проверок вложенности выполняется по вершинам и промежуточным точкам. Это не математическое доказательство валидности произвольного GIS-полигона; production должен сохранять эту границу либо использовать подходящую полную проверку топологии.

Building:part связывается с доказанным физическим родителем; его имя/семантика не становятся отдельным конкурентом автоматически. Для Врангеля 14 частей должны дать один общий кандидат с доступными компонентами. Многоконтурный «Росгартен» остаётся двумя геометрическими компонентами одного связанного объекта, а не выпуклой оболочкой, включающей свободное пространство между корпусами.

Адреса связываются с контуром по прямому boundary membership/доказанному пространственному покрытию, с provenance. Если точка входа находится на границе, простой строгий point-in-polygon может её потерять. Группа адресов не превращается в один случайно выбранный номер. Территория школы/больницы, POI арендатора, подъезд и физическое здание — отдельные сущности со связями.

### 5.3. Углы, направление камеры и неопределённость

Азимут к точке: `atan2(east, north)`, нормализованный в 0–360°. Угловой интервал контура должен корректно проходить через 0°; это не обычный min/max чисел. Для камеры внутри полигона или вплотную к краю нельзя выдавать минимальный интервал по вершинам за надёжный сектор взгляда.

Нет компаса — нет единственного азимута камеры. Используй несколько пространственно различных гипотез, включая противоположные стороны улицы. Направление улицы, время EXIF, положение солнца без полноценной модели и последовательность чужих фото не подменяют GPSImgDirection. Если heading есть, учитывай True/Magnetic reference и его реальное происхождение.

При верхней границе смещения камеры u и фиксированной геометрии расстояние d становится совместимым с интервалом `max(0,d−u)..d+u`. Для одной фиксированной точки объекта на расстоянии d>u угловая неопределённость может достигать `asin(u/d)`. Например, 10 м на дистанции 20 м дают 30° — больше всего горизонтального поля 72 мм portrait. При смещении камеры ближайшее ребро может переключиться: формула для фиксированной точки не гарантирует такой же границы для bearing-to-nearest-boundary. Если d≤u, жёсткий направленный фильтр особенно опасен. Без measured error значения 10/30/60 м остаются сценариями чувствительности, не подставленным фактом.

### 5.4. Поле зрения, crop и верхние этажи

Если f35 обоснован и используется диагональное соответствие 35 мм, при соотношении сторон r=oriented_width/oriented_height:

```text
D = sqrt(36² + 24²)
w_equiv = D × r / sqrt(1+r²)
HFOV ≈ 2 atan(w_equiv / (2 f35))
```

Соответствующим образом вычисляется VFOV. Храни предположения и условность результата. Полный фасад, фрагмент, верхние этажи, башня и зум — признаки SOURCE, которые определяет модель. Небольшой объект на большом расстоянии и близкий crop могут занимать одинаковую часть кадра; f35 само по себе не даёт дистанцию.

Для фронтального отрезка ширины W, симметричного относительно направления на его середину, угловая ширина даёт `d≈W/(2tan(angle/2))`. При косом фасаде нужна проектируемая ширина и учёт положения камеры; crop купола требует отдельной модели видимого объёма. Используй диапазоны размеров и углов как приор правдоподобия, не как идентификатор здания. Не сравнивай ширину всего многокорпусного объекта с crop одной башенки.

### 5.5. Улицы и видимость

Сохраняй roads/footways/intersections отдельно от building candidates. По геометрии можно выделить расположение по сторонам улицы, длинные линии фасадов, углы перекрёстков и возможные направления открытого обзора. Это сокращает поиск, когда на SOURCE виден угол или перспектива улицы.

Окклюзия по 2D-карте является мягким признаком. Без высот, отметок рельефа, положения камеры и угла наклона нельзя отвергать верхний купол из-за низкого здания между камерой и объектом. Деревья на SOURCE, отсутствующая детализация OSM и снимок через проём также ограничивают строгие выводы. Полноценную 3D-реконструкцию города для этого исправления строить не требуется.

## 6. Эффективная стратегия исполнения

### A. Одна подготовка, несколько параллельных источников контекста

Сразу сохрани original SHA, метаданные и oriented preview. Один совместный SOURCE + map вызов может дать OCR с неопределённостью, наблюдения о фасадах/crop, выбор физического объекта и итог достаточности geometry. Для geometry proof нужны реальные SOURCE и карта; реальные SOURCE и внешний REF обязательны только внутри выбранной reference-ветки. Не добавляй обязательный отдельный observation/planner вызов, если joint call уже решает задачу.

Независимо получай local map patch и обратное геокодирование. Не заставляй готовые OSM-кандидаты ждать Wikipedia и общего landmark sweep. Сильный читаемый текст может сразу открыть одну адресную/именную поисковую ветку; это не отменяет последующий physical binding.

Начальное покрытие должно зависеть от наблюдений. Обычному широкому фасаду нужен компактный участок;240 мм и crop верхнего купола заранее требуют проверки более удалённых обычных домов, а не только landmarks. Исследовательские 240/420 м — измеренные параметры этой работы, не универсальная магическая константа. Зафиксируй мотивированный выбор региона и максимум одно расширение после анализа coverage в пределах первой попытки. Исчерпанный бюджет при недостаточном покрытии даёт `coverage_incomplete`/`budget_exhausted`, а не утверждение «объект отсутствует». Учитывай возврат полных ways/relations за пределами bbox и явную неполноту relations.

### B. Дать модели пространственную сцену до дорогого discovery

Для пространственного планирования передавай одинаковый versioned DTO и небольшой локальный рендер по готовности: камера, масштаб, север, контуры с короткими ID, улицы, адресные входы, связанные части, неопределённость и граница покрытия. Сильная OCR-ветка может стартовать независимо; готовая карта дополняет выбор физических кандидатов и binding, не заставляя повторять всю уже выполненную подготовку. У объекта сохраняются метры, интервал азимутов, размеры/компоненты, уровни при наличии и provenance. Не передавай тысячи вершин в каждом повторном prompt: полный snapshot хранится отдельно, компактная сцена переиспользуется.

Модель рассматривает до 2–3 содержательно разных гипотез из **полного полученного physical pool**, объясняя совместимость с SOURCE и существенные альтернативы. Они могут быть не самыми близкими и не исторически известными. Если совокупность SOURCE + geometry достаточна, тот же вызов принимает identity без discovery/REF; иначе выбирает одно различающее действие. Возможность продвижения объекта из observed в active нужна до дорогих запросов, а не только после случайного обнаружения подходящего фото.

Геометрический контекст не должен подсказывать готовую identity из этого отчёта. Цвета и детали фасадов, которых нет в OSM, не выдумываются. Карта может сама дать достаточное различающее доказательство вместе с SOURCE. Только существенный неразрешённый недостаток признаков открывает адресный reference search или другое наиболее полезное уточнение; отсутствие внешнего фото не понижает уже принятую geometry identity.

### C. Выбирать следующий шаг по новой информации

Сначала используй сильные именованные/OCR leads, затем адреса геометрически совместимых зданий и их групп, затем конкретную следующую неопределённость. Не повторяй «красный дом с башней Калининград» другими словами, если новых кандидатов такой запрос не даёт.

Один запрос может искать фото и содержательную статью одновременно. Первичная карточка учреждения, муниципальная архитектурная галерея, музей, проектировщик/подрядчик современного дома часто полезнее общего агрегатора. Доступность конкретного источника важнее формального предпочтения домена: один недоступный официальный сайт не блокирует другие доказательства.

Храни журнал: hypothesis → query → новые entities/URLs → outcome → следующая нерешённая часть. Нулевой результат, временная ошибка транспорта, captcha, найденная статья без нужной фотографии и доказанное несовпадение имеют разные причины остановки. Не обходить защитные страницы; выбирать доступный источник. Не повторять одинаковую отправку с неизвестным outcome.

### D. Условная reference-ветка: извлечение медиа и сравнение

Этот раздел применяется, если внешняя фотография нужна для разрешения оставшейся identity-неоднозначности. При принятой geometry весь раздел пропускается; ноль внешних фото и pair calls является допустимым полным identity-результатом.

Разбирай scoped gallery, `srcset`, lazy attributes, ссылки на оригиналы и доступные метаданные страницы. Сохраняй соответствие article → image URL → caption/section → physical subject. Карточки «другие места», логотипы, карты маршрута, интерьеры квартир и tracking pixels не становятся равноправными фасадными REF.

При единственном качественном REF или очень малом однозначном наборе сразу переходи к exact pair: отдельный вызов triage не нужен. Для галереи с несколькими ракурсами сначала собери один контактный лист небольших изображений. Exact comparison выполняется только для 1–2 отобранных полноразмерных кадров, затем при необходимости ещё для конкретной альтернативы. Галерея 107 показывает, почему первый снимок не гарантирует нужную часть;110 — почему другое крыло не означает отказ всему источнику;112 — почему пустой text extract не доказывает отсутствия медиа.

Контактный лист выбирает перспективные кадры, но не является окончательным доказательством. Exact pair должен назвать соответствующие локальные детали и видимые противоречия, отделить ремонт/ракурс от смены объекта, подтвердить scope и связать REF с физической сущностью. Сохраняются SOURCE/REF hash, ориентация, article provenance и результат binding.

### E. Факты начинаются после принятой identity и проверки предмета текста

После принятой identity с `proof_kind=geometry` или `visual_reference` немедленно используй подходящий уже полученный текст: проверить предмет/область статьи → нужный фрагмент → семантическое извлечение → review → shared POI readback. Реально связанная с просмотренным REF статья переиспользуется по существующему reviewed-reference path; для geometry она не обязательна. Не запускать image search ради допуска к фактам. Первый подтверждённый полезный факт доступен до завершения всех остальных источников.

Для современного дома переключайся на строительство, проект, назначение и изменения, а не требуй краеведческую биографию. Для исторического здания не смешивай время строительства, юридическое создание учреждения, открытие музея, реставрацию и дату обновления реестра. Для ансамбля/крыльев указывай scope каждого утверждения. Похожие адреса и несколько публикаций одной фотографии не доказывают независимость источников.

Если сведения объективно ограничены после небольшого целевого поиска, сохрани identity и найденные конкретные данные, но не объявляй полноценную историческую карточку. Случаи 105/108 должны проверять честную границу, а не становиться поводом дописывать неустановленные даты.

Это проверки конкретных потерь информации и контрпримеров, не десятки тестов, повторяющих каждую строку реализации. Переиспользуй существующие fixtures/transport. Никакой inference не нужен, чтобы проверить арифметику, поля DTO, topology, source mapping и дедупликацию.

### Затем ограниченная автоматическая проверка

Для обычного поддержанного быстрого случая цель обработки identity ≤30с после доступности SOURCE при одном joint call; end-to-end от upload и первый eligible fact измеряются отдельно. Это цель реализации, не результат данного ручного исследования. Сохраняются hard acceptance caps сложного fallback: identity до3 минут, первый полезный eligible fact до5 минут, завершение до8 минут от upload. Цель первого факта до3 минут отслеживается отдельно. Их нельзя задним числом ослабить, сославшись на удачное ручное исследование.

Перед canary зафиксируй одну candidate version, config/provider revision и ожидаемую глубину сведений. Актуальный согласованный набор — **102, 104, 111, 130, 132**, максимум пять полных случаев на одну выпускную приёмку; первые canary входят в эти пять. 107/109/120/121/122 и новые106/125/126/130/132 используются как сохранённые offline/targeted fixtures без отдельной полной серии. После системного дефекта останови серию, исправь и повтори только затронутый путь.

Все 9 кейсов должны иметь честный статус исследования. Автоматическое нахождение в один новый release проверяется без handpicked REF/адресов этого документа. Для объектов с богатыми подтверждёнными материалами ожидаются минимум 3 содержательных eligible facts; для ограниченного материала — минимум 1 конкретный полезный подтверждённый eligible fact с заранее зафиксированной ожидаемой глубиной. Наблюдение по SOURCE/REF должно сохранять свой тип и не засчитывается автоматически как исторический eligible fact; это решается существующим semantic review. Если не получен даже один подходящий факт, identity остаётся подтверждённой, но фото→facts PASS не достигнут. Unknown дата не становится известной ради PASS; факт «файл загружен в 2025 году» не заменяет историю здания.

Отчёт на каждый автоматический run: original SHA, metadata class, map snapshot SHA/bounds, полный observed pool, выбранные IDs и причины, release/config, cold/warm/recovery, принятая identity, proof_kind и scope, SOURCE/map hashes и использованные REF hashes только при наличии, существенные предположения/альтернативы, время identity/first fact/total от upload, reviewed eligible facts с источниками, actual sends/tokens/bytes, empty/failed/not_sent/unknown и stop reason. Для маленького корпуса не выдавай p95 за устойчивую статистику.

Только после backend PASS выполняется один предусмотренный emulator E2E. Работа этого документа не является разрешением на публикацию пользовательских фотографий наружу или отдельную социальную публикацию ради теста.

## 9. Что считать завершением доработки

Агент должен показать на одной версии, что GPS и геометрия реально меняют запросы и сохраняют правильный объект до discovery; затем что реальные изображения дают корректный physical binding; затем что принятые факты доступны в POI-memory и истории при закрытом клиенте. Исправленные поля или красивый рендер карты без такого пути не закрывают продуктовую задачу.

Эффективность доказывается уменьшением бесполезной работы при сохранённом результате: не раскрывать 14 частей башни как 14 домов, не перебрать десятки общих запросов без GPS, не скачать всю квартиру ради одного фасада, не прочитать все музейные интерьеры, не начать facts discovery с нуля, не платить второй раз за незакрытую отправку. Реальные ресурсные показатели предъявляются из receipts, а не оцениваются на глаз.

Гарантировать произвольную историческую информацию для любого дома нельзя: она может отсутствовать в доступных источниках. Проверяемая инженерная гарантия — не потерять доступные исходные данные, не отсечь объект неверной математикой, выполнить ограниченный мотивированный поиск и вернуть доказанное содержание с явной границей неизвестного. Распознанный дом с ограниченной историей и неизвестный объект — разные исходы.

Полный [воспроизводимый пакет](../research/20261008-gps-osm/README.md) включает нормализованный EXIF manifest, девять gzip-копий исходного XML, fetch provenance, карты, скрипты и ожидаемые таблицы. Из его каталога достаточно выполнить:

```bash
python3 -I -S reproduce.py --output reproduced
```

Для повторного построения карт при уже установленном matplotlib:

```bash
python3 -I reproduce.py --maps --output reproduced-with-maps
```

Пакет проверен в отдельном пути с пробелами при другом CWD, с отключённой сетью и без продуктового inference. `offline_reproduction_pass` относится к математике; он не подтверждает автоматический visual/facts pipeline. Фотографии в Git-пакет не включены: ссылки на просмотренные внешние кадры приведены в разделе 4, исходные bytes доступны владельцу по указанному серверному каталогу. Подсветка ожидаемого объекта на исследовательских картах используется только для анализа результата; модель самостоятельного replay должна получать карту без ответа.

Приложенные исследовательские скрипты повторяют сборку геометрии, расчёт расстояний, карты и сценарии чувствительности на сохранённом XML. В manifest указаны оригинальные URL и SHA каждого snapshot; сетевое обновление создаёт новую версию данных, а не незаметно заменяет старый эксперимент. Фотографии остаются собственностью своих авторов; ссылки и визуальное сравнение используются как исследовательские доказательства, не как набор иллюстраций для автоматической перепубликации.
