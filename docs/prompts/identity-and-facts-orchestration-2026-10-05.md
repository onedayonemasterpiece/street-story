# Street Story — единая доработка идентификации, исследования фактов и доступности моделей

Дата: 5 октября 2026. Документ подготовлен ChatGPT после совместного разбора двух исполнительных тредов, текущего релиза и предыдущего OpenCode-пилота. Это постановка на продолжение, не отчёт о выполненной интеграции.

## 0. Как использовать документ

Это **новая основная исполнительная постановка**. Она заменяет последовательность и границы предыдущей `opencode-parallel-research-product-finish-2026-10-05.md`, но сохраняет её результаты измерений, ограничения безопасности и незавершённые операции. Предыдущий документ — справочное приложение, не второй независимый заказ на реализацию.

Не запускать полный текст одновременно двум независимым writers. Один действующий Codex-тред отвечает за интеграцию и релиз. Второй может продолжать только явно выделенный участок с общей согласованной границей. Код не начинать заново; повторный общий аудит или турнир моделей не требуются.

Цель владельца: он выбирает фото и может не знать название объекта. Сервис сам формирует гипотезы, находит изображения из разных источников, проверяет фактическое совпадение с фото, затем приносит пригодные факты. На просьбу «найди ещё» исследование расширяется, а не перечитывает завершённые статьи. Временная недоступность конкретной модели/поиска/квоты не должна уничтожать или завершать эту работу отказом.

Уточнение новой постановки: визуальное решение принимает **проверенная модель с image-input**, не обязательно текущая голосовая Live-сессия. Mira остаётся собеседником и редактором. Live-first — приоритет разумной стоимости и переиспользования, а не обязательная зависимость каждого фонового шага от живого микрофона. LLM-first, защита доказательств, выбор автора и общий POI-корпус сохраняются. Изменять более широкие продуктовые требования несогласованно нельзя.

## 2. Новые конкретные выводы из кода

Проверены исходники релиза `57df972…`, а не только отчёты:

- `identity_discovery.py::web_image_sources` вызывает только `service.providers.gemini.discover_article_urls`. Ошибка уже не превращается в успешную пустую выдачу, но независимого search provider в этом входе нет. OpenCode нужно подключить **и здесь, до подтверждения POI**, иначе прежняя постановка запускает его слишком поздно.
- `live_visual_comparison.py` сохраняет очередь, progress и привязку photo/generation, но выдача задания/вердикт и continuation завязаны на Live session. Нужно переиспользовать эти данные через общий ограниченный исполнитель, а не написать вторую очередь.
- `article_media.py::article_candidates` присваивает сторонней статье `candidate_id=web:<hash(URL)>`. При match `_record_place_comparison` передаёт выбранный ID в `ensure_poi_identity`. Это не доказывает наблюдавшийся production-дубликат, но показывает риск: **идентификатор статьи не должен становиться новой физической достопримечательностью вместо существующего OSM/Wiki/POI**. Требуется явное evidence-backed связывание reference subject с объектом.
- `_record_place_comparison` вызывает `visual_match(raw, pending['candidates'])`; `visual_match` учитывает альтернативы только среди переданных candidates. В обычном кадре один REF. Поэтому названный моделью реальный конкурент из общего shortlist, отсутствующий в текущем кадре, может не блокировать match. Воспроизвести регрессией и исправить границу проверки. Не объявлять этот статический риск новым наблюдавшимся ложным match.
- `confidence >= 0.90`, непустые observations и наличие отправленного reference не являются измеренной 90%-й точностью. Сначала нужны корректная доставка pixels, предметное сопоставление и проверка альтернатив. Не снижать качество acceptance ради доступности.

Сохранить основные точки переиспользования: `article_media.py`, `identity_references.py`, `live_visual_comparison.py`, `identity_lifecycle.py`, `identity_progress.py`, `research_runs.py`, `poi_memory.py`, имеющийся fact/evidence intake, jobs и `ai-resource-control`/`live-interaction`. Не создавать параллельную canonical POI БД, новый универсальный LLM gateway или новую систему задач.

## 3. Одна продуктовая операция, два назначения исследования

```text
Фото + доступные метаданные + запрос владельца
  → кандидаты OSM / Wikipedia / существующей памяти
  → identity_research: статьи и иллюстрации гипотез
  → фактическое сравнение SOURCE / REF моделью с image-input
  → подтверждённый физический POI
  → fact_research: существующие пригодные факты + новые порции
  → просьба «ещё»: продолжить незавершённое / расширить новые аспекты
  → выбор автора → draft → инфографика → согласованный тестовый пост
```

Это не требование полностью последовательного I/O: найденную статью можно скачать один раз, одновременно разобрать её media и сохранить текст для будущего fact extraction. Следующую порцию иллюстраций можно получать, пока сравнивается текущая. Но **публикационная проекция фактов конкретного объекта не должна зависеть от ещё не подтверждённой гипотезы**. До подтверждения допустимы candidate-scoped evidence/кэш, не уверенный рассказ «это точно X».

Не выполнять полный fact research для каждого из десятков соседних объектов. До идентификации приоритет — материалы, которые помогают различить несколько правдоподобных кандидатов. После подтверждения ресурс переключается на факты; уже прочитанный текст не теряется.

## 4. Identity research: уверенность из доказательств, не из названия страницы

### 4.1. Кандидаты

OSM/Wikipedia/GPS — источники гипотез, не доказательство, что объект на фото именно ближайший. Геометка фото задаёт место съёмки; она может быть неточной, а объект расположен в стороне. Использовать направление/точность только если они действительно доступны. Не выдумывать их и не превращать расстояние в semantic verdict.

Объединять доказанные aliases OSM/Wiki/Commons одного физического объекта; не считать их конкурирующими воротами. Одноимённые места без явного связывания не объединять. Сохранять вариант «ни один из текущих кандидатов»: при недостаточном shortlist расширить географию/тип объекта/описательный поиск разумной следующей порцией.

Не требовать от пользователя назвать достопримечательность. При отсутствии EXIF сервис сначала использует доступный разрешённый контекст и видимые признаки. Если место остаётся действительно неопределённым, допустим вопрос о городе/районе или ещё одном снимке, а не обязательная ручная идентификация. Фото не должно молча получать текущую геолокацию телефона вместо места старой съёмки.

### 4.2. Поиск статей и изображений

Для доступных гипотез использовать общий API search: работающий Google route и независимый OpenCode websearch route. Не ждать исчерпания часовой паузы Google, чтобы начать другой разрешённый маршрут. Запросы направляет модель по недостающим видам/деталям и реальным альтернативам, а не вечный повтор первого имени.

При недостаточных Wiki/Commons references получать другие статьи/галереи. Статические фото с другого ракурса могут быть достаточны для содержательного сопоставления; искать идентичный ракурс любой ценой не нужно. Но отсутствие видимого на переднем фасаде признака на фото заднего фасада само по себе не mismatch объекта.

Использовать существующий article-media reader: основные иллюстрации, подписи, раздел страницы и галерею; не только og:image/первое фото. Если обычный HTTP не даёт нужное содержимое, тихий изолированный браузер читает **конкретную найденную статью**, не поисковую выдачу. CAPTCHA/запрет доступа не обходить; идти к другому источнику.

Фото в статье о воротах может изображать парк или другие ворота. Должна сохраняться цепочка `страница → контекст/подпись → изображение → предполагаемый physical subject`. Совпадение SOURCE с картинкой не превращает заголовок обзорной статьи в имя изображённого объекта.

### 4.3. Сравнение

Мультимодальный worker получает реальные SOURCE и REF pixels, их метки и минимальный контекст. URL, alt, caption, имя файла, успешный download или запись «изображение отправлено» не заменяют доказательство корректного мультимодального вызова и связанного ответа.

Переиспользовать исправленный SOURCE/REF contact sheet либо нативные image attachments выбранного провайдера. Сохранять ориентацию и пропорции; не терять элементы при crop. Для мелких различительных деталей разрешить следующую ограниченную проверку более высокого разрешения или явно обозначенный detail-crop вместе с полным кадром. Не строить 3D-реконструкцию, CLIP-платформу или новый поисковый движок ради первого релиза.

Минимальный ответ по сравнению: logical comparison ID, фото/generation, рассмотренные reference IDs, match/uncertain/mismatch, предполагаемый физический кандидат, конкретные совпавшие/противоречащие признаки, оставшиеся альтернативы. Сохранять разные значения:
- картинка не относится к статье/объекту;
- ракурс/качество недостаточны;
- имеются предметные противоречия;
- есть достаточное визуальное подтверждение.

Не вводить обязательный кворум из двух моделей или произвольного числа источников: один качественный reference с различительными деталями может быть достаточным. Дополнительная проверка нужна по содержательной неопределённости, а не для формального увеличения числа шагов.

Mismatch одного REF не исключает весь POI. Unknown/плохой image transport не равен отрицательному семантическому ответу. Проверять альтернативы относительно общего shortlist с учётом подтверждённых aliases, а не только одного REF в кадре.

Не выбирать положительный ответ путём бесконечной смены моделей. При содержательном разногласии допустима одна ограниченная независимая проверка или новые различительные снимки; результат не решается большинством одинаковых догадок. Не заставлять Mira повторно смотреть каждую уже надёжно проверенную пару только ради того, чтобы всё происходило в текущем голосовом треде.

После принятия результата связать evidence с существующим POI через явные ссылки/модельное entity resolution и существующий registry. `web:<hash(URL)>` оставить адресом источника/гипотезы, не автоматически новой canonical identity. Если это действительно новый объект без существующего POI, создавать его через существующий intake, не автоматически по любому заголовку.

### 4.4. UI

Галочка «Визуальное сравнение» означает принятую автоматическую визуальную проверку. `owner_confirmed` сохранять отдельно и не маскировать под такую проверку.

Счётчик — уникальные reference изображения, по которым завершён валидный verdict относительно текущего фото/generation. Download, pending, повторная доставка и повторная проверка той же пары другим worker не увеличивают число уникальных просмотренных. Число фактических model attempts хранить отдельно в телеметрии. После отказа/перезапуска счётчик не обнуляется и не растёт сам.

Показывать различие между «проверяю другие изображения», «ожидаю доступный ресурс» и «пока недостаточно свидетельств». Состояние микрофона не является состоянием research job.

## 5. Fact research и повторное использование источников

После подтверждения сразу показать уже пригодную память объекта. Продолжить её ограниченными модельными порциями. OpenCode researcher и Live работают с одним semantic intake, known claim IDs и текущими interests пользователя, а не создают собственные независимые списки.

Просьба «ещё» увеличивает request revision/цель и добавляет работу: непрочитанные источники, незавершённые фрагменты, отсутствующие аспекты. Если аналогичная работа уже идёт, расширить её цель/присоединить запрос без второго идентичного job. Новая formulation поискового запроса не делает известную статью новой.

Отдельно учитывать состояния одной страницы:

| Результат обработки | Что ещё может быть нужно |
|---|---|
| URL найден | Скачать текст и/или media |
| Текст сохранён | Извлечь факты; перечислить иллюстрации из того же тела |
| Текст полностью обработан для scope | Не повторять extraction, но можно продолжить необработанную галерею |
| Media перечислены | Ещё требуется visual verdict по нужным кадрам |
| Картинка просмотрена для фото A | Для нового фото B допустимо новое сравнение, используя кэш байтов |
| Частичный текст/галерея | Продолжить с cursor, не обозначать весь источник completed |

Переиспользовать existing source/version/checkpoint storage. При недостатке полей добавить минимальные purpose-specific поля/индексы в него. Нужны отдельные ключи идемпотентности для acquisition, media enumeration, image comparison и fact extraction; глобального «URL уже был — запретить всё» недостаточно.

Один source snapshot скачивается один раз при пригодном cache/доступе; оба назначения получают одну ссылку на него. Scope/версия/доступ владельца входят в проверку reuse. Shared public corpus не должен открывать приватные фото/голос/черновики другой истории или аккаунта. Подтверждение фото A не является подтверждением нового фото B только из-за близких координат.

Каждая принятая fact-порция сохраняет точный источник/фрагмент, qualifiers времени и модальности, authorship модели и нормализованный смысл через existing intake. Модель отвечает за entailment, атомарность, эквивалентность и противоречия; механический код — за ID, schema, наличие passage, bindings и идемпотентный commit. Полная повторная экстракция каждого ответа Mira не обязательна. Ошибочный claim изолируется, хорошие не задерживаются до идеального покрытия всего объекта.

Новые пригодные факты сразу поступают в server POI memory и Android projection с `selected=false`. Не менять ранее выбранные факты, concept и draft от позднего ответа worker. Материалы проверки изображения не получают автоматически разрешение на использование чужого фото в финальной публикации; основой остаются разрешённые материалы владельца.

## 6. Модели и независимые области отказа

Не выбирать одну «самую надёжную вообще» модель на все этапы. Нужны небольшие роли и проверенные возможности каждого маршрута:

| Операция | Требуемая возможность | Начальный практический вариант |
|---|---|---|
| Формулирование поисковых запросов/работа с tools | Text + tool calling | Уже проверенная MiMo2.6 через OpenCode; GigaChat2 Lite после tool roundtrip |
| Поисковая выдача | Реальный search backend и его quota | Google API или OpenCode websearch с наблюдаемым backend |
| Чтение страницы/картинок | HTTP, допустимый тихий browser, scoped artifacts | Существующие readers Street Story |
| Визуальное сравнение | Image input + проверенная доставка SOURCE/REF + структурированный verdict | Существующий Live; независимо проверенный headless VLM резерв |
| Извлечение/нормализация фактов | Text semantic extraction + evidence contract | Live/MiMo/GigaChat Lite в одной очереди |
| Беседа/редактура | Conversation/voice | Mira; фоновая работа не обязана иметь активную голосовую сессию |

### Уже имеющиеся измерения — не повторять без причины

- MiMo `opencode/mimo-v2.6-flash-free`, task `dvt_d1ac72da029c4061b89c8aa8365b9aef`: 149.731s, 2 websearch, 4 webfetch, 2 прочитанных новых статьи, 15 кандидатов с отдельными обнаруженными ошибками. Это text/tool pilot, не проверка image-input и не production import.
- Giga `GigaChat-2`, actual `GigaChat-2:2.0.30.01`: OAuth/models/balance HTTP200 по трём существующим bindings, Lite balance250млн на каждом перед тестом; synthetic function call200, 1.241s, 255tokens. Не доказаны независимость аккаунтных квот и точный expiry. Не повторять расходный balance/inference sweep на каждом шаге.
- **GigaChat2 Lite принимает только текст.** Output image через builtins не означает image understanding. Для визуального резерва Giga2 Pro/Max имеют документированный image-input, но это другие тарифные buckets. Прежде чем назначать их, нужен реальный positive/negative pixel test выбранного adapter. Наличие моделей/баланса не доказывает quality/transport.
- История630 OpenCode tasks и 30d counts уже сохранены в прежнем prompt. Completed не равно accepted; cancelled/interrupted не считать provider outage. Пилот MiMo не устанавливает вероятность успеха99%.
- Свежий `list_models(provider=opencode, verified_only=true)` вернул предупреждение об отсутствующем verification receipt; показанные capabilities — reasoning/toolcall без достаточного image-input подтверждения. Generic filter text/tool не годится для выбора vision fallback. Сохранять raw modality capability и фактическую проверку в существующем каталоге/receipts, не угадывать по названию модели.

Минимальная цель поставки — один работающий основной и один действительно независимый проверенный резерв для search и vision, а не десятки подключённых моделей. Для Giga использовать существующий/официально рекомендуемый совместимый adapter и корректный OAuth/CA; не писать новый большой proxy. Не менять default всех соседних проектов.

OpenCode — runtime инструментов, не сам поисковик и не гарантия мультимодальности. Разные его LLM могут пользоваться одним Exa/Parallel backend. Если упал именно он, смена LLM не чинит поиск. И наоборот, отказ Google Search не означает, что текущая Live-модель не может сравнить уже сохранённые картинки.

Не делать OpenCode единственной обязательной точкой отказа: существующие прямые search/reader/vision маршруты должны оставаться используемыми. Сначала проверить контракт установленной версии OpenCode; не применять параметры v2 вслепую к другому runtime.

## 7. Оркестрация ресурсов и продолжение

Переиспользовать существующие jobs, retry timestamps, provider health и atomic admission `ai-resource-control`. Нужен тонкий выбор следующего разрешённого шага по capabilities/health/quota; не отдельный orchestration framework.

Логическая работа владеет прогрессом, а попытка модели — временный исполнитель. Сохранять logical request, stage/purpose, photo generation, canonical candidate context, source/ref versions, cursor, attempt/provider ID, доступность и следующий due time. Provider session ID не должен быть единственным носителем результата.

### 7.1. Обработка отказов

| Событие | Правильное продолжение |
|---|---|
| Короткий 429 / Retry-After | Учитывать указанную паузу на затронутом route; выполнять доступную независимую работу; не крутить tight retries |
| Дневная/пакетная quota исчерпана | Исключить затронутый quota scope до доказанного reset/контрольного probe; выбрать другой разрешённый независимый ресурс |
| Из нескольких ключей один project | Считать общей квотой там, где так устроен provider; смена ключа не создаёт бюджет |
| Timeout/5xx | Сохранить completed outputs, прекратить/ограничить старую попытку, продолжить незавершённую единицу через подходящий резерв |
| Image input не поддержан/потерян | Не считать verdict; исключить этот route из vision, не из text research |
| Истёк OAuth | Штатно обновить token; credential failure не объявлять отказом всех моделей |
| Внутренний context/setup budget | Передать меньший релевантный capsule/порцию; не пересоздавать ту же переполненную беседу по кругу |
| Search backend недоступен | Сменить search backend, а не только текстовую LLM; сохранённые статьи/картинки всё ещё пригодны |
| Live disconnect/пользователь выключил микрофон | Не терять job; выполнять разрешённое фоновое исследование и показать результат при возврате |
| Пользователь отменил именно исследование | Отменить его новые действия и не автооживлять; сохранить уже полученные пригодные результаты |
| Все разрешённые ресурсы временно исчерпаны | Durable waiting, честное состояние и bounded due-resume; не ложный match, не окончательный «объект не найден» |

Последняя строка неизбежна: невозможно гарантировать немедленную обработку, когда нет ни одного разрешённого вычислительного ресурса. Требование — отсутствие потерянной работы/окончательного отказа по временному событию. Автопродолжение выполняет продуктовый scheduler, а не обещание чат-агента в отчёте.

Не обещать точный reset, если provider его не сообщает. Отличать локальное cooldown, provider quota и локальный бюджет/политику владельца. Старый last_failure не равен текущей недоступности. Google quota считается по project, не API key; отдельно учитывать model/operation, если это определяет реальный лимит.

### 7.2. Границы расходов и параллельности

Допуск route сначала требует разрешения на расход, нужной modality/контракта и минимально приемлемого качества по этому workload. Среди допущенных выбирать по текущим quota/health, наблюдаемой успешности, скорости и стоимости. Не брать text-only или непроверенную слабую модель для vision потому, что у неё большой баланс; доступность не понижает качество acceptance.

Не ограничиваться двумя полностью serial giant tasks. Допускается ограниченный pipeline acquisition/verification/extraction, но одновременно одну source-version единицу не должны извлекать Live и OpenCode. Применять имеющиеся lease/идемпотентность; late result принимается только подходящей актуальной generation/revision.

При таймауте сетевой вызов мог продолжаться у провайдера: ограничивать совокупное число попыток, сохранять их correlation, fencing и расход. At-least-once execution с идемпотентным commit достаточно; не заявлять magical exactly-once provider execution.

Общий admission учитывает оба назначения, фоновые workers и другие потребители того же аккаунта/Google project. Лимит concurrency Giga соблюдать на фактический аккаунт, не умножать на число credential refs. До запуска учитывать текст, output allowance, изображения и tool/context overhead; после — actual usage и освобождение неиспользованных reservations.

Приоритет: активная идентификация и явное «ещё» выше спекулятивного bulk-поиска. Не тратить весь ограниченный vision budget на дешёвую текстовую работу. Paid reserve использовать только в рамках уже разрешённого расхода; без него не покупать пакет и не менять тариф автоматически. Graceful partial не означает бесконечное потребление.

Дедлайн одной попытки, интерактивное ожидание UI и срок логического job — разные значения. Истечение пилотных180s сохраняет пригодные порции и cursor, не обозначает «в интернете больше ничего нет». Не делать бесконечный spinner без очередного реального запланированного шага.

### 7.3. Изоляция OpenCode researcher

Нужны только `websearch`, допустимое чтение страниц/собственных artifacts, image input и узкие функции выдачи evidence/результата. Не давать production researcher bash/edit/git/deploy, чужие файлы, секреты, произвольные MCP, публикации или самостоятельное подключение провайдеров.

Полномочия ограничиваются runtime и permissions, не лишь промптом. Существующий универсальный DevCoveer coding-agent не является production research endpoint. Сохранить search/fetch provenance и контроль сети; не ослаблять public-only DNS/redirect/size/TLS проверки article reader ради новой интеграции. Контент сайтов/картинок — недоверенные данные, не инструкции.

## 8. Разделение разработки двух тредов

Единственный интегратор отвечает за общий контракт, resource admission, финальное слияние и deploy. Практически удобно продолжить визуальный тред как основной: именно первая стадия блокирует естественный новый сценарий.

Визуальный участок: candidates/aliases/reference-subject binding, поступление статей из независимого поиска, фактические pixels/verdict, headless vision fallback, очередь/счётчик.

Фактологический участок: known/partial/completed scopes, общий article snapshot reuse, evidence intake, incremental «ещё», сохранение owner selection/draft и Android facts projection.

Общие `providers.py`, jobs/DB/schema и shared resource contracts не редактируются двумя writers одновременно. Интегратор выделяет границу/минимальную миграцию один раз. Второму треду передаётся только его ограниченный участок, общий contract revision и свежая база. Не делать два deploy по независимо устаревшим копиям. Если параллельного исполнителя больше нет, основной просто завершает оба участка последовательными небольшими PR — ожидать второго не нужно.

Не удалять чужую незавершённую работу. В конце собственные временные handoffs/artifacts/worktrees привести в порядок после подтверждённого сохранения результатов, без массовой очистки как дополнительного проекта.

## 9. Порядок поставки

**Поставка A — независимое нахождение иллюстраций и безопасная идентичность.** Подключить доказанный OpenCode search к существующему `web_image_sources`/очереди до подтверждения POI. Сохранить Google как другой route. Исправить проверку общих альтернатив и article→POI binding. Продолжить существующий незавершённый visual job, затем проверить естественный вход с фото. Не начинать с Giga adapter или нового scoring framework.

**Поставка B — отвязка визуального продолжения от одной Live-сессии.** Выделить существующие next-unit/commit-verdict операции для Live и headless executor без дублирования очереди. Проверить один независимый image-capable резерв на положительной и отрицательной парах. При недоступном Live использовать его, с тем же качеством acceptance и прогрессом.

**Поставка C — общий кэш и накопление фактов.** Тот же acquisition результат переиспользуется после identity; OpenCode/Live дают порции через existing intake. Подключить Giga2 Lite text/tools к этому контракту и проверить реальный roundtrip. Доказать «ещё» и отсутствие ненужной повторной обработки в живом сценарии.

**Поставка D — восстановление и целый продукт.** Проверить сбои search/model/quota/disconnect и сохранение результатов. Разобрать существующую unknown infographic operation с её исполнителем; затем review изображения/текста и retained test Telegram publication/native readback. Не подменять D1–D12 зелёной сборкой.

## 10. Приёмка D1–D12

| ID | Проверяемое требование |
|---|---|
| D1 | Работа начинается от текущего релиза с обоими уже слитыми участками; старые fixes и данные не потеряны. Один release owner, нет конкурирующих deploy. |
| D2 | В natural Android flow дано фото владельца и доступные реальные метаданные, но не правильное имя/seed URL. При недостаточных Wiki видах сервис сам находит новую статью через независимый search route и получает её фактические основные media. |
| D3 | Actual SOURCE/REF transport проходит негативный контроль: парк/похожее другое сооружение/отсутствующий attachment не дают match. Поздний полезный кадр галереи достигает модели; счётчик растёт только по завершённым уникальным verdict. |
| D4 | Настоящая альтернативная identity вне текущего REF-batch не теряется. Aliases одного объекта не создают ложное разногласие. Web article ID не создаёт второй canonical POI при доказанной связи с существующим. |
| D5 | На реальном контрольном Закхаймском фото получено автоматическое подтверждение с reference provenance и отображением в Android. Не подменять его owner_confirmed/понижением порога/названием статьи. Отдельно отработаны genuine ambiguous/none-of-shortlist случаи без принудительного положительного ответа. |
| D6 | Основной vision route недоступен — проверенный независимый image-capable резерв продолжает ту же единицу. Text-only route не получает visual assignment. Actual image test, не только model catalog. |
| D7 | Search429/backend outage/model quota exhaustion классифицированы отдельно; healthy разрешённый резерв используется без повторения всех завершённых шагов и без обхода общей квоты. Все routes blocked → сохранён waiting/due state, затем автоматическое продолжение после восстановления. |
| D8 | Disconnect, process restart, duplicate result, смена фото/POI, Stop research и late result безопасны: прогресс не теряется, нет stale commit/двойных новых facts/самовольного возобновления отменённой работы. |
| D9 | Один источник реально используется двумя назначениями без лишнего fetch/extraction: complete text не блокирует unread gallery; уже просмотренное для фото A допускает проверку для фото B с reuse media bytes. Partial остаётся partial. |
| D10 | После confirmation видны ранее пригодные facts; реальное «ещё» приносит полезные новые/уточнённые facts в POI И Android, а не только речь/лог. Completed unchanged источники не обрабатываются заново; owner selection и draft сохранены. |
| D11 | Для принятого identity и fact batch есть actual provider/model, transport/backend, source/ref/cursor, время, input/output/cache/image usage и расход либо explicit unknown. Сырые candidates, accepted facts, duplicates и conflicts посчитаны раздельно. |
| D12 | После authoritative reconciliation старой infographic operation получен проверенный no-crop visual, согласованный текст и retained post в разрешённой test Telegram-группе с native readback. Реальная естественная сквозная приёмка + подписанный обновляемый APK, не только компонентные тесты/CI. |

Focused regressions включают фактические дефекты пилотов: source/quote mismatch дат, неверную модальность planned/done, отвязанный image attachment, park false positive, alias duplicate и alternative вне текущего batch. Не заменять semantic tests правилом на конкретную дату/название ворот.

Инъекции отказов в тестах разрешены и явно помечаются; успешный вызов резерва должен быть реальным. Не выдавать injected429 за фактический provider outage и seeded fixture за natural discovery. Для живого теста достаточно ограниченного проверяемого набора, не нового большого benchmark. Маленький набор не доказывает99%-ю accuracy; отделять долю ложных подтверждений, долю неопределённых ответов и покрытие.
