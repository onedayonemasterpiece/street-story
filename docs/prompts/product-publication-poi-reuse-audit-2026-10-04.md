## 3. Кодовые причины на e68f262

### F1. Live-first не использует память источников для исключения повторов

`providers.py::search_web()`, около 3034–3077: ветка `topic_context['live_first']` рано вызывает `_public_web_search(query)` и возвращает discovery. Память из topic context не становится здесь параметрами исключения/покрытия. Cached sources в fallback не равны нормальному планированию с учётом прошлого.

`providers.py::_public_web_search()`, около 1044–1143: `excluded_urls` преобразуется в `_processed`, но не используется для фильтрации. Комментарий объясняет это возможной новой целью исследования. Вместе с неправильным вечным blacklist отсутствует и правильное условное исключение завершённой работы.

### F2. Версия текста сохранена, но semantic processing начинается заново

`research_runs.py`, около 200–325: версия определяется по URL/содержимому, но новый run создаёт новые `research_chunk_runs` в состоянии planned. `saved_run_document()` и checkpoints привязаны к текущему `run_id`. Завершение для того же POI/версии/объёма в прошлом run не становится достаточной причиной пропустить повторное извлечение.

### F3. Память разделена по candidate IDs

`poi_memory.py`: `poi_key()` возвращает candidate ID; `_read_facts()` и `processed_sources()` читают конкретный ключ. Registry/aliases не объединяют автоматически Wikipedia и Commons. Разный способ распознавания одного места даёт другой раздел памяти.

### F4. Hydration не обновляет непустую story

`poi_memory.py::hydrate_story_facts()`, около 317–393: наличие хотя бы одной записи `facts` приводит к `return 0`. Уже непустая история не получает этим способом новые общие факты. Наличие hook после identity ещё не доказывает требование «используем всё накопленное».

Ограничение model-facing порции допустимо, молчаливый предел доступных пользователю знаний — нет. `processed_sources()`, около 435–457, содержит ссылки, но не достаточное описание завершённости извлечения; встреченный URL нельзя автоматически считать обработанным.

## 5. Ретроспектива Live: сохранить удачное

Прочитать существующий `docs/retrospectives/facts-live-first-retrospective-2026-10-04.md` и релевантные receipts, не запускать новый общий аудит.

| Наблюдение | Что сохранить / не повторить |
|---|---|
| Live давала 16 и 17 partial findings, выбранные подмножества давали draft за секунды | Не заменять Live-first обязательным paid helper/global reviewer |
| Большие tool envelopes блокировались внутренним admission до провайдера | Различать resource wait и provider latency; не объявлять это outage модели |
| Малые страницы, короткие refs, перечисление тезисов и собственные passages улучшали результат | Сохранить простые небольшие semantic operations, не загружать весь corpus в prompt |
| HTML-меню обрабатывались как статьи | Непригодная выгрузка не означает отсутствие фактов в статье |
| Read/save имели разные границы evidence | Одни адресуемые passages, контекст на границе, сохранение модальности и времени |
| Глобальная review-лестница удерживала хорошие факты | Сомнительный кандидат изолировать, пригодный набор оставить доступным |
| Свободная речь после search не сохраняла facts; новые gates создавали deadlocks | Реплика, tool response и завершение исследования — разные события; один save не разрешает любые unsaved claims |
| Echo вызывал interruptions/backpressure; другой AEC/NS подавлял сигнал | Не менять аудиоконфигурацию вслепую, сохранить guards и освобождение research focus |
| Canary менял память и требовал ещё novelty на том же POI | Стабильные изолированные регрессии вместо бесконечного прироста одной owner story |

Официальная Live API документация требует корректного возврата FunctionResponse с call ID/name. Синхронное/асинхронное behavior зависит от модели; не переносить NON_BLOCKING/scheduling без проверки фактических модели и SDK.

Compression, resumption и GoAway относятся к жизни model connection, не заменяют POI-memory и durable cursor приложения. Отсутствие параметра в Street Story не доказывает его отсутствие в shared framework. При возобновлении передавать цель, подтверждённый объект, короткий индекс claims и точный незавершённый шаг, не весь архив.

- https://ai.google.dev/gemini-api/docs/live-api/session-management

## 6. Исполнительное продолжение для того же агента

### P0. Получить реальный тестовый пост из уже доступной ценности

1. Сверить текущие checkpoint/HEAD. Если работа уже дальше среза аудита, продолжать от первого её фактического blocker. Не повторять PR140–144.
2. Если актуален identity failure выше, разобрать именно эту story: фото/координаты → candidates → доставленные reference images → решение → match/uncertain → продолжение. Исправить минимальный разрыв без обязательного знания названия автором и без обхода visual verification.
3. При полезном пригодном наборе идти selection → concept → draft → visual → test publication, не ждать полной исторической базы. «Два» и «семь» — наблюдавшиеся числа, не потолок. 70% — ориентация на полезное неполное покрытие, не разрешение ложных фактов и не измеренный recall без эталона.
4. Для отладки следующих стадий продолжать сохранённую story штатным клиентским путём, не обнулять всё при каждом повторе. Затем один свежий полный проход с обычными репликами без имён tools.
5. Сгенерировать infographic из выбранных facts/концепции; проверить глазами объект, crop и границы текста. Через приложение/Миру со штатным подтверждением опубликовать в тестовый `street_story_e2e_20260928_tg`, `keep_publication=true`; выполнить native readback. Ручная отправка картинки другим инструментом не заменяет маршрут.

Один непубликуемый сомнительный кандидат не блокирует пост с остальными. Успешный пост не закрывает автоматически дефекты накопления P1.

### P1. Исправить подтверждённые дефекты существующей памяти

**Общая память:** подтверждённые aliases одного POI читают общий набор существующих таблиц. Связь Wikipedia/Commons Закхаймских проверить координатами/референсами или existing identity contract, не похожим названием. Hydration сделать добавочной/idempotent: новое общее знание видно непустой story; owner selection и draft не сбрасываются и не копируются из чужой story. Пользователю доступен весь пригодный набор с пагинацией, модель получает малые порции.

**Переиспользование извлечения:** использовать существующие versions/checkpoints. Различать URL/snippet, fetched text, частичное и завершённое извлечение. Завершённое для того же POI/версии/объёма не повторять; partial продолжать с cursor. Изменение текста или новый вопрос вне покрытия допускают ограниченное доисследование с причиной. Fetch failure/меню не считать «в статье нет фактов».

Это условное исключение завершённой работы, не вечный blacklist URL/домена. Проверять disputed claim по музею можно; повторять все его обработанные chunks без причины нельзя. Учитывать final URL/redirect и версию без агрессивного объединения разных страниц. В Live-first память должна фактически влиять на поиск и очередь extraction, не только упоминаться в prompt.

**Честный прирост:** различать new eligible claims, evidence к existing claim, reused facts, withheld/insufficient, skipped completed chunks и resumed chunks. Observation к старому тезису не объявлять новым фактом. Для богатого объекта цель — разнообразный полезный набор; любой единственный save не является достаточным основанием автоматически завершить нормальное исследование.

Минимальные проверки:
- Подтверждённые aliases дают общую память без cross-POI утечки.
- Непустая story получает новое пригодное общее знание без изменения выбора автора.
- Повторный run на неизменённом завершённом источнике не делает повторное semantic extraction.
- Partial продолжается с checkpoint; snippet-only источник не исключается как полностью обработанный.
- Один bounded реальный запрос «ещё» использует непройденный источник/пробел либо честно сообщает отсутствие новых подтверждений и сохраняет доступ к публикации.

Не запускать ещё пятнадцать novelty-canaries на изменяемой owner story. Изолированные tests не загрязняют production; реальная проверка — штатными операциями, не SQL-вставкой готовых фактов. Отсутствие новых facts после повторного чтения старого не доказывает, что новое знание найти невозможно.

### P2. Использовать имеющуюся телеметрию для первого разрыва

Связать story/session/run/tool-call, шаг/длительность, resource wait, model-visible refs/размер/output, source-version/chunk, reuse/skip/retry reason, save result и UI projection до/после. Если данные уже есть — собрать профиль, не строить новую observability platform.

Polling HTTP200 не является анализом прогресса. Для спорного факта смотреть именно показанный модели контекст, не только длинную статью. Полные безопасные payload доступны по refs; ключевые passages не обрезать в анализе. Секреты и скрытые рассуждения модели не логировать. Watchdog PR144 проверить, не реализовывать повторно. Без новых данных или изменения причины повтор того же прогона не является новой проверкой гипотезы.

## 7. Приёмка

Сначала видимый тестовый пост из пригодных фактов. Затем узкие регрессии P1 и ограниченная проверка накопления, без нового перфекционистского аудита.

Отдельно отчитаться:
- **Сквозной результат:** фото, автоматическое match, пригодные facts, выбор, concept, draft, asset, Telegram post/item ref, native readback, screenshots и длительности.
- **Накопление:** aliases, добавочная hydration, reuse завершённых chunks, resume partial; новое знание отдельно от evidence и дублей.

Не менять auth/device token, requirements, provider budget без измерения, чужие сервисы/destinations. Не вводить обязательный helper/global reviewer, второй canonical POI layer, общий перенос таблиц или новую ontology. Не ослаблять доказательность ради зелёного canary. Сохранить полезные решения, данные и текущую работу агента.
