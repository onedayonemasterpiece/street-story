## 2. Новые выводы: куда сейчас направить работу

### R1. RESOURCE_TOKEN_BUDGET — отказ допуска нашего resource control, не установленный сбой Gemini

В журнале есть несколько разных исходов: первоначальный targeted запросил 35 418 единиц, получил 54 ожидания и не сохранил фактов; последующий targeted сохранил три самостоятельных утверждения, но не завершил review, запросив 40 119 единиц. Поздняя broad-проверка даже после уменьшения ответа до **6 673 единиц** осталась без завершения: 7 unreviewed claims, 2 сохранённых batch, обработан 1 из 2 chunks. Это сведения из предоставленного журнала, не новый online-прогон аудита.

Причину нельзя свести к «провайдер снова недоступен». Прочитанный установленный `ai_resource_control.client.Lease.before_send` сначала запрашивает grant у общего контроллера. `Control.rpc` преобразует его отрицательный ответ `reason=token_budget` в `RESOURCE_TOKEN_BUDGET`. Это происходит **до ws.send в Gemini**.

Для обычного текстового/JSON payload установленный `estimate_input_tokens` использует длину компактной сериализации UTF-8 в байтах. Это консервативные единицы допуска, **не измеренные токены провайдера и не биллинг**. В частности, уменьшение количества символов не является полной проверкой размера JSON envelope. Сам по себе консервативный estimator не доказан ошибочным.

Прочитанная repository-версия `ai_resource_grant_v1` сопоставляет запрос с суммой ещё действующих grants всех leases одного quota_scope/quota_group и локальным minute_token_limit. Но **живые значения политики, занятости и установленная SQL-версия этим аудитом не прочитаны**. Не утверждать, что известна точная ёмкость или причина её исчерпания. Требуется различить пакет больше полной ёмкости, временно занятое окно, удержанные резервы, ошибку учёта и несовместимость установленного пакета/политики.

[Shared transport](https://github.com/onedayonemasterpiece/live-interaction/blob/4d16dc10ede1d7a649ca88049b0f558c32fe8f92/python/live_interaction/provider.py#L106-L153) **уже умеет ждать grant до 95 секунд для одного неотправленного tool result**, не повторяя выполнение инструмента. Добавлять ещё один retry loop поверх него не нужно. Сжатие контекста модели не освобождает автоматически окно центрального допуска.

В прочитанном installation нет отдельного live_budget.py: релевантная реализация находится в client.py. Перед исправлением найти фактически импортируемый пакет через его metadata/path; не подменять установленную версию соседним checkout. Private SDK не копировать в публичный Street Story.

**Практический вывод:** следующий online-запуск должен проверять измеренное исправление budget path, а не ещё одну попытку «может, теперь пройдёт». Локальный отказ допуска не обосновывает замену API-ключа, повышение квот, изменение provider или отключение guard.

### R2. Final review заставляет голосовую модель выполнять избыточное копирование служебных идентификаторов

[finalize_fact_review](https://github.com/onedayonemasterpiece/street-story/blob/e4836918324a66a38432b555a1af19360d7790b5/backend/street_story/live.py#L3281-L3465) требует fact_id, revision_digest и supporting_evidence_ids для каждого элемента. Полученный bundle должен в точности совпасть со **всем evidence-backed inventory истории**, не только с текущей порцией. При несовпадении требуется повторное чтение. В журнале уже есть выдуманный digest, корректно отвергнутый сервером, и дополнительные циклы чтения/сохранения.

Защита ревизий нужна; заставлять модель многократно переносить длинные хеши — не единственный способ её получить. Перенести механическую адресацию на сервер, сохранив семантические решения модели: замороженный review packet с короткими локальными ссылками на утверждения и evidence; сервер хранит соответствие точным версиям.

Есть и строгая граница: вход ограничен 240 reviewed_assertions, а current_bundle содержит все evidence-backed facts. При 241 таком факте условия уже несовместимы. Это вывод из кода, **не причина, доказанная для текущего теста с тремя фигурами**. Проверить отрицательным структурным тестом, но не превращать исправление в большой графовый движок вместо маленького работающего сценария.

Числовые passage_ids для extraction уже реализованы. Использовать тот же принцип для review. Само чтение packet не является успешным review: модель должна явно вернуть решения о поддержке тезиса, эквивалентности и расхождениях. Нельзя заменить это одним флагом «всё eligible».

### R3. Приёмочный тест смешивает причины ошибок и может ложно принять неверные факты

[Текущий harness](https://github.com/onedayonemasterpiece/street-story/blob/e4836918324a66a38432b555a1af19360d7790b5/backend/tools/facts_research_acceptance.py#L61-L125): любой event type=error становится BLOCKED_PROVIDER, любое исключение bootstrap тоже. RESOURCE_TOKEN_BUDGET записывается в ту же категорию. Это не позволяет отделить внешний 429/503 от локального admission, ошибки контракта, истечения lease и дефекта приложения.

Gold evaluator ищет подстроки имён в eligible facts, требует три различных ID и лишь непустое evidence где-либо в ответе. В изолированной локальной проверке исполнен **тот же предикат** с синтетическими заведомо неподходящими кандидатами:

| Текст синтетического кандидата | Почему не подтверждает целевой факт |
|---|---|
| «Оттокар II не изображён на фасаде.» | Отрицание требуемого тезиса |
| «На фасаде изображён Фридрих III.» | Другой номер правителя; «Фридрих I» совпадает как подстрока |
| «Реставратор Альбрехт работал с камнем.» | Другая роль, не изображённая фигура |

При трёх разных ID, state=completed и единственном evidence для **постороннего** fact_id получено `gold_ok=true`, `status=PASS`. Это доказательство слабости evaluator, **не результат реальной модели и не утверждение об истории ворот**. Новая проверка не запускала весь harness, production или paid provider.

Также evaluator просит limit=100 у get_facts, который [ограничивает страницу 50](https://github.com/onedayonemasterpiece/street-story/blob/e4836918324a66a38432b555a1af19360d7790b5/backend/street_story/live.py#L1428-L1481), и не следует cursor. Evidence читается для первых 20 IDs, тоже одной страницей. Это не полный audit inventory.

Наконец, harness дописывает к обычному запросу длинную инструкцию: какой tool и в каком порядке вызывать, какие поля заполнять, как закончить review. Это допустимая **guided integration проверка**, но не доказательство обычного пользовательского сценария. Retrieval, identity и helper outage здесь контролируются фикстурами; сам отчёт это уже признаёт. Не выдавать такой прогон за проверку поиска в интернете или физического микрофона.

### R4. Зелёные тесты частично проверяли не тот слой

В журнале зафиксировано, что уменьшение ответа сначала не действовало: get_research_chunk выходил через early return до общей projection. [Теперь маршрут исправлен](https://github.com/onedayonemasterpiece/street-story/blob/e4836918324a66a38432b555a1af19360d7790b5/backend/street_story/live.py#L1006-L1033). Повторять этот patch не нужно. Но проверять только helper _model_result недостаточно: нужен тест через фактический execute_tool, окончательный functionResponses envelope, estimator и guard с управляемым окном grants.

Три неверных batch или три discovery без save теперь дают partial. Это полезный ограничитель ущерба, но не улучшение полноты само по себе. Partial должен давать понятное продолжение сохранённой операции, а не вынуждать автора снова запускать исследование с нуля.

## 3. Задание текущему Codex: выполнить узкую доработку до проверяемого результата

### Границы

Продолжи существующий worktree и PR #126 либо его уже слитое продолжение. Не создавай новый worktree и конкурирующего писателя. Сверь только новые изменения после e483691; актуальные AGENTS и защищённые продуктовые требования сохраняются. В этом исполнительном окне Codex вносит и проверяет исходные изменения сам; не возвращай задачу на ещё одно окно для пересочинения patch. Не менять auth, публикационные разрешения, LLM-first семантику или пользовательские данные.

Нужен один исправленный маршрут: **обычный запрос автора → доступное evidence → сохранённые атомарные facts → модельный review → выбираемые пригодные факты**. Не расширять задачу до нового RAG, миграции инфраструктуры, UI-редизайна или проверки всех соцсетей. Не отменять текущую доставку полезных исправлений, но не объявлять факты готовыми по одному CI.

### Шаг 1. Разобрать один сохранённый отказ до нового платного прогона

Возьми поздний сохранённый receipt с запросом 6 673 единиц или более свежий эквивалент. Сохрани исходный receipt неизменным. Построй короткую таблицу событий: tool call → durable save/read → projected reply → request grant → denial/wait → provider send или его отсутствие → terminal state. Определи, что именно уже сохранилось и что модель ещё не получила.

Read-only сверить установленную версию SDK и действующий контракт authority. Для отказавшего окна собрать только не секретные данные: policy revision/ёмкость, занятое allowance, оценку полного пакета, carry, grant deadline/sequence, время возможного следующего допуска, агрегированное влияние других leases. Не выгружать ключи, env, сырые токены владельца или чужие разговоры. Когда историческое состояние восстановить нельзя, явно это указать и добавить ограниченную диагностику для следующего единственного прогона.

Отдельно классифицировать:
- внешний provider 429/503;
- локальную/центральную resource admission policy;
- ошибку или недоступность authority;
- contract/semantic failure и timeout теста.

Наличие одного временного denied, после которого пришёл granted и сценарий завершился, не делает весь прогон заблокированным. Не подменять первую причинную ошибку последующим host.stop.

### Шаг 2. Исправить измеренный budget path без обхода ограничений

Воспроизведи найденную границу offline на fake clock/authority с реальным serializer/estimator и production tool route. Проверить различие: пакет больше полной ёмкости; ёмкость временно занята; окно пополнилось; lease истёк; ответ уже сохранён, но ещё не отправлен. Повторять 180-секундный платный broad ради этих механических случаев не требуется.

Сделай выдачу документов/evidence/review packet ограниченной по **фактической оценке окончательного JSON envelope**, а не только по числу строк или facts. Кириллица, метаданные, идентификаторы и обёртка учитываются. Не отрезать готовую JSON-строку. Пагинация сохраняет coverage всех core spans и соседний контекст; незагруженный хвост не помечается обработанным. Не разрезать один function response на произвольные транспортные куски: разделять на корректные доменные страницы/пакеты.

Уменьшение сообщения не решает полностью занятое окно: используй уже существующий bounded wait/checkpoint и учитывай допустимое окно для следующего шага. Перед началом большой порции учитывать стоимость save/review, чтобы не тратить весь доступный бюджет только на чтение. Не обещать мгновенное завершение сверх реальной квоты.

При отказе сохраняются данные и состояние ожидания; не повторяются поиск, extraction и side effects. Если текущую Live-сессию продолжить безопасно нельзя, новая сессия восстанавливает **тот же research run** и адресный следующий шаг, не перечитывая всё по памяти восьми реплик. Не добавлять key hopping внутри разговора, guard bypass, искусственную смену quota scope или очистку ledger.

Если численная политика действительно несовместима с подтверждённой provider entitlement, подготовить измеренное изменение через существующий механизм и разрешение владельца. Не увеличивать лимит или делить estimator на четыре наугад. Отдельную private SDK-починку выполнять в её репозитории; в Street Story только совместимая зависимость. SHA соседних сервисов не обязаны совпадать.

### Шаг 3. Упростить review-контракт, оставив смысл модели и проверки серверу

Минимально расширь существующий read/review путь: замороженный packet с коротким packet reference и локальными номерами фактов/evidence. Сервер хранит связь с точными assertion/evidence revisions, story/owner/run/identity generation. Модель получает текст тезиса и относящиеся к нему passages и возвращает явный семантический вердикт по локальным refs. Внешний длинный digest не нужен в каждой модельной строке; внутренняя проверка версий остаётся обязательной.

Сохранённое решение не означает автоматическую истинность. Нужны положительная поддержка, отрицание/неподдержанность, различие ролей, equivalence и конфликты. Пустой набор конфликтов допустим после указанного полного review. Устаревший/чужой packet отклоняется; replay идемпотентен. Неразрешённый конфликт, quarantine и неподтверждённое evidence по-прежнему удерживают факт.

Не заставляй заново возвращать весь inventory после каждого batch. Переиспользуй валидные решения для неизменённых ревизий, отдельно проверяй новые отношения между порциями. Несколько независимых пакетов не означают автоматически полную cross-packet contradiction coverage. Для малого текущего corpus достаточно одного доступного по бюджету пакета либо нескольких явно сверенных порций; большой граф и новую БД не строить.

Добавь проверку границы >240 без искусственного удаления facts или повышения числа ради зелёного теста. Нужна завершаемая обработка порциями или ясная ограниченная операция с continuation, но исправление масштабирования не должно задерживать первый рабочий сценарий из трёх фигур.

### Шаг 4. Сделать acceptance честным и полезным для диагностики

Оставь один существующий harness. Исправь классификатор по причине и слою, добавь статусы локального resource block отдельно от provider block, а также FAIL_CONTRACT/FAIL_SEMANTIC. Итог может быть FAIL с несколькими сопутствующими причинами; не превращать все исключения в «внешний блокер».

Обойти все страницы facts/evidence. Для каждого gold assertion проверить конкретную связь subject–predicate–value/role и его собственное подтверждение. Глобальный непустой массив evidence недостаточен. Автоматические совпадения строк допустимы как подсказки оценщику, не как доказательство истины. Приведённый отрицательный контрпример обязан перестать давать PASS. Содержательную оценку выполнять по вручную проверенному gold/corpus и отдельному review фактических результатов; не переносить evaluator-эвристики в production extraction.

Разделить три результата: controlled transport/contract test; реальная модель на frozen corpus; реальное retrieval + обычный пользовательский запрос. Guided prompt оставить как отдельный diagnostic режим. Приёмка обычного сценария должна работать без дописанных harness-инструкций о названиях tools, пустых source_refs и копировании digest. Ожидаемые имена в broad input не передаются.

Сначала один малый targeted run после изменения измеренной причины, затем broad/holdout. Сохранять конкретные model/dependency/source/policy revisions и terminal evidence для каждого запуска. После одинакового воспроизводимого отказа без изменившегося условия не повторять платные прогоны. Успех extraction с тремя unreviewed facts — прогресс, но ещё не успешный результат.

## 4. Условия завершения этой итерации

| Gate | Доказательство |
|---|---|
| U1: причина определена | Для конкретного отказа понятны слой, стадия, единицы, применённая политика и состояние окна либо честно указан недоступный исторический параметр; это не catch-all BLOCKED_PROVIDER. |
| U2: реальный путь проверен | execute_tool → projection → envelope → estimator/guard проверен offline для deny/refill/oversize/replay. Нет потери payload, повторного поиска и скрытого усечения coverage. |
| U3: review исполним | Модель успешно завершает проверку по доступным коротким refs; точные серверные версии защищены; отрицательные/устаревшие/чужие решения не дают eligibility. |
| U4: PASS достоверен | Негативный пример выше отвергается; evidence привязано к каждому факту; страницы не пропущены; обычный targeted даёт 3 самостоятельных gold facts с завершённым review, broad/holdout оценены отдельно. |
