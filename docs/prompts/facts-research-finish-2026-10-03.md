### A4. Новый дефект correctness: допуск зависит от последнего обработанного конфликта

См. [fact_ledger.py:715–764](https://github.com/onedayonemasterpiece/street-story/blob/96b934820837cc283f62190bf6f0070f3738d311/backend/street_story/fact_ledger.py#L715-L764), `refresh_review_status`.

Функция сначала применяет последний scan всей истории ко всем assertions, затем по очереди выставляет eligibility для каждой пары конфликтов. Это не агрегирует все препятствия к использованию одного факта. Поздняя пара с prefer_left может отменить withheld, установленный другой неразрешённой парой. Этот же цикл может снять quarantine. Scan выбирается только по `status,coverage_complete`, без проверки членства и версий конкретных assertions.

В свежем аудите исполнена точная транскрипция этой функции с SQLite `:memory:`; только legacy backfill и downstream POI sync заменены no-op. **Это изолированные контрпримеры, не телефонная E2E и не изменение production-БД.**

| Проверка | Ожидание | Наблюдение |
|---|---|---|
| A–B unresolved, затем A–C prefer A | A withheld | A eligible |
| Те же решения, обратный порядок обхода | Тот же результат | A withheld |
| A quarantined, затем A–B prefer A | Quarantine остаётся | A eligible |
| Новый B добавлен после старого complete scan | B unreviewed | B eligible |

Следовательно, нужно не ослаблять gate ради релиза, а корректно применять **все** актуальные модельные решения к их точным версиям. Версионная история арбитража уже добавлена — её не переписывать с нуля.

## B. Исполнительный промпт

### Цель и границы

Продолжи уже реализованный Street Story. Доведи исследование фактов до проверяемой поставки с использованием актуальной разработки, а не начинай ещё один аудит или новую архитектуру.

**Обязательный результат:** после одного запроса автора Мира исследует подтверждённый объект, читает необходимые источники, сохраняет атомарные факты с адресными доказательствами, устраняет дубли, фиксирует/арбитрирует расхождения и возвращает факты, которые можно выбрать и использовать в черновике. При временном сбое сохраняются реальные результаты и понятный resumable partial. Нельзя выдавать «готово», когда только вызван поиск или сохранены непроверенные кандидаты.

Исходники и документацию проектирует и пишет ChatGPT. GitHub/Direct Ops использовать для чтения, точных патчей, тестов, сборки и поставки. OpenCode — вспомогательное read-only review/операции, не самостоятельное сочинение реализации. Не изменять `CORE-LLM-FIRST-SEMANTICS` и прочие защищённые требования. Семантика фактов, equivalence, entailment и арбитраж остаётся у Миры/настроенной модели; код исполняет и проверяет ссылки, версии, состояние и ограничения.

Live Мира остаётся единственным собеседником автора. Существующая текстовая модель может помогать; её недоступность не должна делать Live fallback фиктивным. Не вводить новую независимую исследовательскую беседу, новый микросервис, вторую POI-БД, другого платного провайдера или отдельную инфраструктуру. Не перетаскивать сюда весь RAG/Projects Hub, редизайн UI, медиабанк и тестирование всех каналов.

### B1. Начать с короткой сверки и одного воспроизводимого разрыва

Разреши реальный workspace, deployed SHA и текущий HEAD. Прочитай незавершённую правку `_save_research_facts`; не затри соседнюю работу. Сделай короткую дельту после baseline этого файла. Старые snapshot читать только для проверки конкретного вывода, не для отката.

Проверь свободный диск до build/deploy. Операционную проблему решай узко, с before/after и сохранением пользовательских данных/rollback. Затем зафиксируй один тест полного fallback, где вспомогательные research-модели недоступны, но Live работает. Этот тест должен сначала показать текущий разрыв после save. Не запускай новый большой online research после каждого косметического изменения.

### B2. Замкнуть Live fallback до конечного результата

Используй существующие research_runs/source_versions/chunks/fact ledger. Расширь существующий tool-контракт минимально, но обеспечь весь путь:

```text
авторская цель / один run
  → discovery и перечень недостающих аспектов
  → получение очередной версии документа / чанка
  → модельные findings по этому batch
  → durable save + подтверждение принятого batch
  → модельный review точного revision bundle
  → coverage / conflict outcome / eligibility
  → completed или честный partial с продолжением того же run
```

Мира должна получать через инструмент ещё не разобранное evidence по run/source/chunk, а не только spans уже существующего факта. Переиспользуй `_fetch_page_documents`, планировщик чанков и текущую URL/SSRF-защиту. Сохраняй подходящий контекст границ и способ дочитать соседний фрагмент. Это не разрешение читать произвольные внутренние URL.

Вызов сохранения должен содержать явные run_id, batch_id и ожидаемую версию, а не угадывать цель по `history[-1]`. Не отказываться от безопасных старых клиентов: старый вызов разрешён только при однозначной текущей операции, иначе понятная ошибка с актуальным run, без записи в чужой batch.

Дай модели контракт review/finalization по конкретному набору assertion/evidence revisions. Он должен уметь выразить **проверенный нулевой набор конфликтов**, подтверждения по конкретным passages, equivalence/различия и незакрытые аспекты. Нельзя сделать инструмент «присвой всем eligible=true». Сервер проверяет границы, полноту ссылок, актуальность и применение решения, но не подменяет смысл регулярками.

В случае недоступного text detector review реально выполняет доступная Мира через этот контракт. Не делегируй ей извлечение, чтобы потом опять без альтернативы потребовать тот же недоступный text detector. Если недоступны и Live, и вспомогательная модель — сохраняется resumable partial с причиной и доступным действием пользователя; обход eligibility запрещён.

`completed` должен соответствовать завершённому review заявленного набора и отсутствию необработанных обязательных частей. Проверенные спорные факты могут оставаться withheld: завершение исследования не требует объявить все утверждения истинными. Отдельно укажи coverage outcome. Любой оставшийся unreviewed обязательный этап виден и не превращается в «полностью готово».

### B3. Исправить применение review, не ослабляя его

Успешный scan/review принадлежит точному набору утверждений и evidence revisions. Новый факт или новое существенное evidence не наследует успех последнего scan всей истории. Существующие неизменённые проверки можно переиспользовать; не заставляй их повторяться без причины.

Eligibility вычисляется по всем актуальным препятствиям: quarantine, неподтверждённое evidence, отсутствующее review, stale decision и unresolved/losing conflicts. Предпочтение факта в одной паре не отменяет другое действующее препятствие. Результат не зависит от порядка чтения conflict rows. Это механическое применение модельных решений, не новая эвристика истины.

Проверь актуальность identity generation/run state непосредственно в транзакции сохранения **после последнего await**, в том числе после conflict analysis. Закрытие/отмена/смена POI не допускают позднюю запись. Существующие revision bundles для draft/visual сохранить.

### B4. Сделать checkpoint фактическим, а не только счётчиком

Перед следующим provider await сохраняй валидированный payload принятого batch или его адресуемые observations, а не только accepted_fact_count. Первая успешная часть остаётся доступной после timeout во второй. Batch receipt должен подтверждать сохранённый результат.

Resume использует тот же run, версии документа, batch IDs и cursor. Завершённое не извлекается заново; duplicate delivery не удваивает findings. У статуса chunk должен быть проверяемый сохранённый результат либо явно подтверждённый no_claims. Нельзя считать chunk обработанным только по старому счётчику, если payload потерян.

Существующие 8/10/12 секунд — ограничения попытки/фазы, не гарантия укладывания всей многостраничной работы. Отдели короткое ожидание tool response от жизненного цикла исследования. При достижении бюджета сохраняй продолжение и уведомляй о partial; не обрывай молча весь массив результатов и не повторяй тот же полный поиск по кругу. Конкретный budget и ограничение попыток должны быть наблюдаемы. Не лечить проблему только увеличением timeout.

### B5. Связать микрофон и UI с целой операцией

Пауза микрофона уже реализована — не писать её заново. Проверь, что listening не возобновляется между search/save/review, если продолжается одна операция; короткий turn_complete не означает завершение исследования. Отмена доступна без голоса.

Cancel/reconnect/фон/ошибка завершают или приостанавливают текущий run согласно явной политике, не теряют подтверждённое и не применяют stale результат. Не отправлять старый PCM после resume. После окончательного результата/partial с передачей управления восстановить прежнее намерение пользователя по микрофону, не включать его неожиданно в фоне. Проверить на реальном Android-клиенте; transport smoke отдельно от physical microphone test.

### B6. Один обязательный acceptance вместо множества observation-прогонов

Переиспользуй лучший существующий harness. Сохрани его в репозитории в подходящем `backend/tools`/tests месте, не создавай ещё десяток untracked variants. Раздели диагностический режим OBSERVED и приёмку PASS/FAIL/BLOCKED_PROVIDER. Exit 0 в acceptance — только после всех обязательных содержательных и state assertions.

Подготовь небольшой вручную проверенный corpus: Королевские ворота и минимум один независимый holdout объект. Найди и прочитай конкретные источники, сохрани разрешённый snapshot, версию и gold facts с passages. Не выдавай имя из навигации/списка экспонатов за доказательство изображения на фасаде. Позиции слева/центр/справа тестируй лишь при прямом подтверждении и определённой точке зрения.

Два разных сценария: широкий запрос об объекте без подсказки имён/ответов и targeted запрос о фигурах. Ожидаемые ответы находятся только в оценщике, не в промпте широкого запроса. Три изображённых персонажа из gold должны появиться как **три самостоятельных выбираемых факта**, не строка с тремя именами. Дополнительные факты оцениваются по релевантности, атомарности и доказательствам, не ради счётчика.

Раздели cold-cache extraction на изолированном store и warm-cache reuse: пользовательский POI cache не очищать. В отчёте фиксируй baseline, новые observations, новые claims, обогащённые источники, unchanged cached facts и eligible result. Корректное переиспользование — полезный результат, но не доказательство нового поиска.

Обязательна локальная интеграционная проверка fallback с управляемыми provider failures, включая успешный финальный review через Live tool contract. Затем один ограниченный реальный прогон доступной модели. При внешней недоступности записать BLOCKED_PROVIDER с точной стадией и сохранённым checkpoint; не переименовывать в PASS и не повторять бесконечно без изменения условия. Работа над детерминированными дефектами и сборкой при этом не останавливается.

### B7. Критерии сдачи

| DoD | Доказательство |
|---|---|
| D01: fallback завершён | Text research/detector unavailable + Live available → точные факты/evidence → review, в том числе zero conflicts → корректная eligibility → результат того же run. Один save сам по себе не PASS. |
| D02: gate корректен | Все четыре контрпримера A4 закрыты; порядок конфликтов не влияет; новое evidence делает нужные решения stale; scan не покрывает чужие/новые revisions. |
| D03: работа не теряется | Прерывание после успешного batch сохраняет payload и позволяет resume со следующего; duplicate delivery идемпотентна; завершённые chunks не переизвлекаются. |
| D04: поздний ответ безопасен | Cancel/смена POI/конкурентная сессия во время последнего await не перезаписывают актуальные данные/выбор; проверка в commit, не только перед сетью. |
| D05: содержательная полнота | Broad и targeted Royal Gates дают 3/3 gold факта о фигурах с раздельными IDs и адресными подтверждениями; holdout и факт из хвоста/границы длинного документа пройдены. Ожидаемые имена не утекли в broad input. |
| D06: пользовательский результат | Факты видны в приложении, выбор сохраняется, eligible используются в черновике; unreviewed/withheld не проходят gate; микрофон/cancel/resume корректны. Реальный Android и mocked tests различены. |
| D07: проверяемая поставка | Committed acceptance, точные выполненные тесты, backend release, APK/version и ссылка на установку/артефакт; место/health проверены; current и rollback сохранены. |
| D08: итог не двусмыслен | Один acceptance report с закрытыми/остаточными пунктами, measured latency, фактическими route/model и terminal states. OBSERVED, CI success и число коммитов не названы готовностью. |

D05 является обязательной проверкой качества при доступной модели/корпусе; недоступность провайдера не означает выполнение D05. Не откладывать все остальные исправления из-за неё. Модельное решение и human review gold не заменять производственным regex-экстрактором.

### B8. Порядок поставки и конечный отчёт

Сначала одна согласованная поставка **полного fallback + исправленного gate**, проверенная негативными интеграционными тестами. Затем checkpoint/resume и run-level UI. После этого содержательный acceptance и APK. Если часть уже закрыта текущим WIP, принять проверенный результат вместо повторной реализации. Не дробить каждый helper на отдельную «стадию 1N/1O/1P» без наблюдаемого завершения сценария.

После функционального пакета выполнить затронутые тесты; полную регрессию — перед поставкой, не вместо разработки. Не добавлять несвязанные обязательные social/image-generation прогоны: эта задача о исследовании фактов, их выборе и безопасном использовании в черновике. Не публиковать в реальные каналы для доказательства качества фактов. Тестовая публикация возможна только в ранее явно разрешённом назначении и если действительно необходима для проверяемого дефекта.

Сохранить отчёт `docs/acceptance/facts-research-finish-2026-10-03.md`. Для каждого D01–D08 указать выполнено/не выполнено, ссылку на evidence и точный остаток. Для общих статусов использовать `IMPLEMENTED_AND_VERIFIED`, `IMPLEMENTED_BUT_EXTERNAL_CHECK_BLOCKED`, `NOT_IMPLEMENTED`; blocked должен содержать наблюдаемую причину, а не «модель, наверное, зависла».

В конце выдать владельцу готовый результат и ссылки: фактический backend/APK, содержательная приёмка, отчёт и единственное необходимое действие владельца, если оно действительно осталось. Не завершать очередным планом, перечнем частичных patches или обещанием доделать позже. Не объявлять внешнюю проверку пройденной, когда доступен только mock.
