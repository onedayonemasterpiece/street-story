# Street Story: диалоговый UX с необязательным Live

Дата: 26 сентября 2026. Статус: **проект для обсуждения, не реализовано и не принято в эксплуатацию**.

Этот документ не заменяет текущий MVP, не разрешает его переписывание и не объявляет `MVP GO`. Изменения приложения, провайдеров и runtime в рамках этого исследования не выполнялись. Рекомендация: **Dialog-first, Live-optional** — единый продуктовый диалог с несколькими способами исполнения.

## 1. Решение

Live хорошо соответствует Street Story: автор показывает фотографию, рассказывает, уточняет, выбирает факты и редактирует будущую публикацию. В основном сценарии это действительно разговор, а не заполнение формы. Но разговор не должен становиться единственным хранилищем истории или новым механизмом публикации.

Предлагается добавить режим «Разговор» к существующей ленте. Его первый исполнитель — Gemini Live. Сохранить полноценный режим «Сообщения»: отдельные голосовые записи, текст, кнопки и асинхронные задачи. Оба режима работают с одной историей, теми же фактами, черновиком и операциями. Смена исполнителя не должна требовать нового фото, повторного выбора фактов или нового заказа изображения.

Главный выигрыш — меньше искусственных остановок «записал → отправил → подождал → записал уточнение». На интерактивном пути native audio может заменить отдельную последовательность ASR → языковая модель → синтез речи. Однако долговременное хранение, проверка фактов, фоновые задания и публикация остаются. Вместо части последовательной оркестрации появляются задачи потокового аудио, прерываний, восстановления и согласованности. Поэтому обещать сокращение всей технической сложности или стоимости в несколько раз до замеров нельзя.

### Что сохраняется без пересмотра

Одна исходная фотография на историю; несколько независимых голосовых сообщений, без обязательного количества; одна вертикальная лента с последними десятью историями; явный выбор истории для микрофона; поиск по явному намерению автора; различение найденного рядом объекта и визуально подтверждённого; источники и выбор фактов; сохранение отклонённых смыслов; оригинальный шаблон изображения; редактируемая подпись; VibePublish как единственная граница визуала и социальных публикаций; нативное отложенное Telegram. VK, MAX и Kaggle не возвращаются в обязательный MVP из-за появления Live. Backend остаётся на DevCoveer, текущие device auth и SQLite сохраняются. [S1–S5]

## 3. Ретроспектива Wonderful Lections: переносить подход, не копировать транспорт

### Полезные решения

В серверном пилоте Live получает небольшой snapshot текущего слайда, а дополнительный контекст — адресными функциями. Изменения проходят через существующий сервис, результат проверяется по принятой revision. Для Street Story аналог — текущая история, выбранные факты и текущий черновик, а не все десять историй или полная база источников. [W1]

Интеграция Live в существующий Review ближе к нужному продукту, чем отдельная тестовая вкладка: пользователь продолжает смотреть на редактируемый объект. Для Street Story разговор тоже должен происходить прямо в ленте, поверх фото и карточек фактов. [W2]

### Что не переносить

В snapshot `d55f8f4` каждый callback браузерного аудио добавляет отдельный HTTP POST в последовательную Promise-очередь. `stopLiveReview` сначала ждёт эту очередь, затем отправляет завершение потока и stop-запрос, и только потом освобождает микрофон. Это конкретная структурная причина возможного запаздывания Stop: остановка устройства зависит от сети и накопившейся работы. Она согласуется с сообщением владельца о задержках, но без runtime-трассировки не объясняет количественно весь инцидент. [W2]

В этом же snapshot события забираются polling, а распознавание локального перебивания использует фиксированный порог энергии. Для уличного Android-сценария это не готовая акустическая реализация. Нужны потоковый канал, ограниченные очереди, независимое локальное выключение и переиспользование имеющегося VAD, а не копирование браузерного порога. [W2, S6]

Нельзя механически переносить три отдельных model round-trip `prepare → apply → readback` на каждую галочку. Для обратимой операции над фактами достаточно **одного атомарного server tool**, который проверяет revision, применяет изменение и возвращает принятую revision с новым состоянием. Отдельное приготовление и подтверждение оправдано для публикации, а не для всех действий подряд.

## 4. Целевой UX

### Два режима в одном месте

**Разговор.** Пользователь включает его явно. Видит исходную фотографию, выбранную историю, состояние микрофона и короткие ответы. Может перебить помощника, поправить адрес, выбрать факт голосом или нажатием, продолжить после паузы. Помощник не читает весь список источников вслух: сообщает главное, подробности показывает карточками.

**Сообщения.** Существующая запись независимых голосовых сообщений остаётся полноценной. Можно надиктовать длинное наблюдение без немедленных ответов, добавить ещё запись и позже запустить поиск. Текст доступен в обоих режимах. Отказ Live не переводит пользователя на другой экран и не обнуляет историю.

Переключатель в ежедневном UI называется «Разговор / Сообщения», а не «Gemini / OpenAI / ASR». Технический исполнитель и возможность его ручного выбора — вторичная настройка. Автоматический выбор учитывает реально проверенные capabilities, доступность и бюджет.

### Пример полного сценария

1. Автор выбирает недавнее фото. Оно сохраняется локально; создаётся история. При выборе «Разговор» система начинает слушать только после явного включения микрофона.
2. Автор рассказывает: «Мне понравилась эта деталь фасада. Сначала просто запиши, я ещё объясню». Помощник сохраняет наблюдение, не запускает исследование на каждой паузе и не перебивает длинное описание.
3. «Теперь найди, что это за здание». Если есть координаты фото, используются они. При их отсутствии помощник уточняет место либо использует явно сказанный адрес. Текущая геопозиция телефона не подставляется молча.
4. Рядом обнаружено несколько объектов. Интерфейс показывает кандидатов и степень визуального совпадения. «Выбираю второй» привязывается к конкретному показанному списку; прокрутка или новый список не меняют смысл уже произнесённой команды.
5. После установления объекта выполняется исследование. Помощник может продолжать разговор, а карточка сообщает «Проверяю источники». Результат: факты, названия источников, количество и ссылки, а не только голосовой пересказ.
6. «Оставь первый и про реставрацию, легенду убери». Выбор отображается теми же чекбоксами. Результат серверной операции подтверждается коротко, доступна отмена изменения. Если ссылка на факт неоднозначна, задаётся один конкретный вопрос.
7. «Сделай текст менее официальным». Меняется черновик на основе принятых материалов. Помощник не возвращает отклонённую легенду и не перезаписывает ручной текст устаревшим результатом.
8. «Подготовь изображение». Запускается существующая операция VibePublish с исходным фото, выбранными фактами и оригинальным шаблоном. Её ожидание не занимает очередь микрофона. Повторное «ну что там?» читает состояние, а не создаёт ещё генерацию.
9. Автор видит изображение и раскрываемую редактируемую подпись. «Поставь завтра на десять в Полюбить Калининград» готовит карточку с точным каналом, календарной датой, временем и часовым поясом. Одно явное подтверждение отправляет ровно этот вариант в нативные отложенные. Статус «Запланировано» появляется после фактического ответа провайдера.
10. Завершение разговора не удаляет историю и не отменяет уже поставленную публикацию. Новое голосовое уточнение не меняет её скрытно.

Кнопки «Найти факты», «Подготовить изображение» и ручное редактирование не исчезают. Голос — дополнительный способ вызвать те же действия, а не новый обязательный ритуал.

### Не путать четыре намерения

«Не перебивай» меняет политику ответов. «Микрофон выключить» немедленно прекращает захват, но не удаляет историю. «Завершить разговор» закрывает live-сеанс и сохраняет результат. «Отмени генерацию/публикацию» — отдельная команда конкретной серверной операции. Перебивание голосового ответа само по себе не откатывает выполненную мутацию.

## 5. UI: сохранить визуальный язык, улучшить устойчивость

### Компоновка

Сохраняется одна вертикальная лента. Основная визуальная опора — фотография и результат работы, не огромный светящийся шар помощника. Предыдущие истории можно свернуть, но не превращать переход на Live в новый мастер шагов.

Нижняя закреплённая панель содержит миниатюру и название **активной истории**, переключатель режима, понятный статус, микрофон и завершение разговора. Прокрутка ленты не переназначает микрофон. При явной смене истории незавершённая реплика сначала сохраняется в старую; новый сеанс получает другое поколение событий.

В самой истории остаются: фото, сообщения автора, компактные ответы, кандидаты места, карточки фактов с источниками, состояние долгой операции, итоговый визуал, раскрываемая подпись и карточка публикации. Частичная транскрипция обновляет один временный блок; каждое слово не создаёт новое сообщение. После фиксации сохраняются отдельно исходная транскрипция и аккуратный отображаемый текст.

### Палитра и типографика

База берётся из текущего `MainActivity.kt`: sage `#D9E4DF`, paper `#F6F3ED`, graphite `#292B29`, ink `#202220`, accent orange `#EF4B23`. Не вводится новая неоновая стилистика. [S7]

Предлагаемые размеры: основной текст 16sp, подписи 14sp; заголовки карточек 18–20sp. Управление микрофоном и завершением — крупное, зоны нажатия не меньше 48dp. Важные состояния различаются словами и иконками, не только цветом. Оранжевый используется для акцентов и индикаторов; контраст каждой пары проверяется отдельно. Нужны крупный системный шрифт, TalkBack, достаточный контраст на улице и режим уменьшенной анимации. Рекомендация 48dp соответствует Android accessibility guidance. [A1]

### Независимые состояния вместо одного «Live занят»

| Ось | Примеры | Пользовательский смысл |
|---|---|---|
| Микрофон | off / listening / speaking / muted | Слышит ли сейчас устройство |
| Ответ | idle / preparing / playing | Говорит ли помощник |
| Соединение | online / reconnecting / messages / offline | Как исполняется диалог |
| Задание | research / visual / scheduling / done / blocked | Что делает сервер |
| История | существующие product states и revision | Что реально сохранено и готово |

Корректное сочетание: «Слушаю» и одновременно «Проверяю источники». Некорректное — блокировать микрофон до завершения генерации картинки.

### Тексты состояний

«Слушаю» — только при фактическом захвате. «Микрофон выключен» — сразу после локального выключения. «Запись сохранена на телефоне» и «Синхронизировано» — разные подтверждённые состояния. «Связь прервалась. Запись сохранена. Продолжим сообщениями» допустимо только после локального подтверждения сохранения. Если хвост реплики не подтверждён, нужно явно обозначить его, а не делать вид, что ничего не потеряно.

После отказа Live выбор фактов, текст в редакторе, положение прокрутки и активная история сохраняются. Подсказка о переходе появляется один раз. Автоматический возврат в Live посреди обычной записи запрещён; пользователь возвращается сам.

### Производительность интерфейса — часть UX

В проверенном Android-коде `liveTick` раз в 700 мс во время записи вызывает `render()`, который заново создаёт корневую ленту и вызывает `setContentView`. Это плохое место для подключения ещё и потока транскрипции. [S7]

Нужны адресные обновления микрофонной панели, временной реплики и изменившейся карточки; стабильные ключи элементов; отсутствие принудительного скролла, если автор читает выше; сохранение фокуса и выделения в редакторе. Полный переход на Compose не является предварительным условием: сначала исправляется способ обновления существующих Views.

## 6. Архитектура без нового оркестратора всего продукта

```text
Android: одна история и один механизм захвата
  микрофон → обработка аудио / существующий VAD
             ├─ устойчивые M4A-чанки → локальное хранилище → обычная синхронизация
             └─ короткие аудиофреймы → потоковый канал

DevCoveer: Street Story backend
  ConversationSession / транспортный шлюз
             ↔ ConversationProvider
               ├─ Gemini Live
               ├─ другой проверенный realtime-провайдер
               └─ составной ASR + LLM + TTS
             ↓ ограниченный диспетчер бизнес-функций
  существующие StoryService / SQLite / durable jobs
             ├─ OSM / Wikipedia / research provider
             └─ VibePublish → изображение / нативная публикация / отмена

Обычные голосовые сообщения и кнопки → те же StoryService и durable jobs
```

Для первой реализации достаточно небольшого модуля сеансов внутри существующего FastAPI backend и адаптера провайдера. Не нужны обязательные Kafka, Redis, отдельная агентная платформа, смена базы или новая инфраструктура публикации.

### Разделить сменяемость по уровням

`ConversationProvider` отвечает за разговор, аудио, транскрипцию и запросы функций. `ResearchProvider` — за поиск и структурированную доказательную базу. `Visual/PublicationProvider` остаётся VibePublish. Смена голосовой модели не должна означать смену поискового конвейера или социальных идентификаторов.

У адаптера достаточно явных возможностей: приём аудио/изображения/текста, потоковый ответ, транскрипция, выбранная политика VAD, прерывание, неблокирующие функции, восстановление сеанса и поддержанные форматы. Не следует обещать одинаковое поведение всех поставщиков или строить универсальный язык workflow заранее.

Gemini Live поддерживает потоковый PCM, транскрипции, функцию вызова инструментов и настройки VAD; в актуальной документации поведение async tools отличается между моделями. Поэтому модель выбирается серверной конфигурацией и проверяется коротким capability smoke, а не жёстко зашивается в APK. [G1, G2]

Как второй native-кандидат можно рассматривать OpenAI voice/realtime: официально предусмотрено серверное управление и исполнение приватных инструментов. Это подтверждает осуществимость альтернативного адаптера, но не означает, что он уже подключён или проверен в Street Story. Его протокол, sample rate и модель на момент реализации выбираются отдельно. [O1]

### Транспорт

Начальный вариант — один долговременный Android ↔ backend WebSocket с бинарными аудиокадрами и небольшими сообщениями состояния. Backend переводит формат в требуемый конкретному provider API. Фото передаётся отдельно, в сеанс входит его уменьшенная визуальная версия и идентификатор, а не постоянная повторная отправка оригинала.

Прямое подключение клиента к provider через временный токен может убрать один сетевой участок, но усложняет смену поставщика, хранение истории и владение tool execution. Это последующая оптимизация после измерений. WebRTC/Opus также допустимы, если измерения мобильной сети оправдают дополнительный транспорт. Они не являются условием первого прототипа.

Google требует raw PCM для Live: вход нативно 16 kHz, 16 bit, выход 24 kHz. [G1] Сжатие на участке телефон → собственный сервер возможно, но перед Google потребуется декодирование. При уже имеющемся PCM не нужно сначала создавать M4A, ждать закрытия файла и декодировать его обратно ради Live. Поток и архив расходятся до архивного кодирования.

Расчёт, не замер: 16000 × 2 = 32000 байт/с входящего PCM, около 1,92 MB/мин; base64 добавляет примерно треть до накладных расходов протокола. Это не бесплатно для мобильного трафика, но само по себе не объясняет многоминутное накопление задержки. Сначала измеряются очереди, затем выбирается сжатие.

## 7. VAD и надёжная запись

**Сегмент речи ≠ реплика диалога ≠ отдельное сохранённое голосовое сообщение ≠ команда начать research.** Смешение этих четырёх границ создаст либо постоянные перебивания, либо ожидание длинных файлов вместо Live.

Существующий `EfficientVad` использует WebRTC VAD, 16 kHz, 480 samples / 30 мс, адаптивный энергетический порог и fail-open при отказе детектора. Его следует переиспользовать вместе с уже проверенной механикой записи, не заводя второй конкурирующий AudioRecord. [S6]

### Предлагаемая политика

Для Gemini первым проверяется документированный hybrid VAD: сервер распознаёт начало речи, клиент сообщает конец через `audio_stream_end`; серверное определение конца остаётся запасным. Это снижает задержку, но слишком ранний сигнал обрезает фразу. Ручной режим с отключённым auto VAD использует отдельные `activityStart/activityEnd` и не должен смешиваться с hybrid по случайному условию. [G1]

Параметры не объявляются окончательными: отправные гипотезы — pre-roll 200–300 мс, акустический хвост 200–400 мс, окончание короткой реплики после примерно 650–1000 мс паузы; для длинного рассказа более терпеливая политика. Их нужно проверять на русской речи, именах, адресах и уличном шуме. Для «сначала расскажу» полезна явная кнопка «Я закончил», без обязанности проговаривать специальную команду.

В live-потоке нельзя бесследно склеивать разрозненные речевые куски, полностью вырезая паузы, и затем ждать, что сервер сам угадает границы. Передаются нужный хвост/сигналы активности и монотонные временные метки. Архивный wall time и сжатая речевая шкала связываются явной картой, чтобы восстановление не дублировало реплику.

### Очереди и Stop

Начальная цель — отправка пакетов порядка 60–100 мс и ограничение устаревающего аудиобуфера несколькими сотнями миллисекунд. Конкретные пороги настраиваются измерениями. Если сеть постоянно не успевает, приложение не догоняет автора минутами: заканчивает попытку Live, сохраняет речь обычным путём и сообщает о переходе.

Stop сначала локально запрещает новый захват и отправку, останавливает воспроизведение и инвалидирует поколение сеанса. Затем завершается сохранение текущего доступного аудио; закрытие внешнего соединения не блокирует кнопки и микрофон. Уже отправленные данные нельзя отозвать обещанием в UI, но старые результаты не могут менять новую историю.

При переполнении нельзя тихо выбрасывать середину реплики и выполнять обрезанную команду. Неполная реплика маркируется; её сохранённое аудио можно дообработать обычным путём. Если локальное хранилище переполнено, нельзя сообщать «сохранено» — запись останавливается с понятным объяснением.

### Перебивание и акустика

При начале речи автора локально прекращается проигрывание ответа и очищается его очередь. Провайдеру передаётся прерывание; поздние аудиочасти прежнего ответа игнорируются. Исполненный server tool при этом не откатывается автоматически: требуется отдельная семантическая отмена или readback.

Нужны проверка эха при громкой связи, шумоподавление без уничтожения тихой речи, смена гарнитуры, звонок/потеря audio focus, блокировка экрана и явный foreground-режим. Нельзя считать любой громкий звук командой перебивания. В шуме доступна запись по удержанию/нажатию — не только попытка бесконечно подкручивать auto VAD.

## 8. Серверные функции

Модель предлагает вызов; backend проверяет его и исполняет существующий сервис. Provider SDK не заменяет бизнес-авторизацию. Live function calling в Google требует собственного обработчика и возврата результата. [G2]

Ниже логический проект функций, не обещание уже существующих новых HTTP endpoints.

| Функция | Результат и граница |
|---|---|
| `get_story_context(slice)` | Короткий snapshot текущей истории; дополнительные источники адресно |
| `find_place_candidates(location_ref)` | Кандидаты из OSM/Wikipedia; происхождение координат и неопределённость |
| `verify_photo_identity(candidate_id)` | Визуальное match/uncertain/mismatch; отдельно от решения владельца |
| `confirm_place(candidate_id, expected_revision)` | Явный выбор автора, не выдаваемый за машинное доказательство |
| `start_research(input_revision)` | Durable operation id и принятый статус, без ожидания всего исследования |
| `get_operation(operation_id)` | Фактическое состояние долгой задачи; не её повторный запуск |
| `get_fact_sources(fact_ids)` | Названия, URL, выдержки и ограничения доказательств |
| `set_fact_selection(change, expected_revision)` | Атомарный выбор/отклонение, новая revision и краткий diff |
| `revise_draft(instruction, expected_revision)` | Новая версия черновика без скрытой перезаписи ручного изменения |
| `request_visual(content_revision)` | Существующая VibePublish-операция с фиксированным owner prompt |
| `prepare_publication(destination, at, content_revision)` | Карточка точного варианта для единственного явного подтверждения |

Финальное подтверждение публикации в первом MVP — привычное действие интерфейса. Голос может заполнить карточку и запросить её показ. Полностью голосовое подтверждение возможно позднее, если оно однозначно связано с показанным вариантом, временем и каналом; произвольное «да» из чужой реплики недостаточно. Не нужно добавлять дополнительные подтверждения на каждую обратимую правку.

Списки инструментов компактны и зависят от этапа. Не выдавать произвольные HTTP-запросы, shell, SQL, полный MCP-каталог или ключи. Story/device binding определяется сервером. Вызов принимается только после полного разбора аргументов и проверки текущей revision; частичные JSON-аргументы потока не исполняются.

Долгие функции быстро возвращают «принято» и operation id, а результат приходит событием. Там, где native non-blocking tools недоступны, составной адаптер воспроизводит ту же модель задания. Это не повод блокировать канал аудио или запускать отдельного планирующего агента для каждого шага.

## 9. Источники и OSM: Live не заменяет доказательства

OSM по координатам даёт кандидатов, не идентичность сфотографированного объекта. Координаты фотографии, явно названный адрес и текущая позиция устройства — разные источники. Для каждого сохраняются происхождение, время и доступная точность. При отсутствии координат задаётся один полезный вопрос, не придумывается уверенное место.

Поиск выполняется по явному намерению, с кэшем и ограниченным расширением области при необходимости. Public Nominatim ограничивает приложение суммарно одним запросом в секунду, требует идентифицирующий User-Agent/Referer и атрибуцию; предполагает возможность смены endpoint и рекомендует кэширование. Это не лимит всей экосистемы OSM/Overpass и не правило для любого коммерческого геокодера. [M1]

Встроенный Google Search в Live существует, но для MVP рекомендуется основной research оставлять отдельной серверной функцией: так сохраняются воспроизводимые результаты, уже выбранные факты и сменяемость голосового провайдера. Нативный поиск может быть позднее использован как один из research-адаптеров, если его результаты переводятся в ту же доказательную модель. Само наличие ссылки не делает утверждение проверенным. [G2]

В текущем `_excerpt_supports` есть лексическая проверка совпадения слов. Это полезный ограниченный фильтр, но не доказательство семантической поддержки утверждения: слова могут встречаться в отрицании, другом контексте или рядом с другой датой. Нельзя считать перенос поля `evidence_supported` в Live достаточной проверкой качества. [S4]

Проектная граница: факт связан с конкретной выдержкой, источником и статусом проверки; даты, числа, отрицания и противоречия проверяются содержательно. Неподтверждённые факты не становятся выбранными автоматически. Личные наблюдения автора сохраняются отдельно и могут входить в пост как авторские впечатления, не маскируясь под историческую справку. Страницы и результаты поиска — данные, не инструкции для модели.

## 10. Сохранение состояния и переход между провайдерами

История живёт дольше любой Live-сессии. Хранить отдельно канонический документ и краткоживущие события аудио.

Минимальные идентификаторы: `story_id`, `capture_session_id`, `user_turn_id`, `command_id`, `provider_session_id`, `session_epoch`, `expected_revision`, `event_seq`. Не все поля обязаны быть отдельными новыми таблицами: сначала использовать существующие story/voice/job/revision/idempotency структуры.

`command_id` обозначает смысловую операцию пользователя. Provider function-call id — только попытку её исполнения. Смена провайдера не создаёт новый заказ картинки или публикации. Намерение и ключ сохраняются до внешнего вызова; после потерянного ответа читается известная операция, а не отправляется новая.

При смене провайдера старому epoch запрещается принимать новые мутации. Уже принятые durable jobs продолжаются независимо от голоса. Поздние tool/audio события не меняют новый сеанс. При конфликте revision возвращается актуальное состояние, а не слепо перезаписывается текст.

Для восстановления передаётся небольшой пакет: текущая история и фото, подтверждённое место, принятые/отклонённые факты, ручной черновик и revision, последние необходимые реплики, состояния операций и неполные намерения. Не загружается вся история аудио или все источники. Резюме разговора не может отменять структурно сохранённый выбор автора.

Запись и транскрипция связываются по реплике и времени. Live-транскрипция — производный артефакт; исходное аудио и прежний raw/display contract сохраняются. Не нужно транскрибировать всю речь дважды по умолчанию. Повторное ASR выполняется только для отсутствующего/неполного текста, восстановления или явно выбранной проверки. Поздняя корректировка ASR не переисполняет команды.

Текст уже сгенерированного ответа не равен тому, что автор успел услышать. Для прерванного вывода хранится статус воспроизведения; новый исполнитель не должен считать неозвученное подтверждение услышанным. Для бизнес-состояния решающим остаётся результат операции.

Google предоставляет session resumption и сжатие контекста, а соединения имеют ограниченный срок жизни. Эти возможности помогают внутри Google, но не заменяют собственное долговременное состояние и не переносят память в другой API. [G3]

### Матрица деградации

| Отказ | Продолжение | Что нельзя обещать |
|---|---|---|
| Недоступен только Gemini Live | Другой проверенный realtime или сообщения с обычным ASR/LLM | Что любой другой Google endpoint тоже недоступен |
| Недоступен Google целиком | Независимый ASR/LLM/research, если настроен; иначе локальная запись и очередь | Полноценный AI-fallback через прежний Gemini ASR |
| Нет сети / backend недоступен | Фото, аудио, текст и выбор сохраняются локально, синхронизация позже | Работу внешнего поиска или генерации без соединения |
| Отказало озвучивание | Ответ текстом в той же истории | Что помощник уже произнёс ответ |
| Отказал research | Можно продолжать запись и редактировать имеющееся; задача честно отмечена | Новые подтверждённые факты из памяти Live |
| Не работает автоопределение речи | Управляемая запись / сообщения | Надёжный hands-free в данном шуме |
| Не отвечает VibePublish | Сохранённый черновик и операция с повторной сверкой состояния | Прямую публикацию в обход VibePublish или фиктивный успех |

Сначала ограниченная попытка восстановления, затем понятный переход. Нельзя одновременно гонять одного пользователя по многим провайдерам, сжигать бюджет и принимать конкурирующие tool-вызовы. После перехода в сообщения Live не включается сам.

## 11. Проверка качества и бюджета

Числа ниже — **проектные цели для проверки, не измеренные свойства нынешнего MVP**. Измерения выполняются отдельно на клиенте и сервере с монотонными часами; end-to-end latency нельзя получать простым вычитанием несинхронизированных timestamp разных устройств.

| Проверка | Предлагаемая цель |
|---|---|
| Нажатие mute/stop → локальная реакция | p95 до 100 мс; отсутствие дальнейшей постановки новых кадров в отправку |
| Начало перебивания → остановка локального проигрывания | p95 до 150 мс |
| Конец короткой реплики → начало полезного голосового ответа без внешнего поиска | Ориентир p50 до 1 с, p95 до 2 с на согласованной сети |
| Принятие долгой задачи | Быстрое подтверждение operation id; полное время research/imagegen измеряется отдельно |
| 1-я, 10-я и 30-я реплики | Нет систематического накопления очереди и задержки |
| Продолжительный сеанс | 20 минут с восстановлением соединения и без потери принятых команд |
| Дубликаты и неверная история | Ноль повторных внешних эффектов и мутаций чужой активной истории в тестовом наборе |

Корпус: русская речь, длинные паузы, самокоррекция, имена и адреса, тихий голос, ветер, транспорт, чужая речь, динамик телефона, гарнитура. Считать не только latency, но обрезанные реплики, ложные перебивания, долю уточнений, успешность завершённой истории и субъективное усилие автора.

Нужны fault-тесты в каждой точке: обрыв до фиксации реплики; после принятия команды; после запуска изображения; после успешной публикации с потерянным ответом; после ручной правки; после смены истории; после нажатия Stop. Проверять одновременно результат на сервере, состояние UI и отсутствие позднего изменения.

Эмулятор с подготовленным аудио проверяет протокол и сценарий, но не качество физической акустики. Это не расширение прежнего обязательного MVP acceptance задним числом: акустическая проверка выделяется отдельно при реализации Live. Текущая задача заканчивается проектом, а не новым runtime gate.

Стоимость считать на завершённую полезную историю: длительность входа/выхода, контекст и его повторная передача, ASR-повторы, research, imagegen, число восстановлений и дубликатов. Не считать минуту установленного соединения равной минуте полезного диалога. Не называть режим безлимитным по старому скриншоту квот. У провайдера используются реальные доступные лимиты и Retry-After; недоступность не лечится лавиной повторов.

## 12. Последовательность реализации после отдельного решения

**Шаг A — небольшой вертикальный прототип.** Feature flag по умолчанию выключен. Одна история, существующий recorder, Gemini adapter, явное начало/Stop, компактный контекст, read-only функция и одна обратимая операция выбора факта. Никакого переписывания текущего research и публикации.

**Шаг B — устойчивость разговора.** Ограниченные очереди, endpointing, перебивание, смена истории, отключение сети, локальная сохранность, восстановление в сообщения. Поддельный provider для детерминированных fault-тестов. До прохождения этого шага не расширять число функций.

**Шаг C — тот же продуктовый путь.** OSM/Wikipedia/визуальная проверка, явный research, выбор фактов, редактура, прежний VibePublish. Прогнать существующий Telegram schedule/readback/cancel, не создавая параллельный harness без необходимости.

**Шаг D — независимый исполнитель.** Подключить второй реальный realtime либо составной ASR/LLM/TTS путь и доказать перенос состояния, а не только заменить имя модели в настройке. Независимость от полного отказа Google требует независимых критичных ASR/research компонентов или честного ограниченного режима.

Необязательны для первого шага: постоянная камера, новый архив историй, shared-agent platform, несколько одновременно активных Live-моделей, автоматический поиск после каждой фразы, обязательный WebRTC, переход на Compose, выделение общего WL/StreetStory SDK до появления второго реально проверенного потребителя. Переносить общие контракты и тестовые случаи полезнее, чем преждевременно объединять две разные реализации.

### Критерий продуктового решения

Live стоит делать основным предлагаемым режимом после того, как он снижает усилия автора и время полезного взаимодействия, не ухудшая фактическую точность, сохранность и управление публикацией. Даже после этого «Сообщения» остаются видимым равноправным способом работы. **Успешный продукт — один Street Story с несколькими исполнителями диалога, а не два несвязанных приложения.**
