## 1. Вывод

Сценарий остановился после голосовой просьбы опубликовать уже подготовленную историю. Сервер распознал просьбу и начал перевод Live-сессии к инструментам публикации, но этот переход затянулся из-за отказов бюджета. После получения бюджета синхронная подготовка фотографии и состояния истории выполнялась в callback `on_resumed`. События этого участка занимают **7,346 с**; в коде работа выполняется синхронно на пути возобновления Live. В том же эпизоде Android зафиксировал **`LIVE_AUDIO_BACKPRESSURE`**, завершил голосовую сессию и затем прошёл новый старт. Минимальное исправление этого участка реализовано в [PR #302](https://github.com/onedayonemasterpiece/street-story/pull/302): синхронная подготовка вынесена из event loop. Четыре новых различающих случая падают на неизменённом `de753520…`; на кандидате прошли все пять целевых проверок. Android backpressure привязан к **09:24:37.001–37.012 по часам телефона** двумя независимыми монотонными якорями. Этот расчёт попадает внутрь серверного resume-интервала 09:24:35.472–42.818; неизвестное смещение часов телефона относительно сервера сохраняется как ограничение. Сервер принял ошибку около 09:24:43.198, поэтому его timestamp нельзя принимать за момент возникновения ошибки.

Это уточняет первоначальный бриф: видимые в logcat `SocketTimeoutException` относятся к отправке диагностики и сами по себе не устанавливают причину падения основного WSS-транспорта. Серверные записи сохранили более предметный код ошибки.

Для второй жалобы обнаружен отдельный последовательный путь задержки. **Исходный thumbnail** сервер выдал уже в 09:22:11.042, примерно через 3 с после запуска приложения. **Готовый processed preview** той же истории получил HTTP 200 только в **09:23:11.487**, примерно через **63 с после запуска**. Перед этим `SyncWorker` поочерёдно синхронизировал другие истории и их assets; выбранная история БФУ не имела приоритета. Хронология запросов и код согласуются с задержкой из-за очередности синхронизации. Точный момент отрисовки пикселей на экране и то, какое из изображений владелец называл «фото», без исходной записи пока неизвестны. Ошибки доступа к старому локальному `content://` URI присутствуют, но не объясняют автоматически всю задержку processed preview.

**Состояние исправления:** backend установлен и здоров; [APK 0.1.1629](https://github.com/onedayonemasterpiece/street-story/releases/download/android-v1629/street-story.apk) выпущен с канонической подписью. ## 4. Время и правила сопоставления

Дата всех событий ниже — **30.10.2026**. **Все часы в отчёте указаны для Калининграда, UTC+02:00**. Серверные epoch timestamps и UTC-записи journal переведены в этот часовой пояс; для сопоставления с исходным UTC нужно вычесть два часа. Android `logcat` использует часы устройства. Серверный `at` — время сохранения/приёма события; для Android-диагностики в payload также есть монотонный `elapsed_ms`. Приведение часового пояса не означает синхронизации часов телефона и сервера.

В logcat есть клиентские таймауты отправки диагностики, а соответствующие события сохранены на сервере. Повторная отправка не доказана: исходный HTTP-запрос мог завершиться на сервере после таймаута клиента. Позднее появление записи в БД не доказывает, что действие на телефоне произошло именно тогда. Нельзя смешивать серверные timestamps и `logcat` без проверки смещения. Метка `Slack created=09:26:21` относится к файлу в Slack; начало самой аудиозаписи из неё не выводилось.

## 5. Подтверждённый разговор и границы аудио

Серверный Live transcript подтверждает, что пользователь дважды попросил публикацию и что Мира распознала тему и начала переход к publication. Это опровергает слишком широкое утверждение «голос вообще не поступал».

В то же время найденный transcript — **не расшифровка параллельного `audio_message.m4a`**, который владелец записывал для расследования. В нём отсутствуют комментарии вне принятого Live-потока, длительность всех пауз и то, что реально звучало из динамика телефона. Нельзя использовать эти шесть сохранённых transcript-фрагментов как замену пользовательской записи.

Причина отсутствия оригинальной расшифровки установлена. Slack connector возвращает для точного файла только metadata; `file_uri`, `file_name`, `mime_type`, `text_content` равны `null`. У существующей документированной server identity `kaliningrad_base` проверка workspace прошла, но `files.info(F0CDEBWSB5L)` вернул **`missing_scope`, требуется `files:read`**. После этого путь остановлен: scopes и identity не менялись, другая учётная запись для обхода отказа не использовалась. Подходящей ранее авторизованной browser-сессии Slack тоже нет.

Для завершения этой части владелец должен предоставить сам файл в чате либо независимо разрешённый доступ к вложению. До этого ASR исходной записи выполнить нельзя; приведённые выше Live-реплики остаются отдельным серверным источником.

**Невыполненная часть исходного поручения:** оригинальное аудио недоступно, поэтому ASR и его сопоставление с logcat не выполнены. Для продолжения нужен сам файл в чате либо независимо разрешённый доступ к вложению. До получения bytes нет достоверных duration, контейнерного времени или относительных таймкодов; время загрузки в Slack не подставляется вместо времени записи.

## 6. Находки: наблюдение, механизм, гипотеза

### 6.1. Синхронная работа при resume Live

**Механизм в коде:** в исполняемой версии `backend/street_story/live.py:1679` метод `on_resumed` синхронный. Он вызывает `_send_visual_snapshot`, затем операции сравнения/наблюдения и вычисляет `_topic_state` перед `product_state`. Подготовка визуального контекста читает и преобразует фото через PIL; состояние истории собирается синхронно. Другие вызовы `_topic_state` в этом же файле уже используют `asyncio.to_thread`.

| Приоритет выбранной истории | Сначала обслуживаются другие истории, готовая картинка БФУ приходит через ~63 с | Существующий цикл `SyncWorker`; меняется порядок, синхронизация остальных сохраняется | Оставлена перестановка порядка, без второй очереди |
| Aliases реальных wait / ready событий | Budget wait есть в диагностике, Android обрабатывал только literal `budget_wait` | Существующие `waitStage`, `waitStarted`, статус и таймер | Переиспользованы; поздний ready не затирает более новый ответ |

Суммарный размер production-изменения — **net +22 строки в трёх файлах**, внутри установленного в PR предела **60 production-строк**. Для UI дополнительно установлен предел ≤20 production-строк; кандидат укладывается и в него. Из пути убрана непосредственная синхронная подготовка на event loop и ожидание выбранной историей всех предшествующих историй; продуктовые функции не удалялись.

Сознательно не добавлялись новый transport, новые очереди, retries, persistent flags, увеличение аудиобуфера, повышение квот, смена SDK, новый diagnostics client или расширение Slack-доступов. Серверная часть уже работает на исправленном SHA. Изменения SyncWorker и UI-статуса станут доступны на телефоне после установки новой APK. Пользовательский результат всё ещё требует проверки на устройстве; PR, host-тесты, health и emulator CI не заменяют эту приёмку.
