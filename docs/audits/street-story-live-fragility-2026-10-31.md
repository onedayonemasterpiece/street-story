# Street Story Live SQLite ACK starvation — 31.10.2026

## Пользователь и установленный дефект

Владелец почти при каждом запуске голосового Live получал разрыв сессии, если SyncWorker одновременно читает истории. Установленная Claude Opus трасса 31.10.2026 17:20:45Z и воспроизведение: `story()` собирал 0,5–1,8 МБ JSON внутри SQLite `BEGIN IMMEDIATE` (на холодном кэше до ~4 с). POST диагностики Live и callback записи реплик блокировали event loop на ожидании SQLite writer lock; ACK PCM не уходил, телефон разрывал WSS после ~1,5 с. Исходные доказательства: `/home/dev/artifacts/street-story/20261031T172204Z-live-fragility-20261031/{findings.md,repro.txt}`. Новое расследование причины не проводилось.

## Исправление

- `service.story()`: write-транзакция охватывает только гидратацию POI; после неё новая WAL read-транзакция `BEGIN` предоставляет согласованный снимок для всей большой проекции, не захватывая writer lock.
- `live.py`: **один** последовательный `ThreadPoolExecutor(max_workers=1)` выполняет диагностические INSERT, сохранение/merge/finalize разговорных реплик и DB-операции закрытия сессии/передачи исследования. Отдельного состояния и второй очереди нет. Порядок операций реплик сохраняется порядком отправки в один executor. Исключения записываются в журнал. Непосредственные синхронные вызовы без работающего event loop по-прежнему ожидают подтверждения записи.
- `app.py`: HTTP POST диагностики дожидается `Future` асинхронно, не блокируя loop; для текстового ввода shared Live host ожидает результат записи до отправки провайдеру (сохраняется existing durability boundary).
- `live_diagnostics(created_at)`: индекс устраняет полный скан в регулярном `DELETE` старше семи дней. Существующая политика retention не меняется.
- `app.py`: журналирование `street_story.*` INFO направляется в уже существующий обработчик `uvicorn.error`/journald, без отдельной службы и нового log pipeline.

Изменения production Python по `git diff --numstat`: `app.py +6/-1`, `live.py +77/-12`, `service.py +6/-4`, итого **+72 строки net** (бюджет до +160). Кроме production добавлен один различающий `backend/tests/test_live_sqlite_ack.py`.

| Асинхронное ожидание HTTP и текстового ввода | Диагностика телефона блокирует loop, текст обязан сохраняться до provider delivery | `asyncio.wrap_future` и shared-host `_maybe_await` уже существуют; новых протоколов не нужно | Оставлено |

## Проверки и границы приёмки

Различающий тест создаёт `BEGIN IMMEDIATE` в независимом потоке на 650 мс, в это время отправляет диагностику и несколько user/assistant-фрагментов и проверяет, что событие audio ACK loop выполняется меньше чем за 300 мс, а сохранённые фрагменты слиты в правильном порядке. На прежнем синхронном коде вызов диагностики под lock задерживал бы loop более 300 мс.

`compileall` изменённых Python-модулей и теста — PASS. Локальный адресный `pytest` пока **НЕ РАБОТАЛ** из-за отсутствия `bs4` в системном окружении, отсутствия `pytest` в production venv и бинарной несовместимости PIL при смешивании двух Python. Полный серверный набор намеренно не запускается; источник проверок — GitHub CI.

**Нельзя считать зелёный CI доказательством исправления на телефоне.** До проверки после деплоя явно остаются: фактическая версия активного процесса и health, journal INFO событий, реальная Live-сессия через провайдера на `story_f4ddb121a6e568382d8470d1` («Вилла») с параллельной загрузкой всех историй, отсутствие физического обрыва и сохранность транскриптов. Выполненные приёмочные шаги должны быть дополнены отдельными проверяемыми квитанциями; физический микрофон не заменяется mock PCM. Shared-framework правило «1,5 с без ACK» **не менялось**; PR #306 (слоты публикации) вне области правки.
