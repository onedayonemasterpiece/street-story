# Street Story: аудит фактов и целевая схема

Дата: 3 октября 2026. Статус: **аудит и предложение архитектуры; исправления реализации не выполнены**.

Постановка на следующий этап: [промпт реализации](../prompts/facts-research-remediation-2026-10-03.md).

## 1. Вывод для принятия решения

Проблема шире регулярных выражений. В проверенных основных путях смысл уже определяют модели, но приложение не обеспечивает сохранность и полноту их входов и результатов. Главные дефекты: частичное чтение источников без достоверного учёта покрытия; замена результатов предыдущего прохода; смешение идентичности утверждения с модельным ключом; недостаточная привязка доказательства к конкретному факту; отсутствие версионного барьера между новым свидетельством, старым арбитражем и использованием факта.

Правильная цель — не «получить побольше пунктов» и не «поднять лимит с 20 до 32». Нужна проверяемая цепочка:

```text
цель автора + подтверждённый POI
    → план аспектов исследования
    → найденные источники
    → версии документов и учёт покрытия
    → извлечение из каждого принятого фрагмента
    → неизменяемые утверждения с адресными доказательствами
    → модельное установление эквивалентности / расхождений
    → версионный журнал решений
    → допуск к использованию ∩ выбор автора
    → текст публикации
```

**Рекомендуемое разделение:** Live Мира ведёт диалог, задаёт исследовательскую цель, уточняет пробелы и объясняет/арбитрирует результат. Существующий настроенный текстовый LLM может выполнять пакетное извлечение и сравнение за явным контрактом исследовательского процесса. Его существование не нарушает LLM-first. Однако имя модели, роль, входное evidence и решения должны быть наблюдаемы; нельзя незаметно считать краткий ответ поискового помощника окончательной истиной. Детерминированный код отвечает за доставку, идентификаторы, версии, очереди, ссылки, сохранение и выполнение принятых ограничений, а не за смысл исторических фактов.

## 3. Что действительно реализовано

Основной `search_web` вызывает отдельный `generateContent` с Google Search grounding. Этот вызов уже сам формирует факты. При недоступности маршрутов выполняется публичный DDG discovery, затем `_semantic_complete_discovery` через текстовый research-маршрут. Только при неуспехе этого шага Live получает `discovery_only` и самостоятельно вызывает `save_research_facts` по ссылкам на сниппеты.

Следовательно, утверждение «Live Мира последовательно читает все статьи, извлекает и дедуплицирует все их факты» не описывает текущий основной путь. Это не доказательство непригодности отдельной модели; это важное различие фактических ролей и ожидаемого продукта.

Полезные механизмы уже существуют: проверка идентичности фото/POI, ограниченные tool payload, привязанные к истории команды и replay, сохранение источников, модельный детектор и журнал конфликтов, сохранение выбора, прогресс в Android. В shared framework уже включены `contextWindowCompression` и `sessionResumption`; есть ограниченная история и обработка событий отмены. Переделывать WSS с нуля не требуется.

## 4. Подтверждённые проблемы и риски

### F01. Страница прочитана частично, но полнота не представлена в данных — P1

В `_fetch_page_excerpts` принимаются максимум две страницы. Читается только ограниченный HTML/text; parser получает лимит 9 000 символов. Redirect, неподходящий тип и ошибка чтения приводят к пропуску. Тело большого ответа ограничивается после получения; нет manifest всех фрагментов, cursor продолжения или явного состояния «остальная часть не прочитана».

В B появилась `_chunk_page_text`, но результат склеивается обратно в одну строку `page_excerpt`, а `evidence_rows` ещё раз берёт первые 9 000 символов. Заголовки чанков и overlap тоже расходуют этот предел. **Это не обход всех частей статьи отдельными модельными проходами.** Факт в конце длинной статьи всё ещё может не попасть во вход модели.

У helper есть дополнительные дефекты: длинный абзац после непустого буфера не пересегментируется; результат обрезается `chunks[:6]`. Второй дефект особенно важен при будущем расширении чтения: поднять только предел страницы недостаточно.

### F02. URL «видели» приравнивается к «обработали» — P1

`persist_research_memory` записывает переданные search/grounding sources в `poi_research_sources`, даже когда известен только сниппет. `processed_sources` возвращает их как previously processed. Основной prompt discourages повторный обход, а DDG fallback исключает эти URL.

Отсутствуют независимые признаки `discovered`, `fetched`, `extraction_complete`, `coverage_partial`, `stale`. Поэтому уже увиденная страница с ещё не прочитанным описанием скульптур может стать менее доступной для последующих поисков.

### F03. Второй проход заменяет первый — P0

В `_semantic_complete_discovery` при непустом `second_facts` выполняется `normalized_facts = second_facts`, а также заменяется extraction audit. Нет объединения неизменяемых наблюдений из двух проходов или явного протокола отзыва конкретного ошибочного утверждения.

Даже если первый проход дал полезные подтверждённые сведения, они исчезнут из результата, когда второй их не повторит. Это реальная механическая потеря модельного результата, не семантическая регулярка.

### F04. Модельный ключ может смешать несовместимые утверждения — P0

`model_fact_id` строится по `claim_key`. `merge_model_fact_inventory` при совпадающем ключе/ID заменяет текст последним, объединяет источники, берёт максимальную confidence и OR для selected/evidence_supported. `poi_research_facts` повторяет сходную семантику upsert по `(poi_key, claim_key)`.

Если модель присвоила один ключ двум вариантам даты, получится один последний текст с источниками обеих версий и уверенностью более уверенной из них. `conflict_scan_items` удаляет повторные `fact_id` ещё до детектора; модель может уже не увидеть обе версии.

Это не означает, что модель всегда выдаёт коллизии. Это означает, что одна ошибка её идентификатора приводит к необратимому смешению доказательств. Ключ должен помогать поиску похожих утверждений, но не разрешать автоматически переписывать их смысл.

### F05. Несколько доказательств с одной страницы перезаписываются — P0

В merge источники хранятся по URL, и более поздний source object заменяет предыдущий целиком. Аналогично обновляются supports в POI memory. Сохранение URL не означает сохранение всех фрагментов этого документа. Нужны адресные evidence edges с версией документа и span, а не один изменяемый объект на URL.

### F06. Наличие ссылки ещё не доказывает конкретный тезис — P0

`_search_web` связывает факт с известным URL и ставит `evidence_supported = bool(sources)`. В discovery fallback проверяется, что `source_ref` относится к найденному источнику с непустым support. Это полезная защита от выдуманной ссылки, но не отдельная проверка того, что фрагмент действительно подтверждает значение, человека или дату в данном факте.

Grounding support segment относится к сгенерированному ответу, и его нельзя безоговорочно выдавать за дословную цитату исходной страницы. Требуется различать discovery snippet, provider grounding annotation и проверенный span исходного документа.

Поиск официального источника уже запрошен в prompt. Однако текущий `official` — классификация найденного URL моделью с ограничениями, а не универсальное доказательство верности всех связанных тезисов. Важны компетенция источника именно по этому утверждению и его конкретный фрагмент.

### F07. Ограниченный снимок используется для полной перезаписи фактов — P0, условный риск

`_search_web` читает `facts ... LIMIT 80`, дополняет часть POI history, ждёт поиск/анализ, затем удаляет все facts истории и вставляет полученный inventory. Это не даёт гарантии сохранности фактов вне загруженного множества. POI rehydration может вернуть часть данных, но не является доказательством сохранности всего inventory.

Между чтением и записью есть async-паузы. Блокировка tools одной Live-сессии не защищает от другой сессии или параллельного изменения выбора/идентичности. Нужны операции над текущими версиями, а не замена состояния устаревшим ограниченным снимком.

В этом же пути старый `text` берётся как `str(row['text'])[:400]` и затем возвращается в постоянный inventory: транспортное сокращение не должно становиться новой сохранённой формой факта.

Не следует формулировать это как «каждый поиск теряет весь выбор»: prior_decisions и отдельные механизмы выбора существуют. Подтверждён дефект гарантии при ограничении/конкурентности, не все возможные последствия в каждой сессии.

### F08. Журнал конфликтов есть, но его состояние не равно безопасному допуску — P0

`analyze_fact_conflicts` логирует unavailable/missing detector, но возвращает `[]`. Это нельзя интерпретировать как «расхождений не обнаружено после полноценной проверки». Новые факты при наличии sources получают selected по умолчанию независимо от результата такой проверки.

`persist_fact_conflicts` обновляет evidence и счётчики, но не переоткрывает старое final_resolution при новых доказательствах; прежние тексты сторон также не обновляются этим upsert. Получается риск сочетания нового evidence со старым арбитражем.

`resolve_fact_conflict` сохраняет решение, но само по себе не меняет выбор и текст публикации. Разделение выбора и арбитража допустимо, **если отдельный допуск к использованию гарантированно учитывает версии и решение**. По прочитанным путям такая гарантия не установлена. Требуется отдельный негативный интеграционный тест до утверждения, что спорный факт не может попасть в публикацию.

Детектор ограничен первыми 80 уникальными ID; evidence сводится к коротким supports. В `detect_fact_conflicts` также есть срез сериализованного запроса. Счётчик n(n−1)/2 — число потенциальных пар, а не доказательство, что модель рассмотрела каждую.

### F09. Экономия контекста убирает именно то, что нужно для проверки — P1

В `_model_result` при semantic_completion из ответа Live удаляются `sources` и `fact_conflicts`; остаются краткие факты и количества. Другие projections обрезают тексты и число объектов. Это разумная попытка уменьшить повторную передачу данных, но без адресного `get_evidence`/pagination Мира не получает необходимую доказательную основу для самостоятельного арбитража.

В B устранён общий срез 36 000 символов из discovery prompt и evidence поставлен перед prior context. Но основной search prompt всё ещё ограничивает сериализованный topic context 12 000 символами; detector — свой JSON-пакет. Срез сериализации может удалить важные поля или оборвать структуру. Компактная проекция и постоянная запись должны быть разными объектами.

### F10. Остались разные правила приёмки для разных путей — P1

B улучшил discovery: missing/oversized key получает безопасный временный exact-text ключ; ошибочная confidence заменяется нулём; ведутся raw/accepted/rejected счётчики; предел текста повышен с 500 до 1 200. Эти исправления учтены и не описываются как отсутствующие.

Но основной Google-grounded `search_web` по-прежнему просит до 20 фактов и проверяет payload целиком: один malformed item может сорвать весь ответ. Fallback просит до 32 и отбрасывает избыточные элементы; наличие reason для over_batch_limit полезно, но не заменяет continuation. Live дополнительно ограничивает собственную нормализацию. Нет единого реестра кандидатов и терминального статуса каждого отклонения.

### F11. Исследование не является отдельной долговечной операцией — P1

Shared session_host запускает tool task через `asyncio.create_task`, а результаты кеширует на уровне сессии. Проверка cancelled ID перед выполнением не равна контролю stale-result при завершении. В `_search_web` commit не сверяет сохранённую generation идентичности с актуальной после ожидания.

Это кодовый риск завершения старого действия после смены объекта/закрытия сессии. Он не объявляется воспроизведённым инцидентом телефона. Нужно проверить interleavings в изолированном integration test: задача, отмена, reconnect, смена POI, поздний ответ, commit.

### F12. «Ищу факты» сейчас не означает выключенный микрофон — P1

Android `research_progress` меняет статус и данные интерфейса. `submitPcm` блокируется состоянием transport/playback gate, но не research progress. `turn_complete` может снова выставить «Слушаю». Следовательно, отдельного режима исследования с паузой записи здесь нет.

При этом неверно говорить, что любой шум обязательно отменяет backend search: уже запущенный tool может продолжить работу. Проблема — несогласованность диалога, UI и lifecycle операции, а не доказанная отмена каждого запроса.

P3 и P4 — наблюдения поведения/сохранённой защиты, а не дополнительные «найденные баги модели». Всего шесть выполненных проверок, четыре конкретных контрпримера; это не шесть пройденных продуктовых acceptance tests.

## 6. Документация Live: существенные выводы

## 7. To-be: один исследовательский процесс, явные роли

В существующем backend/SQLite добавить устойчивую операцию `research_run`, привязанную к actor/workspace, story, POI, версии подтверждения фото и цели автора. Не создавать новый микросервис, отдельную БД или вторую несвязанную беседу ради этой задачи.

Мира составляет/уточняет цель и план аспектов. Поисковый functional call возвращает discovery, а не окончательный вердикт. Research worker использует существующий явно выбранный LLM для обработки ограниченного доказательного пакета. Мира получает проверяемый результат, открытые вопросы и адресные фрагменты для арбитража. Делегирование текстовой модели должно быть задокументировано в модели возможностей и телеметрии; новая модель/платный маршрут не включаются неявно.

Состояния:

```text
planned → discovering → fetching → extracting → reconciling → verifying
        → completed | partial | failed | cancelled
```

`completed` означает завершение заявленного объёма исследования, а не «найдены все факты интернета». Наличие unresolved claims не скрывать: итоговый coverage/outcome отдельно сообщает, что исследовано и что пока нельзя использовать. Ожидание квоты/повторная попытка представлены как явные подстатусы, а не бесконечный «думаю».

Каждое принятое действие содержит `run_id`, `batch_id`, `source_version_id`/`chunk_id` при необходимости, idempotency key и expected revision. Результат сначала сохраняется, затем подтверждается модели. Повторный transport delivery не повторяет внешний поиск и не создаёт новые facts. Возобновление использует сохранённый checkpoint, а не реконструкцию из последних восьми реплик.

Для конкурентных действий нужны optimistic concurrency и граница семантической записи на run/POI. Не держать SQLite transaction во время сетевого/model await. Перед commit проверять идентичность, доступ, статус run и версии. Поздний ответ отменённой или устаревшей операции не присоединяется к новому объекту.

## 8. To-be: поиск и полноценное чтение

Модель планирует исследование по аспектам: строительство/авторство, назначение, изменения, именованные детали фасада, связанные люди, музейная история. Фото служит основанием спросить про фигуры/надписи, но не основанием придумать имена. Текущую идею нескольких различных запросов сохранить, заменив чисто prompt-based завершение явным coverage ledger.

Один найденный URL может быть discovered, но ещё не fetched; fetched, но обработан частично; полностью обработан для прежней цели, но нуждаться в новом аспекте/версии. Кешировать snapshot и учитывать его возраст/версию, а не запрещать страницу навсегда после сниппета.

При fetch сохранять нормализованный документ, исходный URL/redirect chain, timestamp, content hash, тип, ограничения чтения, заголовки/таблицы/подписи и доступные pointers к оригиналу. Redirect проверяется на каждом шаге; сохраняются ограничения адресов/SSRF и размера. Ошибка, PDF без поддержанного извлечения, недоступная JS-страница и лимит — разные явные причины неполного покрытия, не «источник обработан».

Извлечение main text не должно выкидывать подписи под иллюстрациями, таблицы и списки, где часто находятся короткие именованные сведения. Полный бинарный архив любого сайта не обязателен: достаточно воспроизводимого допустимого snapshot и адресной доказательной основы с политикой хранения/правами доступа.

### Чанки

Сначала выделить структуру документа, затем сформировать чанки по фактическому token budget. Небольшую статью можно передавать целиком. Для большой — разделять по разделам/абзацам, сверхдлинный абзац делить по предложениям, а крайний технический разрез снабжать соседним контекстом и явной возможностью дочитать.

У каждого чанка есть непересекающийся core span и дополнительный context overlap; совокупность core spans покрывает весь принятый релевантный текст. Сохранять manifest с индексами и границами. Заголовок раздела, единицы таблицы, подпись и антецедент местоимения могут переноситься как контекст. Одного фиксированного overlap недостаточно для всех зависимостей: модель может запросить соседний фрагмент.

Стартовый эксперимент — несколько тысяч токенов на пакет, с небольшим overlap и резервом под ответ; конкретные числа выбрать по precision/recall, latency и стоимости. Это не повод hardcode ограничение «первые шесть чанков». Все принятые чанки должны закончиться состоянием `extracted`, `no_claims`, `needs_context`, `failed`, `deferred` либо `cancelled`. Для complete не остаётся необработанных обязательных частей. Лимит результата означает continuation, не удаление лишних фактов.

## 9. To-be: факты, идентичность и доказательства

Нужно отделить пять сущностей: документ, наблюдение об утверждении в документе, нормализованное утверждение, связь между утверждениями и решение об использовании. Использовать/расширять существующие POI claims/evidence/contradiction сущности, согласовав legacy web-memory, а не создать ещё один параллельный источник истины.

Концептуальная запись наблюдения:

```json
{
  "observation_id": "server-generated",
  "run_id": "research-run",
  "poi_id": "confirmed-poi",
  "source_version_id": "document-version",
  "chunk_id": "chunk",
  "claim": {
    "subject": "object-or-component",
    "predicate": "depicts",
    "value": "named-person",
    "qualifiers": {"scope": "facade sculpture", "time": null},
    "display_text": "Один лаконичный тезис."
  },
  "evidence": [{"span_id": "span", "relation": "supports"}],
  "model_decision": {"model": "configured", "prompt_version": "version"},
  "status": "candidate"
}
```

Названия полей здесь проектные. Нельзя принуждать все исторические факты к узкому набору regex predicates; схема допускает неизвестные типы и модельную нормализацию. Слот «год строительства» полезен для поиска сопоставимых claims, но конкретные 1843 и 1853 — разные версии утверждения. Foundation/completion/restoration также нельзя объединять без учёта значения и стадии события.

Модель устанавливает `equivalent`, `different`, `contradicts`, `refines`, `temporal_sequence`, `scope_difference` с конкретными IDs и доказательствами. Только подтверждённая эквивалентность объединяет отображаемый тезис; оригинальные observations не удаляются. Даже при ошибочном existing_fact_id нельзя перезаписать исходный смысл и доказательства без следа.

Проверка span/URL/версии кодом доказывает существование текста. Отдельное модельное решение устанавливает, поддерживает ли этот текст именно тезис, полностью или частично. Нет подтверждения — сохранить candidate/needs_review, но не объявлять publishable. Сниппет может оказаться достаточным для простого тезиса, однако его ограничения должны быть видимы; при нехватке контекста читать страницу.

Одна страница может подтверждать несколько фактов несколькими passages. У одного факта может быть несколько sources и несколько spans одного source. Повторение одного материала на разных доменах относится к одной source family и не становится независимыми голосами.

Лаконичность — цель display layer. Слишком составной ответ модель разделяет. Технический предел не должен молча удалять содержательный candidate: требуется bounded repair/continuation и сохранённая причина. Повышение лимита до 1 200 символов само по себе не улучшает атомарность.

## 10. To-be: противоречия и доверие

Классификация конфликта должна учитывать объект/компонент, дату действия, роль человека, временной период, единицы и точность. Разные даты начала и окончания строительства не противоречат друг другу. Историческое и нынешнее название могут быть одновременно верными. Разные авторы проекта, скульптуры и реставрации не должны сливаться в «автор объекта».

Официальный источник имеет высокий приоритет по вопросам своей компетенции. Но это не правило «официальный всегда прав». Арбитру передаются полные релевантные фрагменты, связь издателя с объектом, версия/дата, первичность, независимость и точность формулировки. Число доменов и модельная self-confidence не являются вероятностью истины.

Журнал сохраняет обе версии, evidence references, тип расхождения, предложение detector, решение арбитра, объяснение, версии модели/prompt, историю переоткрытий. Решение привязано к digest набора утверждений и доказательств. Новое релевантное свидетельство делает прежнее решение stale; старый verdict остаётся в истории, а не приклеивается к новому evidence.

Допустимые результаты: предпочесть одну версию; разрешить обе с разными scopes; оставить неизвестным; отложить публикацию. Не нужно изобретать новый сложный интерфейс конфликта на первом этапе — важнее корректная модель и журнал. Мира может объяснить решение в текущем диалоге.

Отдельно хранить `owner_selected` и `eligibility`. Публикация использует только пересечение выбранных и допустимых фактов. Недоступный detector/arbiter — `unreviewed`, не пустое подтверждение отсутствия конфликтов. При изменении использованного утверждения проверять revision bundle текста/визуала: совпадение прежнего ID не означает, что прежний draft ещё действителен.

## 11. To-be: контекст и управление Мирой

Использовать двухуровневую память: durable evidence/manifest/решения в приложении и небольшой рабочий пакет в модели. В пакет входят цель автора, подтверждённый POI, текущие вопросы, адресные факты для данного сравнения, ссылки на документы и следующий шаг. Передавать все старые статьи при каждом tool result не нужно.

Не обрезать готовый JSON строковым срезом. Пагинация и отдельные поля `omitted_count`, `next_cursor`, `coverage_status` делают сокращение явным. Projections не возвращаются в постоянные поля факта как новая авторитетная версия. Компактизация резюме не удаляет исходные цитаты и выбранные пользователем сведения.

Сохранять checkpoint после подтверждённых пакетов; после resumption или новой provider session перечитывать актуальное состояние run. Применять явный tool behavior и подходящее scheduling, чтобы промежуточные результаты не вызывали лишнюю голосовую реплику и не перебивали текущую. Не внедрять новый completed user turn только ради передачи внутреннего evidence.

Отделить provider cancellation конкретного call от пользовательской отмены всего исследования. Во всех случаях поздний результат проходит проверку актуальности до применения. Статья и извлечённый текст — недоверенные данные: указания внутри источника не могут менять цель, вызывать публикацию или отменять системные правила.

## 12. To-be: временная пауза микрофона

Для первой надёжной реализации рекомендуется **явный режим фокуса исследования**, а не незаметное игнорирование речи. Это продуктовый выбор, а не ограничение, будто Live не умеет асинхронность.

После завершения запроса показать в переписке: «Ищу и сверяю факты. Микрофон временно выключен», прогресс по источникам/фрагментам и доступную кнопку отмены. Приостановить реальный capture, корректно завершить текущую audio activity, очистить неподанные PCM и установить input epoch. Не отправлять накопившийся старый звук после возобновления. Live transport не закрывать только ради mic pause.

На backend также учитывать input policy и generation run. `turn_complete` не завершает исследование и не включает слушание. Cancel отменяет дальнейшее применение результатов, но сохраняет уже подтверждённые записи; reconnect продолжает тот же run. Ошибка/квота/таймаут не оставляют вечную блокировку.

Возврат к слушанию возможен только согласно прежнему намерению пользователя и актуальному foreground/permission состоянию; не включать микрофон неожиданно после ухода в фон. Точный UI этой политики согласуется в этапе реализации. Full-duplex во время исследования можно оставить будущей опцией, когда управление параллельными действиями проверено; mute не заменяет корректность backend.

## 13. Приёмка: проверять полноту, а не наличие какого-либо результата

Контрольный пример — Королевские ворота и три фигуры. Ожидаемые именованные сущности из пользовательского сценария: Оттокар II Пшемысл, Фридрих I, герцог Альбрехт. Это перечень для построения gold fixture, а не самостоятельное доказательство расположения фигур. Позиции слева/в центре/справа добавлять только после проверки источников и точки зрения.

До теста зафиксировать реальные доступные документы, вручную прочитать относящиеся к ним passages и сформировать список атомарных gold facts. Не выдавать список экспонатов или имя в навигации сайта за доказательство того, кто изображён на фасаде. Одно соединённое предложение с тремя именами не заменяет три независимо выбираемых тезиса.

Нужны два разных запуска: широкий запрос об объекте без подсказки ответов и направленный запрос про фигуры. Передавать ожидаемые имена в model input широкого теста запрещено. Добавить несколько holdout POI, чтобы исправление не превратилось в специальное правило для ворот.

### Обязательные группы проверок

1. **Покрытие и recall.** Факты в конце текста после 9 000 символов, у границы чанков, в списке/таблице/подписи. Все core spans принятых документов обработаны; missing/deferred видны. Все три обязательных факта получены при наличии доступного проверенного evidence. Общую полноту оценивать по объявленному corpus, не по «всему интернету».
2. **Сохранность.** Результаты pass 1 не исчезают после pass 2; >80 facts не удаляются; same-key different-value не сливаются; несколько supports одного URL сохраняются; неоднозначная metadata идёт на repair/quarantine. Batch overflow имеет продолжение.
3. **Смысл и доверие.** Human review атомарности, attribution и entailment. Дедупликация перефразирования без false merge разных дат/ролей; обнаружение настоящего конфликта без смешения временных стадий; официальность не отменяет контрдоказательства; зеркала не считаются независимыми.
4. **Журнал и использование.** Новый evidence переоткрывает решение; detector unavailable не даёт publishable; selected disputed факт не проходит допуск; изменение факта инвалидирует связанные утверждения draft/visual согласно их revision bundle.
5. **Lifecycle.** Две сессии, смена POI, отмена, поздний ответ, повторная доставка, disconnect, provider compression/resumption, malformed response, quota wait. Проверка mic pause/restore/no stale PCM и доступности отмены. Сначала изолированные integration tests, затем разрешённый тест на устройстве.

Для количественной оценки определить precision, recall относительно corpus, dedup false-merge/false-split rate, contradiction precision/recall и долю фактов с точной доказательной привязкой. Цели вроде 90% recall допустимы как заранее объявленный benchmark на конкретной выборке, но не как измеренный этим аудитом результат. Для трёх обязательных сущностей при доступных источниках целевой gate — 3/3 с отдельными фактами и корректными ссылками.

Минимальный funnel: discovered URLs → fetched documents → planned/processed core spans → raw observations → repaired/quarantined → deduplicated claims → disputed/withheld → eligible → selected. Сохранять route/model/prompt version, причины потерь, реальное время, tokens и cost. Не считать количество потенциальных пар измеренным объёмом семантической проверки.

## 14. Порядок исправления

**Этап 1: прекращение потерь и ложного допуска.** Неизменяемые observations/evidence, безопасные идентичности, merge без удаления прошлых вариантов, delta persistence вместо capped snapshot replacement, раздельные review status и eligibility. Негативные tests на F03–F08.

**Этап 2: полнота и устойчивое выполнение.** research_run, source manifest, структурные чанки, continuation, модельная обработка каждого принятого пакета, явный partial, цель/аспекты, checkpoint и pause/cancel. Не подменять это очередным увеличением лимита.

**Этап 3: качество и эффективность.** Корпус с ручной разметкой, broad/targeted/holdout evaluation, настройка размеров пакетов/модельных ролей, query diversification и latency/cost. Текущие сильные механизмы WSS, защиты идентичности и выбора сохранить.

Поставка оценивается по прохождению доказательной цепочки и пользовательского сценария, не по числу новых документов, тестов или совпадению SHA соседнего сервиса. Следующий исполнитель должен сначала сверить delta после C и выполнить оставшиеся пункты, а не начинать аудит заново.
