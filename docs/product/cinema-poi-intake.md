# Кинолокации: прямое наполнение POI из ChatGPT

Поручение владельца: 03.11.2026. Workstream: [#333](https://github.com/onedayonemasterpiece/street-story/issues/333).
Технический статус сверять с последним комментарием issue: наличие исходников не означает deployment.

## Решение: MCP уже есть, новый сервер не нужен

Исполнитель семантики — текущий ChatGPT. Транспорт — уже подключённый **DevCoveer MCP**, операция `direct_ops_v2` / `project_action.run_tool`. Исполняется репозиторный `backend/tools/poi_intake.py`, а не модель Codex/OpenCode. CLI вызывает доменные функции Street Story в том же процессе и одной транзакции существующего Store. Это локальный owner-оператор, не отдельный сетевой сервис и не универсальная SQL-консоль.

Новый MCP endpoint, OAuth, OpenAI Tunnel, демон, очередь и второй POI-каталог не добавляются. Tunnel решил бы доставку запросов к новому серверу, но не отсутствующий доменный вход для веб-исследования. При нескольких десятках проходов существующий authenticated MCP достаточно удобен. Если впоследствии понадобится отдельный read/write коннектор для партнёра, эти же операции можно обернуть узким MCP с собственными правами; сейчас такой сервис не реализуется.

Кто замечает результат: владелец при повторной подготовке истории о доме и при решении о соавторстве VK. Частота: каждый исследовательский проход и каждая история с найденными кинофактами. Конкретный пробел: RKB-мост требует книжные evidence/page/region refs, а прямого пути для самостоятельного веб-исследователя не было. Корень: отсутствие доменного приёма внешнего исследования, не отсутствие ещё одного транспорта.

## Состав и повторное использование

| Компонент | Существующий механизм | Изменение / почему нужно |
|---|---|---|
| `poi_intake.py` (домен) | `ensure_poi_identity`, `persist_research_memory`, `hydrate_story_facts`, `confirmation_consistency_error` | Узкая оболочка проверок исходных чтений, OSM, явного решения исследователя и receipts. Не новый источник семантики. |
| CLI `backend/tools/poi_intake.py` | DevCoveer `run_tool`, установленный Python и Store | Один управляемый вход из чата без агента разработки. |
| `poi_intake_packets` | существующая `idempotency` | Неизменяемые результаты чтений/OSM/lookup/commit/checkpoint и продолжение. Факты здесь не становятся альтернативной памятью. |
| `persist_source_version(run_id=None)` | `source_versions`, `source_chunks` | Сохранить веб-источник без фиктивной темы, research run и задачи модели. Обычный путь с run_id не меняется. |
| `Store.open_existing` | `Store.connection/tx` | Не выполнять migrations/backfill при каждом чтении и не создать пустую БД при ошибочном пути. |
| cinema/attribution в `supports` | `merge_source_payloads`, каноническая POI-память и источники темы | Не терять film/scene/frame связи и вклад партнёра при повторном использовании. Новые таблицы films/POIs и сервисы не нужны для текущего объёма. |

Нет background workers, новых account tokens, публикационных действий и новых элементов Android UI. Существующая автоматическая исследовательская сессия обычной новой темы не отключается глобально; **этот оператор** её не создаёт.

## Точный протокол одного прохода

1. Прочитать эту инструкцию, текущие owner decisions и `--instructions`. Прочитать все страницы `readback(campaign)` до `next_cursor=null`. Взять последний checkpoint и следующий исходный материал, не начинать всю подборку заново.
2. Найти/прочитать VK, Дзен, Кинокарту и независимые материалы. Web/browser/VibePublish — поиск и получение оригинального контекста, не доказательство импорта. Для сохраняемых фактов получить **полное собственное чтение** через `read`; проходить `next_ordinal` до конца. Поисковый сниппет нельзя выдать за полную статью.
3. Найти OSM way здания через карту/поиск. Передать **реальный найденный** `way_id` в `osm`: оператор сам читает фиксированный OSM API, возвращает версию, теги, контур и адрес. Не присылать изготовленные моделью геометрии/OSM-ответы.
4. Выполнить `lookup` с полученным `osm_packet` и названием/адресом. Прочитать результаты и известные факты через `readback(poi_id)`. Похожее имя или соседняя точка не доказывают тождество. Явно выбрать реальный `poi_id` или `null` для нового объекта, объяснить идентичность и перечислить **все** рассмотренные `reviewed_candidate_ids`. При изменении реестра повторить lookup, не обходить конфликт новой догадкой.
5. Самому исследовать **всю историю здания** по обычным инструкциям: постройка, архитектор, владельцы, историческое и нынешнее использование, архитектурные детали, охранный статус, события и кино. Учреждение не равно зданию; история соседнего дома не заменяет пробел. Отзывы о сервисе не нужны; наблюдения о доме — только с оговоркой об источнике мнения.
6. Каждому атомарному утверждению дать исходные версии/собственные chunks и полную `NETWORK_SCHEMA` оценку. Один читатель — `verification_level=one_model`; это не независимое двойное подтверждение. Указывать точное неизменённое `existing_fact_id` только для действительно того же уже принятого факта. Не добавлять неподтверждённое в память «на потом».
7. Вызвать `commit` с небольшим пакетом проверенных фактов, типизированными кино-связями и coverage всех девяти аспектов. Запись атомарна. Проблемный факт исключить из пакета и описать как нерешённую задачу, а не ослаблять проверку остальных. Нет квоты обязательного числа фактов и нет требования выдумать недостающего архитектора.
8. Прочитать receipt по `packet_id` и POI по `poi_id`. Проверить конкретные `fact_ids`, поддерживающие источники и cinema/provenance. Доставка не равна просто успешному вызову команды. После потерянного ответа повторить **тот же** `request_key` и payload; другой payload с тем же ключом отклоняется.
9. Сохранить `checkpoint`: последний источник, следующие URL, неразрешённые вопросы, что искать дальше. Краткий итог прохода оставить в issue #333: прочитано / существующие POI / новые POI / факты / кино-связи / кадры / пробелы / receipt IDs. GitHub хранит координацию, продуктовая БД — факты и receipts.

`campaign`: `snyato-v-kaliningrade-2026`; каждый реальный проход имеет новый `pass_id`, например `pass-001`. `request_key` стабилен для одной операции, например `cinema-001-house1-source1-p0`. Чтения привязаны к проходу. Для повторного источника в новом проходе `read(source_packet,ordinal)` возвращает сохранённые неизменяемые chunks с новой собственной квитанцией, без повторного сетевого скачивания. Для обновления страницы — новый URL-read/new key; старая версия остаётся.

## Команды из существующего MCP

Не передавать секреты и не читать их в чат. Перед первым использованием проверить реальное systemd WorkingDirectory, source SHA и путь канонической БД. Не использовать случайную `data/street-story.sqlite3` в рабочем checkout.

Транспортная форма:

```json
{
  "project": "street-story",
  "plane": "project_action",
  "operation": "run_tool",
  "payload": {
    "tool": "bash_script",
    "path": "scripts/run_backend_python.sh",
    "args": [
      "/home/dev/.local/share/street-story/current/venv/bin/python",
      "/home/dev/.local/share/street-story/current/source/backend/tools/poi_intake.py",
      "--database", "<фактически проверенный абсолютный путь канонической БД>",
      "--request-part", "{...реальный JSON команды...}"
    ],
    "timeout_seconds": 45,
    "request_key": "<стабильный ключ MCP операции>"
  }
}
```

CLI сам выбирает backend из собственного установленного release, а не из случайного cwd. `--instructions` не требует БД. `--readback '{"campaign":"snyato-v-kaliningrade-2026"}'` читает историю; для следующих страниц добавить `after`. `--readback '{"poi_id":"<returned>"}'` читает факты/связи. `--readback '{"story_id":"<real story>"}'` возвращает вклад партнёра по **выбранным eligible фактам** темы.

MCP ограничивает аргумент 500 символами: большие JSON разбиваются на последовательные `--request-part` не длиннее 450 символов, без вставки разделителей. Это данные, не код. До 64 аргументов — практично сохранять по 1–3 факта в операции и столько операций в проходе, сколько нужно. Для больших пакетов допустим `--request-file` из управляемого artifact, максимум 256 KiB. Не писать пакеты с длинными цитатами/медиа в GitHub. Не ставить фиктивные host paths из локального ChatGPT sandbox.

CLI не создаёт БД и не выполняет установку схемы: до нормального deployment вернёт `intake_schema_not_installed_deploy_product_first`. Нельзя запускать неподтверждённую ветку против production Store. После deployment выполняется read-only readback и bounded acquisition, отдельно фиксируется live evidence.

## Адрес, идентичность и ограничения первой версии

`osm` v1 принимает **closed OSM building way** и его собственный адрес либо единственный однозначный адрес входа, являющегося узлом этого контура. Соседний адрес не подставляется. Отсутствующий/противоречивый адрес — явный отказ, не отсутствие дома. OSM подтверждает наблюдаемую карту, но не автоматически историческую личность здания.

Relations, внутренние адресные точки вне way nodes, утраченные здания и составные вокзальные комплексы в первой реализации **не принимаются автоматически**. Для них сохраняется checkpoint с точным пробелом; не создавать суррогатную точку. Их можно покрыть отдельным обоснованным расширением существующих геометрических механизмов после наблюдаемого случая.

HTTP-чтение сейчас поддерживает публичные HTML/text/JSON, без CAPTCHA/логинов, PDF/video decoder. Недоступный VK/Дзен читать разрешённым браузером/коннектором; пока у оператора нет подтверждённого import-native-read пути, такой материал остаётся discovery, а не имитацией HTTP200. Доступная атрибутированная статья может служить самостоятельным источником.

## Полное исследование, а не только кино

Coverage содержит ровно: construction, architect, ownership, historic_use, current_use, architecture, heritage, events, cinema. У каждого аспекта `found/not_found/not_applicable/pending` и содержательная заметка. Неполный объект допускает проверенные полезные факты сейчас, но не помечается исследованным целиком. `research_sufficient=true` несовместим с pending или remaining_gaps. Дата обращения не превращается в дату события; прежнее назначение не объявляется нынешним без основания. Противоречащие/неустановленные утверждения не проходят positive intake; перечислить конфликт в checkpoint с прочитанными источниками, не решать числом повторяющих сайтов.

## Структурные кино-связи

Связь хранится в доказательстве конкретного принятого факта: `film_key`, название/год фильма, источник сведений о фильме, `scene_key`, вид связи, описание сцены, экранная роль, отдельный год съёмки при наличии и кадры. Отдельные сцены одного фильма у одного дома не создают новый POI. Один дом в нескольких фильмах — несколько связей в той же памяти.

Различать exterior/interior/background/documented_location/miniature. Не приписывать зданию экранное разрушение макета. Не склеивать монтажные интерьеры разных зданий. Таймкод не обязателен; найденный таймкод требует конкретной серии/версии фильма. URL картинки должен быть реально извлечён из собственного источника; визуальное подтверждение ассоциации выполняет ChatGPT и оставляет reason/evidence_ref, не выдаёт это за независимую проверку фильма.

Факт о кино может быть принят по надёжному текстовому доказательству, пока кадр ещё не просмотрен или не разрешён к публикации. Это разные состояния.

## Происхождение и соавторство

У **каждой опоры факта**, **метаданных фильма** и **каждого кадра** отдельная `attribution`:

- `partner_original`: непосредственно прочитанный и установленный оригинал партнёра;
- `partner_credited`: прочитанный материал явно указывает исследование/кадр партнёра;
- `independent`: собственное независимое основание;
- `unknown`: происхождение не установлено, его нельзя автоматически считать независимым.

Партнёрские значения требуют `partner_id`, точный `credit_read_ref`, буквальную `credit_quote` и смысловое объяснение. Хештег, название коллекции, географическое совпадение и общий водяной знак сами по себе не доказывают авторство всех фактов страницы. VK и Дзен одного проекта — одна исследовательская линия, не два независимых подтверждения.

Технический partner slug — `snyato-v-kaliningrade`; настоящий VK community ID, исходный аватар и условия разрешения ещё требуют первичного подтверждения. Не придумывать numeric ID и не считать найденный сторонний профиль официальным автоматически.

Street Story получает metadata вместе с источниками через обычную POI hydration. В компактный голосовой контекст Миры добавлена `cinema_provenance`: названия/годы фильмов, виды связи и вклад партнёра именно в выбранные eligible факты. Инструкция Миры требует кратко сообщить владельцу об этом вкладе при подготовке поста, не приглашая соавтора автоматически. При выборе конкретных фактов `readback(story_id)` даёт список использованных опор, по которому владелец решает соавторство. Факт того, что у POI вообще есть партнёрский материал, не означает, что текущая публикация его использует. Снимок selected_facts в визуальной подготовке сохраняет исходные supports. Перед публикацией сверить **финальный выбранный/frozen набор**, а не старый список темы. Автоматического приглашения соавтора через VK API и нового UI здесь нет.

## Кадр + логотип «Снято в Калининграде» — согласованный следующий слой

Запроектировано, не выдаётся за готовый renderer:

1. Хранить оригинальный frame source/provider ref неизменным. По возможности использовать существующий media storage/provider ref, не коллекцию вечных локальных копий.
2. Убедиться, что кадр действительно относится к этому POI/фильму/сцене. Хранить результат просмотра и ссылки на доказательства, при наличии таймкод/версию.
3. Отдельно установить допустимость публикации кадра и использования подлинного логотипа. Исследовательский credit не является автоматическим разрешением.
4. Получить оригинальный avatar/logo из подтверждённого аккаунта или от партнёра; зафиксировать источник и согласованный branding preset. Не генерировать логотип по названию.
5. При выборе такого кадра в подготовке темы создавать **производную** версию детерминированным overlay, не imagegen-перерисовкой. Согласовать позицию/размер/отступы; не закрывать опознавательные детали, титры или чужую атрибуцию. Оригинал сохраняется отдельно.
6. Сохранять исходный frame ref, logo ref, preset version, derivative ref, POI/scene и выбранную публикацию. Отзыв/исправление разрешения не должен менять оригинал. Кадры не выбираются автоматически по близости координат.

В текущем intake все кадры получают `publication_status=not_cleared`. Это честный барьер до подтверждения договорённости и подключения производного медиа к существующему multiphoto flow. Исторические факты и film links от него не зависят.

## Пилот и критерий готовности

[Семь стартовых объектов](cinema-poi-seed.json) — discovery seeds, не принятые факты и не заранее известные OSM ID. Их партнёрское происхождение первоначально `unknown`.

Первый тестируемый вертикальный срез: прочитанный публичный источник + настоящий OSM way → lookup существующего реестра → пакет обычных и кинофактов → повтор той же операции не создаёт дублей → новая тема получает eligible факты и все supports → выбор одного кинофакта показывает точное происхождение. Запись не создаёт stories/jobs/publications.

Автотесты используют универсальные вымышленные здания и MockTransport, отдельный Store. Обязательные отрицательные проверки: неверная цитата, чужой проход, ложный credit, непрочитанный кадр, чужой физический субъект, конфликт, неполное чтение, stale lookup, другой payload под тем же ключом и недоступная БД. Fixture GREEN не равен Android/published/live acceptance.
