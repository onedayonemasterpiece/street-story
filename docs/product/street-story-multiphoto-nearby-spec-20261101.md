# ТЗ Street Story: несколько фотографий и локальный поиск снимков рядом

[Сводное исследование и результаты реальных поисков РКБ](../reports/street-story-product-research-20261101.md)

Дата исследования: 1 ноября 2026 года, Europe/Kaliningrad. Статус: техническое задание и исследование кода; реализация и измерения на телефоне не выполнялись.

## 1. Решение и пользовательский результат

Сделать локальный индекс фотографий телефона: координаты съёмки, время, ссылка на доступный оригинал. По точке исходной фотографии или выбранного POI приложение быстро показывает снимки рядом в сетке из трёх колонок; пользователь выбирает несколько, задаёт порядок и основной кадр. Этот шаг работает до получения фактов и без сети. На сервер попадают только выбранные фотографии.

Индексация начинает работу автоматически после предоставления доступа, подхватывает новые и изменённые файлы при открытии приложения и продолжается средствами Android в фоне. На главной странице видно, сколько доступных файлов обработано, сколько содержат координаты и сколько ещё осталось. Уже обработанная часть доступна для поиска до завершения полного прохода.

Утверждённый владельцем предел **8 относится к итоговым карточкам истории**, включая обложку и финал. Его нельзя автоматически превращать в ограничение количества исходных фотографий. Не наследовать существующее неиспользуемое `FUTURE_LIMIT = 9` как новое продуктовое решение.

Основание: [обсуждение сторителлинга](https://mira-projects.slack.com/archives/C0C7XQU60CX/p1793519503798709), [обсуждение историй рядом](https://mira-projects.slack.com/archives/C0C7XQU60CX/p1793520174996019), уточнение владельца об автоматической индексации и прогрессе в первом треде от 01.11.2026 10:10:58 EET.

### Три основания по devserver-simplicity

1. Кто замечает: автор истории при каждом подборе других ракурсов того же здания из накопленной галереи.
2. Решение владельца: автоматический индекс координат, даты/времени и файла; поиск рядом; сетка по три кадра; выбор нескольких; независимость от поиска фактов.
3. Корень: нынешняя модель истории, импорт, HTTP-контракт, визуал и публикация принимают один SOURCE. Одного изменения интерфейсного лимита недостаточно. Индекс галереи отсутствует в проверенном пути импорта.

## 3. Границы данных: три разные сущности

1. **Локальная фотография медиатеки.** Одна доступная запись MediaStore либо отдельно предоставленный document URI. Владелец оригинала — Android/provider; приложение хранит metadata, а не копию всей галереи.
2. **Фотография конкретной истории.** Выбранный человеком кадр со своим `photo_id`, порядком и оригиналом на сервере после загрузки. Один снимок может использоваться в разных историях. Удаление строки из локального индекса не удаляет уже созданную историю.
3. **Карточка истории.** Выходной кадр карусели: связан с выбранными фотографиями/фрагментами и проверенным текстом. Количество source-фото и количество карточек не обязаны совпадать.

Ни географическая близость снимков, ни одинаковая дата не доказывают, что на них один дом. Индекс предлагает кандидатов; выбор остаётся явным действием автора. Дополнительное фото не должно автоматически менять подтверждённый POI или переносить факты с соседнего объекта.

## 4. Локальное хранение координат и быстрый поиск

### 4.1 Минимальная модель

Расширить текущую SQLite БД. Логические таблицы ниже — проект структуры, а не выполненная миграция.

| Таблица | Основные поля | Назначение |
|---|---|---|
| `phone_photos` | локальный `id`; `volume_name`; `media_store_id`; `content_uri`; `latitude`, `longitude` как REAL nullable; `captured_at_ms` nullable; исходное EXIF-время/offset при наличии; `date_modified_s`; `generation_modified`; размер и MIME; результат чтения metadata | Индекс доступных фотографий. Для MediaStore уникальность в пределах тома и актуальной версии его каталога. Не использовать basename или абсолютный файловый путь как ID |
| `phone_photo_volumes` | `volume_name`; version MediaStore; завершённый generation checkpoint | Дельта обновлений, корректный сброс при перестройке MediaStore; технический checkpoint не должен изображать пожизненное разрешение доступа |
| `story_photos` | `photo_id`; `story_id`; optional local index ID; собственный source URI/upload ID/server asset; `position`; source coordinates/time | Упорядоченные выбранные фото истории. Основной кадр — один определённый элемент коллекции, а не независимая копия строки |

Индекс медиатеки содержит только разрешённые сведения. Не создавать историю для каждого найденного в телефоне файла. Не посылать координаты всей галереи в РКБ или backend. Точный путь Android (`/storage/...`) может измениться и не является главным способом открытия: использовать `ContentResolver` и `content://` URI.

Сохранять координаты WGS84 как числовые значения, с `NULL` при отсутствии. `0,0` не является заменой отсутствующего GPS; валидная координата 0 сама по себе тоже не должна отбрасываться. Время съёмки и время добавления файла — разные значения; если EXIF не содержит timezone, не приписывать ему UTC по предположению. Для отображения использовать доступную date taken и явно обозначать неизвестное время.

### 4.2 Рекомендуемый первый индекс

Начать с существующего SQLite и индексированного bounding box. Это убирает самый дорогой повторный путь: открытие и EXIF-чтение всей галереи на каждом поиске.

```sql
CREATE INDEX phone_photos_geo
ON phone_photos(latitude, longitude, id)
WHERE latitude IS NOT NULL AND longitude IS NOT NULL;

SELECT id, content_uri, latitude, longitude, captured_at_ms
FROM phone_photos
WHERE latitude BETWEEN :south AND :north
  AND longitude BETWEEN :west AND :east
  AND latitude IS NOT NULL AND longitude IS NOT NULL;
```

Затем вычислить расстояние до центра только для кандидатов и оставить `distance_m <= radius_m`, сортировать по расстоянию, затем времени и стабильному ID. Применять paging/число видимых элементов после проверки радиуса и сортировки; предварительное `LIMIT` по произвольному порядку потеряет ближайшие снимки. Вычисление расстояния можно выполнить штатным `Location.distanceBetween`, не запрашивая текущую геопозицию устройства.

Это **не полноценный двумерный spatial index**: составной B-tree эффективно ограничивает первый диапазон latitude, а longitude остаётся дополнительным фильтром. Поэтому обещать конкретную скорость для любой галереи без замеров нельзя. Следующий индекс выбирается по фактическому профилю, если bbox-проход перестаёт отвечать требованиям: пространственные ячейки с B-tree либо R-tree. Не поддерживать сразу несколько независимых механизмов поиска.

Почему не записать безоговорочно `CREATE VIRTUAL TABLE ... USING rtree`: R-tree требует включения расширения в сборку SQLite. Текущий проект использует платформенный SQLiteOpenHelper; проверенный официальный AOSP `dist/Android.bp` не задаёт `SQLITE_ENABLE_RTREE`. Это не проверка телефона владельца и не доказательство отсутствия расширения на каждом OEM, но достаточное основание не считать его гарантированной функцией Android. Подключение bundled SQLite ради R-tree — отдельная зависимость, которую следует обосновать измерением. [SQLite R-tree](https://sqlite.org/rtree.html), [официальный AOSP build](https://github.com/aosp-mirror/platform_external_sqlite/blob/38878b88206dbc25342587258cbe8723b3c19d50/dist/Android.bp), [правила использования B-tree](https://sqlite.org/optoverview.html).

Если выбран R-tree, хранить исходные Double/REAL координаты в основной таблице, а R-tree использовать лишь для отбора bbox; обычный `rtree` хранит 32-битные floats и округляет границы наружу. Для поиска использовать пересечение bbox, а окончательный радиус вычислять по исходным координатам. Поиск в одной geohash-ячейке тоже не эквивалентен поиску по радиусу: все пересекающиеся ячейки обязательны.

### 4.3 Центр, радиус и смысл расстояния

По умолчанию стартовать от **координаты исходного снимка**, пока объект не выбран. После выбора POI дать явный контекст «Фотографии рядом с объектом»; не переключать центр незаметно. Координата камеры и координата здания могут различаться на десятки метров: автор снимал здание с противоположной стороны улицы.

Радиус — UI-параметр в метрах, а не порог «это тот же объект». В первом варианте нужен компактный контрол радиуса и подпись текущего центра. Конкретные значения быстрого выбора подобрать на реальном корпусе; не объявлять произвольные 50/100/300 метров доказанными настройками. Фильтр по дате необязателен: по умолчанию ищем во всей доступной истории телефона, а не только за текущий день.

Bounding box должен гарантированно покрывать круг. Для Калининградской области достаточно обычной реализации с поправкой longitude на широту; общий helper должен корректно обрабатывать переход ±180° двумя диапазонами и широты у полюсов, чтобы будущие фотографии из путешествий не терялись. Не сравнивать разность градусов longitude с метрами и не сортировать по `abs(lat-lat0)+abs(lon-lon0)`.

## 5. Индексация: первый проход, изменения, фон

### 5.1 Один владелец работы

Создать один локальный worker индексации на существующем WorkManager, без сетевого ограничения. Он использует одну реализацию перечисления/metadata extraction/SQLite upsert. Запуск на старте, повтор на resume при изменении доступа и ContentObserver пока процесс активен должны сходиться к этой работе, не порождать параллельные обходы.

WorkManager обеспечивает выполнение в условиях ограничений Android. Требование «в фоне» выполнимо, но не означает непрерывную работу каждые несколько секунд после force-stop/в Doze. Периодический WorkManager имеет минимум 15 минут и может задерживаться. Частота обновления **видимого прогресса** раз в несколько секунд не должна становиться частотой полного сканирования галереи. [PeriodicWorkRequest](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest), [наблюдение progress](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/observe).

### 5.2 Первый проход

1. Перечислить доступные изображения через MediaStore на background dispatcher, получить URI/ID/том/время/размер/MIME. Не ограничивать проход первыми N или последними фотографиями.
2. Читать EXIF из stream/file descriptor оригинала с `setRequireOriginal`, где разрешено. Не использовать нынешнее `readPhotoBytes` для всех снимков: оно загружает целый файл, имеет upload-лимит 16 МиБ и относится к выбранному source, а не metadata-индексации.
3. Сохранять результаты пачками транзакций. Не держать транзакцию БД открытой во время EXIF I/O. Сохранять `NULL`/причину для файла без доступного GPS, чтобы не перечитывать его бесконечно в каждом проходе.
4. Показывать уже проиндексированные фотографии немедленно. Один повреждённый файл не отменяет полезные остальные.

MediaStore `LATITUDE`/`LONGITUDE` нельзя читать как готовый GPS-каталог: в Android API 29 они deprecated и возвращают null. Поэтому предварительное EXIF-чтение действительно требуется. [Официальный контракт ImageColumns](https://developer.android.com/reference/android/provider/MediaStore.Images.ImageColumns#LATITUDE).

### 5.3 Инкрементальный проход

На API 30+ использовать `MediaStore.getVersion(volume)` и generation markers. Сначала проверить version; при её смене заново согласовать каталог тома. При той же version выбирать добавленные/изменённые записи через generation, сохраняя high-watermark прохода только после фиксации всех его результатов. Не продвигать checkpoint мимо необработанных записей. Записи, изменённые после начала прохода, попадут в следующий.

Удаление не решается только `GENERATION_ADDED > checkpoint`: нужна сверка множества доступных ID или обработка удаления с последующим перечислением. При API 29 делать доступный полный metadata inventory и перечитывать новые/изменённые записи; более слабую надёжность `DATE_MODIFIED` по сравнению с generation честно учитывать. [MediaStore getGeneration](https://developer.android.com/reference/android/provider/MediaStore#getGeneration(android.content.Context,%20java.lang.String)), [описание обновлений](https://developer.android.com/training/data-storage/shared/media#detect-updates-to-media-files).

При возврате из settings/access reselection перечитать доступные MediaStore записи: cached metadata не даёт права показывать отозванный снимок. Отсутствие URI в успешном согласовании может означать удаление либо сокращение доступа — показывать только доступные результаты. Сбой запроса или неполный проход не является основанием удалить весь индекс. Отдельный story photo с уже загруженным asset сохраняется независимо от доступности галереи.

Облачный снимок, видимый только в системном picker, не обязательно является локальной MediaStore-записью. Индекс телефона не должен незаметно скачивать облачную медиатеку. Такой кадр добавляется вручную через существующий document/picker путь.

### 5.4 Прогресс на главной

Пример текста: «Фотографии: обработано 3 420 из 8 106 доступных · с координатами 2 487». При частичном доступе добавить «Выбранные фотографии». Счётчик обработанных включает проверенные файлы без GPS; число GPS-фотографий отображается отдельно.

Числа относятся к текущему доступному набору и могут измениться, если появились новые файлы или пользователь изменил доступ. Не использовать количество всех когда-либо увиденных URI как знаменатель. Никакого ожидания 100% перед открытием истории.

Использовать WorkInfo progress для текущего прохода и подсчёт строк индекса для уже накопленного результата; обновления UI объединять раз в несколько секунд. После завершения worker progress не является отдельным вечным источником истины — конечный результат читается из индекса. Не заводить второй scheduler или серверный статус ради этого индикатора.

## 6. Разрешения и работоспособность без полного доступа

| Android | Разрешение на перечисление чужих фото | Особенность |
|---|---|---|
| 10–12L / API 29–32 | `READ_EXTERNAL_STORAGE`, `maxSdkVersion=32` | Проект уже поддерживает эти версии; metadata-index не должен пользоваться API 30 без ветки совместимости |
| 13 / API 33 | `READ_MEDIA_IMAGES` | Видео не нужны, поэтому `READ_MEDIA_VIDEO` не запрашивать |
| 14+ / API 34+ | `READ_MEDIA_IMAGES` + поддержка `READ_MEDIA_VISUAL_USER_SELECTED` | Доступ может быть только к выбранным фотографиям, и набор меняется |
| 10+ для GPS оригинала | `ACCESS_MEDIA_LOCATION` | Отдельно от разрешения на файлы; отсутствие доступа не означает отсутствие GPS в самом оригинале |

Системное разрешение запрашивается при включении функции. Фоновой worker не инициирует диалоги. При отказе сохраняется возможность явно добавить несколько снимков через document/picker и работать с уже созданными историями. Индекс описывает только текущий разрешённый набор; в UI нет утверждения «в телефоне больше нет фотографий» на основании частичного доступа.

Текущая геолокация устройства этому сценарию не нужна. Сохраняется исходное решение manifest: не добавлять fine/coarse/background location ради EXIF. [Android partial photo access](https://developer.android.com/about/versions/14/changes/partial-photo-video-access), [MediaStore и EXIF](https://developer.android.com/training/data-storage/shared/media).

## 7. Выбор, показ и связь с историей

### 7.1 Экран подбора

- Сетка **3 колонки**, lazy thumbnails из `ContentResolver.loadThumbnail`; оригиналы читаются при открытии/добавлении, а не декодируются для всех ячеек.
- На ячейке: миниатюра, выбранный номер, дата; расстояние — когда есть координаты. Отдельное открытие полного кадра не сбрасывает выбор.
- Рядом с заголовком: центр и радиус. Список пополняется по мере индексации; выбранные элементы сохраняют свои номера и не прыгают при обновлении.
- Нижнее действие «Добавить N фото». Повторный вход показывает уже выбранные. Можно убрать, переставить, назначить основной кадр.
- Снимки без GPS доступны через явный picker/раздел без координат; они не попадают в результаты радиусного поиска. Дополнительный выбранный кадр без GPS может использоваться визуально при уже определённом центре/объекте истории. Для стартовой фотографии без координат требуется конкретная точка/POI, а не подстановка GPS телефона. Это осознанное изменение нынешнего `requireGps` для дополнительного кадра, не глобальное снятие проверки идентификации.
- Пустое состояние отличает «нет снимков в радиусе», «индексация ещё идёт», «нет разрешения» и «нет доступных GPS-метаданных» понятным текстом, без добавления новых серверных фаз.

[Официальные thumbnails](https://developer.android.com/training/data-storage/shared/media#load-file-thumbnails).

### 7.2 Экран истории

Показать полосу выбранных оригиналов с количеством, основным кадром и кнопкой добавления. Полноэкранный просмотр листает кадры и показывает номер. Не смешивать source-фотографии и итоговые карточки в одной неразличимой ленте: автор должен понимать, что будет опубликовано.

Добавление фотографии сохраняет уже принятые факты/текст/POI. Изменение набора визуальных источников меняет только зависимый визуал; оно не запускает повторное историческое исследование автоматически. Если автор действительно сменил объект, действует существующий механизм смены POI и его зависимостей.

### 7.3 Миграция и серверный контракт

Мигрировать каждую существующую историю в коллекцию из одного source-фото с сохранением старого upload ID, координат и ссылок. На переходном этапе старые одиночные wire-поля могут быть совместимой проекцией основного элемента; не оставлять два независимо редактируемых источника истины.

Продолжить существующие idempotency/outbox/jobs и durable source storage. Добавить операции attach/remove/reorder либо один атомарный update коллекции внутри текущего API; окончательный выбор должен соответствовать работающему стилю домена. Для каждого photo — стабильный ID и per-photo upload outcome; обрыв второго upload не создаёт вторую историю и не стирает первый.

Коллекцию и порядок передавать через Android Models/StoryStore/ApiClient/SyncWorker, backend parser/service/db/snapshot, source recovery, thumbnail/full preview, photo-format crop, visual context, Live image context и публикацию. Поиск всех consumers обязателен перед реализацией. Existing `photo_format` revision и source привязка должны стать привязкой к выбранному photo, чтобы crop одного кадра не применился к другому.

## 8. Приёмка и порядок реализации

### Первый самостоятельный выпуск: локальный индекс и подбор

Реализовать локальный индекс, автоматический проход, главный progress, поиск и трёхколоночный multiselect. Сохранение набора в истории входит в полезный результат этого этапа; конечная генерация карусели не должна быть блокером индексатора. Локальный подбор можно выпустить первым самостоятельным этапом, пока исходный визуальный маршрут использует явно выбранный основной кадр. Однако полная задача поддержки нескольких фото считается принятой только после сохранения и readback всей выбранной коллекции на backend, отображения после повторной синхронизации и корректной передачи выбранных исходников в визуал; локальный выбор сам по себе эту приёмку не заменяет.

Одна различающая проверка: на телефоне доступна галерея с фотографиями за разные даты, среди них три близких кадра и один дальний; после индексации, без сети, открыть историю и выбрать три близких кадра. После перезапуска сохраняются они же, тот же порядок и один `story_id`; новые изображения не теряются, выбор не ждёт фактов, поисковый запрос не открывает все оригиналы.

### Затем: полный поток нескольких SOURCE и карусель

Провести упорядоченную коллекцию через upload/server/readback/визуал и выходные cards; это изменение уже затрагивает shared integration и должно следовать [локальной S2S-политике](https://github.com/onedayonemasterpiece/codex-devcoveer-mcp/blob/main/docs/operations/local-service-connections.md). Сохранять исходные идемпотентные ключи публикации. Сценарий снятия/перестановки кадра после создания draft должен обновлять именно будущую публикацию по штатному пути, не повторять уже совершённый send.

### Необходимые контрпримеры

| Случай | Ожидаемый результат |
|---|---|
| Близкое фото другого здания | Предложено как кандидат; не присваивает POI автоматически |
| Камера через дорогу от POI | Предсказуемый центр/радиус; разница камеры и объекта видна |
| Файл без GPS / GPS скрыт permission | Не попадает в радиусный поиск; причины различаются; не хранится как 0,0 |
| Изменение EXIF / новый файл после запуска | Дельта обновляет строку и поиск, не создаёт копию |
| Удаление / отзыв доступа | Нет недоступной ячейки в результатах; сохранённая история не удалена |
| Изменился MediaStore version, ID переиспользован | Старый URI не связывается с новым снимком без согласования каталога |
| Force-stop / reboot / offline | Работу возобновляет Android в допустимое время; уже сохранённый индекс пригоден |
| Повреждённый файл | Остальной проход и выбор работают |
| Частично проиндексированная галерея | Показаны пригодные результаты и реальный прогресс |
| Одно фото в двух историях | Две истории независимы; удаление одной не удаляет файл пользователя |
| Повтор attach после сетевого обрыва | Один photo_id в исходной истории |
| Переставлены фото после создания визуала | Новый порядок не выдаётся за уже опубликованный; существующий send не дублируется |
| Дополнительный кадр без GPS | Визуальный материал сохранён; геоопора истории остаётся исходной |
| Снимки у границы bbox/±180° | Фильтр радиуса не теряет правильные точки |

### Измерения до заявления «быстро»

Снять на реальном целевом телефоне: число доступных фото и долю GPS; время первого полного прохода и дельты; bytes/database size; число EXIF-чтений на повторном запуске; число кандидатов bbox; query plan; время SQL+distance и время первого экрана с thumbnails; UI frame stalls и потребление памяти при одновременном Live. Предварительные продуктовые ориентиры для согласования: тёплый nearby-query до 100 мс и первые thumbnails до 500 мс; это цели, а не результаты исследования.

Проверять галерею владельца и отдельно плотный сценарий «много лет фотографий одного района», где слабость одноосного B-tree наиболее заметна. Только это измерение определяет необходимость spatial grid/R-tree; тест с десятком строк не подтверждает скорость. Полный поиск не должен зависеть от числа сохранённых историй Street Story.

## 9. Ограничения реализации и правила для исполнителя

Применить [devserver-simplicity](https://github.com/onedayonemasterpiece/codex-devcoveer-mcp/blob/main/skills/devserver-simplicity/SKILL.md). Для первой задачи нет поручения менять Live-транспорт, распознавание объектов, историческое ранжирование или импорт РКБ. Не создавать вторую очередь, серверный индекс всех личных фото, новый ORM или сервис поиска. Существующие SQLite/WorkManager/EXIF/URI и outbox остаются владельцами своих обязанностей.

Убрать одиночные `.single()`/single-file barriers только в согласованно обновлённом пути. Их нынешняя защитная ценность известна: они не позволяют молча потерять дополнительные кадры при однокадровом backend. Нельзя просто удалить проверки прежде коллекционного server-контракта. Не наследовать лимиты «9 source» и «8 output» как один параметр.

Добавленные элементы должны быть оправданы в PR: локальная metadata-таблица — повторный поиск по галерее; индекс координат — отбор кандидатов без EXIF; checkpoint — изменения без полного чтения; story photo rows — несколько выбранных кадров; отдельный локальный worker — offline обработка, которую сетевой SyncWorker не исполняет. В описании PR привести таблицу §6 skill, net production lines и фактическое покрытие проверок. Жёсткий бюджет строк владельцем не установлен; исполнитель должен дать фактический объём, не выдумывать ограничения.

## 10. Что пока не доказано

На телефоне не измерены объём галереи, разрешения, доля доступного GPS, время EXIF-индексации, наличие R-tree и скорость выбранного индекса. Не проверена актуальная установленная APK. Условия облачных provider URI различаются. Нынешний production runtime не осматривался в этой части исследования. Все требования выше — предлагаемый контракт доработки, а не заявление о готовой функции.
