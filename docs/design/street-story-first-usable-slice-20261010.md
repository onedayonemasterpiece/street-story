## 1. Результат и границы

Backend сохранил фотографию и принял работу → приложение можно закрыть → сервер устанавливает точный физический объект автоматически либо сохраняет конкретный вопрос автору → получает собственные пригодные факты со всеми сохранёнными источниками → reopen через обычный API показывает результат и позволяет выбрать/использовать факты.

Не локальный выбор файла, а durable acknowledgement обозначает начало этого обещания. Время возвращения через 10–20 минут не продлевает бюджет и не оправдывает задержку первого результата. При неопределённости/ограничении показываются честное состояние и уже пригодный partial; число фактов не заменяет качество. Действующая цель конкретного запуска, включая согласованный минимум, сохраняется.

В срез входят обычный выбор и использование фактов в тексте. Голос, генерация визуала, полнота всех типов городских фото, массовая очистка и будущий RKB ingestion не расширяют его обязательную цепочку. Их существующие контракты не отменяются. Дополнительное исследование не удерживает редактор и может завершиться полезным partial.

## 4. Один смысловой проход → одна фиксация

`HeadlessFacts._prepare_units` уже получает frozen source portions, подтверждённую identity и известный inventory. `_extract_unit` → `research_adapter.extract_fact_page/_extract_fact_route` выполняет **одну** ограниченную смысловую операцию чтения, выделения тезисов, нормализации, оценки собственной опоры и отношений. Переиспользовать существующие смыслы fact/review contract и source/quote IDs; не создавать ещё один паспорт с обязательными флагами. Источник называет утверждение, модель решает его support/scope; код не угадывает историческую истину.

Результат содержит по пунктам тезис, его собственные evidence references и достаточное семантическое решение, включая локальный неподдержанный/спорный исход. Host, а не модель, связывает его с adapter/prompt contract version и frozen IDs. Это не нынешний raw extractor с автоматически выставленным `supported`. Старый candidate-only checkpoint идёт в адресный assessment, а не immediate admission; model self-report «qualified» не меняет контракт. Не поддерживающий новый результат старый маршрут не допускается как эквивалентный однопроходный путь без проверки его контракта.

На общей provider boundary нормализовать только доказанно эквивалентную форму: optional null/omission, однозначный singleton адрес. Сохранить raw и каноническое представление; fresh и retained readback используют тот же контракт. Неверный ID, другая source version, неоднозначность, конфликт или пропущенное смысловое решение не ремонтируются догадкой. [Schema/commit расхождение](https://github.com/onedayonemasterpiece/street-story/blob/e40dba990ff56a989811cdbd43825e146835fa45/backend/street_story/review_packets.py#L485-L501).

`_commit_unit` вызывает общий admission helper, выделенный из существующей `_finalize_fact_review`, а не делает ещё один inference. Одна транзакция согласованно сохраняет observation/evidence, accepted claim/basis, POI proof и story projection. Внутри нет network calls. Непригодный пункт локален, если независимость соседних пунктов и cross-item relations однозначны; иначе сохраняется минимальная неразрешённая группа. Готовые факты доступны сразу после commit.

`HeadlessFactReviewer._run_one` остаётся для действительно неоценённого legacy, недостающего контекста, конфликта/repair по затронутому scope. Он **не планируется по умолчанию** после уже принятого результата нового source-reading прохода. Имя класса или старый вызов scheduler не должны тайно возвращать обязательный extract→review.

## 5. Принятая опора, POI и клиент

Принятое решение адресует конкретную claim revision, канонический физический subject/scope и использованные source revisions/passages. Растущий inventory digest нужен для research replay/staleness, но не является lifetime этого решения. Generation исходной операции сохраняется в provenance; warm-проекция в другую историю проверяет её собственные current fences и тот же физический субъект, не требует совпадения номеров generation двух историй. Новая corroborating observation добавляет поддержку, не отзывает прежний basis. Закрытый собственный passage не пропадает, когда URL временно offline: живой re-fetch не условие чтения/повторного использования. Смысловая смена, реальный конфликт либо непригодность использованной опоры локально изменяют статус; эти решения проходят тот же commit.

Одновременно убрать конкурирующие writes/reset: all-observation digest reset в `fact_ledger.persist`, reset из `review_packets.read`, pending-packet/full-scan veto в `refresh_review_status`, прямой Live status/unselect и POI whole-source snapshot rejudgment. `_finalize_fact_review` сохраняет idempotency/source/owner/lease checks, но не требует глобального coverage/exhaustion для отдельного supported item; unrelated редакторское поле не меняет semantic dependency. Подготовка review и чтение inventory не владеют eligibility. Не выпускать новый admission рядом с несовместимым старым writer. [Ledger reset](https://github.com/onedayonemasterpiece/street-story/blob/e40dba990ff56a989811cdbd43825e146835fa45/backend/street_story/fact_ledger.py#L475-L507), [pending veto](https://github.com/onedayonemasterpiece/street-story/blob/e40dba990ff56a989811cdbd43825e146835fa45/backend/street_story/fact_ledger.py#L866-L874), [Live writes](https://github.com/onedayonemasterpiece/street-story/blob/e40dba990ff56a989811cdbd43825e146835fa45/backend/street_story/live.py#L4331-L4365).

Одна pure passage-preserving union обслуживает `model_facts` in-batch и durable evidence merge; same URL — одна отображаемая ссылка, не потеря второго passage. Учитывать существующий import ledger→model_facts, без цикла. `sync_poi_review_from_story` переносит явный receipt, `hydrate_story_facts` проецирует его без synthetic `poi_memory_reuse` scan как нового пропуска и без обратного повторного sync. Legacy backfills не конкурируют с новым writer. История хранит свой выбор/черновик; cold DB не пополняет installed POI автоматически.

REST/reopen возвращает сохранённую identity, пригодные и pending факты, job outcome и текущий owner selection. Для среза достаточно существующего REST-readback/polling; новая WSS-доставка фактов не требуется и не объявляется реализованной. Убрать `_execute_tool`/`get_facts` guard, требующий новое research observation для чтения старых eligible; не возвращать огромный setup context. Один факт показывает все доступные источники с понятными названиями, открывающими оригинал; наличие source URL не заменяет support, необработанный или противоречащий источник не представляется принятой поддержкой. Explicit research Stop идёт независимо от неисправной voice upload; остановка микрофона не равна Stop исследования.

## 6. Совместимость и порядок изменений

1. На сохранённых закрытых примерах согласовать один semantic-result/admission контракт, чистое объединение evidence и exact-subject commit. Изменить связанные writers вместе. Проверить нормализуемые формы и отрицательные смысловые случаи; новый normal path не считается доказанно равным старому до этой проверки.
2. Связать intake и существующие runs с durable job, затем удалить session ownership. Подключить новый semantic result к общему commit без второго вызова; затем story/POI/warm и REST читают одну принятую revision. Не вводить двойной active writer или shadow model sends.
3. Согласовать минимальный клиентский readback/control и позднюю подсказку; проверить сквозной срез ниже. Нормативные target-строки и tests-as-contract обновляются с поведением. Отдельная экология/массовая миграция не блокирует результат.

**Выбранное хранение:** два nullable поля `accepted_revision_digest` и `accepted_basis_json` в существующей `fact_assertions`; существующий `poi_research_assertions.review_proof_json` хранит версионированный envelope того же решения. Текущий inventory `revision_digest` не переименовывается в accepted proof. Basis заполняет host из claim/subject, выбранных immutable evidence и semantic operation/relations; модель не переписывает hashes/generation ради сертификата. Никаких новых canonical таблиц.

**Устойчивый POI basis.** В той же SQLite admission-транзакции существующий `persist_research_memory` сохраняет immutable `poi_research_observations` и возвращает новый mapping story `evidence_id` → canonical `observation_id` + selected support/span digest. `source_version_id` и offsets сохраняются, когда имеются, и не становятся новым барьером для совместимого legacy. В `observation.sources_json` сохраняются точные выбранные supports с текстом passage и имеющейся version/span metadata; POI envelope адресует этот observation/support, не временный story/chunk ID и не копию полного frozen packet. `source_versions` уже глобальная таблица; canonical support сохраняет пригодный passage и после разрешённого удаления story/chunk, а retention версий учитывает canonical references. Нельзя расширять `access_scope`/ACL при таком переносе. Hydration создаёт новые story-local evidence IDs из canonical supports и сохраняет исходный admission, проверяя доступ и текущие story fences. External RKB/network не участвует в условии SQLite commit. Legacy без точного span остаётся opaque legacy receipt, без придуманных offsets/version. [Существующее сохранение POI](https://github.com/onedayonemasterpiece/street-story/blob/e40dba990ff56a989811cdbd43825e146835fa45/backend/street_story/poi_memory.py#L870-L890).

**Dual-read, single-write.** Новый envelope читается как новая admitted revision. Без него сохраняется исходный legacy accepted contract/receipt и его provenance, без обязательной повторной модели или выдуманной новой proof. Старые pending/withheld не повышаются автоматически; известный конфликт или отсутствующий/отозванный basis не игнорируется ради совместимости. Сохранить старые receipts, command IDs и readers; не делать общий rereview памяти или destructive backfill. При rollback новые записи не должны быть молча неверно истолкованы старым reader: совместимость writer проверить до переключения, иначе откатывать лишь на совместимый кандидат, без стирания данных.

## 7. Несколько различающих сценариев

- Accepted upload → закрытие клиента **до identity** → объект/собственные пригодные факты либо честное needs-user → reopen, выбор и текст сохранены. Pending local upload не имитирует принятую задачу.
- Реальный façade match с `verify_binding` не создаёт соседний POI; корректный body-bound ответ проходит. Вопрос автору переживает истёкшую старую волну: содержательная подсказка продолжает поиск, неверная подсказка не становится фактом.
- Один frozen source → один semantic call → общий commit → usable facts; null/omission и singleton не вызывают новый provider send. Другой источник/subject, неподдержанный тезис и конфликт остаются локально withheld.
- Уже принят A; приходит поддержка A и спорный B → A/выбор/текст сохранены. Истинный конфликт A меняет только затронутую revision. Два passages одного URL доходят до POI и одной UI-ссылки.
- Same-session старые eligible + новая незавершённая волна → editor читает/выбирает их без нового research. Warm-история того же подтверждённого тела получает совместимый basis без повторной extraction; canonical passage остаётся доступным и без исходного story/chunk, без расширения ACL.
- Stop/новая generation/UNKNOWN/перезапуск: старый send не дублируется, активный lease не крадётся, поздний ответ не применяется вне разрешённого scope. Недоступная voice upload не удерживает независимый Stop.

Сначала разрешённые проверки сохранённых данных, затем адресные реальные вызовы только изменённого пути и нужного разнообразного входа. Не полный корпус после каждого commit; штатный bounded retry временной сети и обоснованная оценка стохастики допустимы, гонка неизменного случая до PASS — нет. Остановленная серия не возобновляется этим дизайном. Готовность среза — сохранённый полезный результат вместе с автономностью и защитами, а не число тестов или несколько eligible сами по себе.

## 8. Сквозное исполнение и доказательство результата

[Программа и методика испытаний](../testing/street-story-product-acceptance-20261010.md) закрепляет неизменённый корпус и исполняемый протокол итоговой проверки.

Основной вход и режим непрерывного исполнения заданы в [постановке](../prompts/street-story-universal-product-recovery-20261010.md). Этот дизайн детализирует ядро, не завершает общее поручение на промежуточном результате: после него интегратор продолжает разрешённые исправления и финальную проверку полного продукта. Голос, замысел/черновик, визуал и reopen проверяются по общим критическим требованиям; внешняя публикация не подразумевается. После адресных проверок обязательна реальная приёмка всего согласованного корпуса на стабильном кандидате: правильный физический объект и собственные пригодные факты по каждому входу, независимая проверка identity, отдельные auto/assisted и cold/warm результаты, времена и явные failures/not-run. Исправимые провалы устраняются до завершения задачи; при настоящем блокере сохраняется точное ограничение. Все последующие P2 не являются условием пригодности этого среза.
