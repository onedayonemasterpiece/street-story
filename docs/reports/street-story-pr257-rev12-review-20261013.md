## 4. Дефекты кода PR

### 4.1 P0 — блокируют факты

**R1. Маршрут чтения для точного выбора закреплён за одной моделью строковым литералом.**
- Код: `research_adapter.py:1086–1101` (`new_fact_routes`) оставляет только маршрут с `model_id == 'mimo-v2.6-flash-free'`, причём только если это основной клиент. Та же функция применяется к review (`headless_fact_review.py`).
- Последствия:
  1. Резервного маршрута нет: отказ MiMo означает ноль фактов.
  2. Если переключить модель через `STREET_STORY_RESEARCH_MODEL` (`config.py:175`), как предполагает rev12 (Muse Spark), список маршрутов станет пустым. Тогда `research_adapter.py:1298` бросает `research_fact_pool_unverified` с повтором через 300 с — бесконечно, пока история в состоянии `researching` и без видимой ошибки.
- Исправление: упорядоченный список маршрутов для точного пути из конфигурации — основной плюс один квалифицированный резервный. Пустой список сразу даёт видимый терминальный статус `reader_unavailable` с причиной.

**R2. Таймаут вызова меньше реальной задержки модели, а UNKNOWN нельзя повторять.**
- Код: `opencode_research.py:35` (`timeout_seconds = 120`). Наблюдаемая задержка завершённых вызовов MiMo на странице — от 13 с до 65 с, а контрольный вызов шёл 444 с; три параллельных вызова на 102 и 131 ушли в UNKNOWN около 120 с.
- Последствие: каждая такая единица до 5 минут ждёт чтения результата, повторить её нельзя. Ориентир «3 факта за 5 минут» недостижим конструктивно.
- Исправление: не поднимать таймаут вслепую. Выбрать маршрут чтения по измеренной задержке на сохранённых страницах (§6, шаг 2). Таймаут точного пути задать по p90 выбранной модели.

**R3. Привязка к объекту проверяется на уровне страницы.**
- Код: `source_assessment.py:87–95` в этом PR требует: «если связь с физическим объектом отсутствует или не ясна — `source_matches_poi=false` и `facts=[]`». При этом `headless_facts.py` (около строки 1263) отбрасывает все факты страницы.
- Последствие: обзорная статья о нескольких зданиях (tvoybro о старейших домах города, где есть раздел про Житомирскую, 22–24) теряется целиком. На 129 оба завершённых чтения дали `false`.
- Исправление: оценивать объект **по каждому утверждению**. Добавить в строку факта поле `subject_scope` со значениями `selected_building` / `complex_or_site` / `other`. Сохранять только `selected_building`, а `complex_or_site` — с явной меткой. Признак страницы оставить как сведение, а не как фильтр. Защита от соседнего дома сохраняется, но работает точечно.

**R4. Два последовательных фильтра «о нашем ли доме» на пути к факту.**
- Код: строгий контракт выбора URL `owner-exact-selected-urls-v1` (`opencode_research.py:829–844`, `research_adapter.py:806–861`) — модель поиска должна вернуть итоговый JSON с отобранными URL. Без него результат — `selection_unavailable`, и исследование заканчивается с `resource_blocked` (`headless_facts.py`, ветка `source_selection_unavailable`).
- Последствие: 122 — два поиска и ноль источников; 105 — поиск в UNKNOWN 185 с. Найденные ссылки из вывода websearch, которые уже есть в receipt (`discovered_sources`), не читаются.
- Исправление: если итоговый JSON выбора недоступен, читать первые N (например, 5) URL из `discovered_sources`. Защиту обеспечивает проверка объекта при чтении (R3), выбор URL — только подсказка порядка.

### 4.2 P1 — искажают результат и измерения

**R5. «Свежая» история получает старые факты.**
- Код: `place_selection.py:387` вызывает `hydrate_story_facts` при подтверждении; `headless_facts.py:704` и `:838` берут URL из `poi_research_sources` до поиска.
- Последствие: на dev-БД, где уже есть результаты по 102, rev12-тест «без подмешивания старых результатов» окажется ложноположительным.
- Исправление: в продукте поведение верное и его нужно сохранить. Для приёмки — новый `DATA_DIR` и проверка в отчёте: `poi_reused_fact_count == 0`, backend поиска не `poi_memory`.

**R6. Ночь потрачена на правила датирования, которые утяжелили чтение.**
- Код: к правилам чтения добавлено около 1,1 тыс. символов (`opencode_research.py:904–920`, `gigachat_research.py:290–304`). Вместе со схемой ответа и прежними правилами модель получает несколько тысяч символов инструкций на каждую страницу.
- Последствие: семантический эффект не доказан, а контроль MiMo закончился исчерпанием вывода.
- Исправление: до появления трёх фактов на двух объектах не добавлять правил. На сохранённой странице 102 измерить исход с блоком датирования и без него: два вызова на модель.

**R7. Три входа в «объект определён» ведут к разным путям фактов.**
- Код: `_owner_exact_fact_scope` (`research_adapter.py:1078–1084`) истинно только для `selection_basis == 'owner_exact'`.
  - Группа, сузившаяся до одного дома (`automatic_within_owner_group`), получает обычные маршруты и обычный поиск. Факты ставит периодический планировщик, а не прямой вызов (`owner_group_identity.py:177`).
  - Голосовое подтверждение (`owner_live`, `place_selection.py:375`) тоже идёт обычным путём.
- Исправление: один предикат «объект подтверждён для фактов» для всех трёх входов и одна прямая постановка задачи.

**R8. Город обязателен в диалоге точного выбора.**
- Код: `PlaceMapPanel.kt:380–420`. Если в тегах контура нет `addr:city` (в OSM это частая ситуация), открывается диалог с обязательным полем «Город».
- Исправление: сервер заполняет город сам — из `addr:city` соседних объектов того же снимка, иначе одним запросом Nominatim reverse, который уже есть в `OSMClient`. Диалог только для пустого адреса и названия.

**R9. Подтверждение ссылается на последний снимок карты, а выбор мог быть сделан на предыдущем.**
- Код: Android перезапрашивает карту при сдвиге больше 120 м (`PlaceMapPanel.kt:202`). Сервер хранит 3 последних снимка (`place_selection.py:169`). Подтверждение отправляет `snapshot_id` текущего снимка (`PlaceMapPanel.kt:442`), а сервер ищет кандидатов только в нём.
- Последствие: если выбранное здание или член группы набраны до сдвига, подтверждение получает 409 `place_candidate_unknown` или `place_snapshot_stale`. Группа из зданий разных снимков не подтверждается вообще.
- Исправление: сервер принимает кандидата из любого сохранённого снимка того же scope; клиент передаёт `snapshot_id` снимка, в котором выбран каждый ID.

### 4.3 P2

- **R10.** `_story_repr` возвращает `place_map` (до 250 контуров с геометрией) в каждой истории, в том числе в списке (`service.py:436`). Это раздувает синхронизацию. Отдавать карту только через `GET /place-map`, в истории — `snapshot_id`.
- **R11.** CI backend: 5 известных падений (`3252 passed / 5 failed`), статус workflow FAILURE. Зафиксировать список как базовый либо исправить, чтобы новые падения были видны.

Backend загружает каждый URL существующим reader, находит цитату в замороженном тексте (после нормализации пробелов) и сохраняет факт через существующий ledger; не найденная цитата — факт отброшен с записью причины. Это изменение разрешений — без решения владельца не включать.
> 8. **После фактов, по порядку:** R7 (один путь фактов для точного выбора, группы и голоса); R8 (город автоматически); R9 (снимки карты); группа; формат 4:5; Android → backend на реальном телефоне.
>
> Перечитывай §8 при смене этапа, без периодического опроса. Отчёт — только при новом результате или блокере.

## 7. Чего не делать

- Не запускать агентский путь с чтением страниц без решения владельца по разрешениям.
- Не менять модель через переменную окружения, пока не исправлен R1.
- Не поднимать таймаут или число повторов, чтобы «дождаться» модели.
- Не добавлять правила в prompt чтения до первых трёх фактов на двух объектах.
- Не повторять полный корпус и не проводить турнир моделей: замер на сохранённых страницах (шаг 2) ограничен 2 моделями × 4 страницами.
- Не засчитывать гидрированные из памяти POI факты как свежий результат.

## 8. Решения владельца

1. Разрешить ли агенту исследования читать веб-страницы самостоятельно (webfetch в продуктовой OpenCode-сессии) — нужно только при неуспехе шагов 1–6.
2. Допустима ли проверка объекта по утверждению (R3) вместо фильтра по странице. Рекомендация — да: защита от соседнего дома сохраняется точечно.
