## 4. Дефекты кода PR

### 4.1 P0 — блокируют факты

**R1. Нет пула: маршрут чтения закреплён за одной моделью строковым литералом.**
- Требование владельца: надёжность «как швейцарские часы» — несколько независимых провайдеров и моделей; отказ одного или нескольких ресурсов не останавливает сценарий; работа без лимитов Codex.
- Код:
  - `new_fact_routes` (`research_adapter.py:1086–1101`) оставляет только маршрут с `model_id == 'mimo-v2.6-flash-free'`, причём только если это основной клиент; та же функция применяется к review.
  - Пул и до PR был узким: `_fact_pool_routes` строит максимум 4 маршрута — Live, GigaChat, одна модель OpenCode из конфигурации и литерал `nemotron-3-ultra-free` на том же endpoint (одна квота Zen).
- Последствия:
  1. Отказ MiMo означает ноль фактов.
  2. Если переключить модель через `STREET_STORY_RESEARCH_MODEL` (`config.py:175`), список станет пустым, и `research_adapter.py:1298` будет бесконечно повторять `research_fact_pool_unverified` раз в 300 с без видимой ошибки.
- Исправление: пул `(provider, model, endpoint)` из конфигурации, не менее двух независимых провайдеров; выбор случайный или по здоровью; переход на другой маршрут при отказе; пустой пул — видимый статус (§6).

**R2. Таймаут вызова меньше реальной задержки модели, а UNKNOWN нельзя повторять.**
- Код: `opencode_research.py:35` (`timeout_seconds = 120`). Наблюдаемая задержка завершённых вызовов MiMo на странице — от 13 с до 65 с, а контрольный вызов шёл 444 с; три параллельных вызова на 102 и 131 ушли в UNKNOWN около 120 с.
- Последствие: каждая такая единица до 5 минут ждёт чтения результата, повторить её нельзя. Ориентир «3 факта за 5 минут» недостижим конструктивно.
- Исправление: не поднимать таймаут вслепую. Таймаут — свойство маршрута по его измеренной задержке; при UNKNOWN независимая работа сразу идёт на другой маршрут пула (R1, §6). Агентным задачам долгая работа разрешена, но результат не ждёт одного медленного агента.

**R3. Привязка к объекту проверяется на уровне страницы.**
- Код: `source_assessment.py:87–95` в этом PR требует: «если связь с физическим объектом отсутствует или не ясна — `source_matches_poi=false` и `facts=[]`». При этом `headless_facts.py` (около строки 1263) отбрасывает все факты страницы.
- Последствие: обзорная статья о нескольких зданиях (tvoybro о старейших домах города, где есть раздел про Житомирскую, 22–24) теряется целиком. На 129 оба завершённых чтения дали `false`.
- Исправление: оценивать объект **по каждому утверждению**. Добавить в строку факта поле `subject_scope` со значениями `selected_building` / `complex_or_site` / `other`. Сохранять только `selected_building`, а `complex_or_site` — с явной меткой. Признак страницы оставить как сведение, а не как фильтр. Защита от соседнего дома сохраняется, но работает точечно.

**R4. Два последовательных фильтра «о нашем ли доме» на пути к факту.**
- Код: строгий контракт выбора URL `owner-exact-selected-urls-v1` (`opencode_research.py:829–844`, `research_adapter.py:806–861`) — модель поиска должна вернуть итоговый JSON с отобранными URL. Без него результат — `selection_unavailable`, и исследование заканчивается с `resource_blocked` (`headless_facts.py`, ветка `source_selection_unavailable`).
- Последствие: 122 — два поиска и ноль источников; 105 — поиск в UNKNOWN 185 с. Найденные ссылки из вывода websearch, которые уже есть в receipt (`discovered_sources`), не читаются.
- Исправление: если итоговый JSON выбора недоступен, читать первые N (например, 5) URL из `discovered_sources`. Защиту обеспечивает проверка объекта при чтении (R3), выбор URL — только подсказка порядка.

### 4.2 P1 — искажают результат и измерения

**R5. «Свежая» история получает старые факты.**
- Код: `place_selection.py:387` вызывает `hydrate_story_facts` при подтверждении; `headless_facts.py:704` и `:838` берут URL из `poi_research_sources` до поиска.
- Последствие: на dev-БД, где уже есть результаты по 102, rev12-тест «без подмешивания старых результатов» окажется ложноположительным.
- Исправление: в продукте поведение верное и его нужно сохранить. Для приёмки — новый `DATA_DIR` и проверка в отчёте: `poi_reused_fact_count == 0`, backend поиска не `poi_memory`.

**R6. Ночь потрачена на правила датирования, которые утяжелили чтение.**
- Код: к правилам чтения добавлено около 1,1 тыс. символов (`opencode_research.py:904–920`, `gigachat_research.py:290–304`). Вместе со схемой ответа и прежними правилами модель получает несколько тысяч символов инструкций на каждую страницу.
- Последствие: семантический эффект не доказан, а контроль MiMo закончился исчерпанием вывода.
- Исправление: до появления трёх фактов на двух объектах не добавлять правил. На сохранённой странице 102 измерить исход с блоком датирования и без него: два вызова на модель.

**R7. Три входа в «объект определён» ведут к разным путям фактов.**
- Код: `_owner_exact_fact_scope` (`research_adapter.py:1078–1084`) истинно только для `selection_basis == 'owner_exact'`.
  - Группа, сузившаяся до одного дома (`automatic_within_owner_group`), получает обычные маршруты и обычный поиск. Факты ставит периодический планировщик, а не прямой вызов (`owner_group_identity.py:177`).
  - Голосовое подтверждение (`owner_live`, `place_selection.py:375`) тоже идёт обычным путём.
- Исправление: один предикат «объект подтверждён для фактов» для всех трёх входов и одна прямая постановка задачи.

**R8. Диалог требует ввести город — это противоречит входному правилу.**
- Правило владельца: сценарий начинается с EXIF GPS, карта фокусируется на этой точке, координаты однозначно задают местоположение; город у автора не спрашивается.
- Код: `PlaceMapPanel.kt:380–420`. Если в тегах контура нет `addr:city` (в OSM частая ситуация), `askAnchor` открывает диалог, где «Город» обязателен (`city.error = "Укажите город"`, строка 420). Город в якоре берётся только из тегов контура (`place_selection.py:59`).
- Исправление: сервер заполняет город сам — `addr:city` контура, затем соседние объекты снимка, затем один reverse-запрос существующего `OSMClient` по точке камеры. Диалог города удалить; подтверждение контура — одно нажатие.

**R8a. В коде остались пути без GPS, которые входное правило исключает.**
- Код: `place_selection.py:117–119` (`place_map_point_required`), ручная точка камеры `manual_camera_point` (`place_selection.py:288–290`, `377–380`), поля широты и долготы в диалоге (`PlaceMapPanel.kt`, `askAnchor`); ночной набор и rev12 включали фото 132 без GPS.
- Исправление: Android без EXIF GPS сообщает об этом и историю не создаёт; backend в ручном режиме без координат — `422 photo_gps_required`. Код автоматического режима не трогать. Фото без GPS из тестовых наборов исключить.

**R9. Подтверждение после большого сдвига карты (P2).**
- Карта открывается на точке GPS, и нужный дом обычно есть в первом снимке (радиус 350 м). Поэтому при обычном сценарии отказа нет.
- Остаточный случай: Android перезапрашивает карту при сдвиге больше 120 м (`PlaceMapPanel.kt:202`), сервер хранит 3 последних снимка (`place_selection.py:169`), а подтверждение отправляет `snapshot_id` текущего снимка (`PlaceMapPanel.kt:442`). Если автор увёл карту дальше радиуса и подтверждает дом, выбранный до сдвига, будет 409.
- Исправление малой ценой: сервер принимает кандидата из любого сохранённого снимка того же scope.

**R12. Нет выхода при смещённом GPS (P1).**
- Реальный случай 12 октября: EXIF GPS со сдвигом около 1,5 км. Заранее его не распознать: признаков точности в EXIF телефонов почти нет (в реестре `GPSDOP` у 1 из 45 фото).
- Код PR: перемещение карты и новые снимки есть, подтверждение расстоянием не ограничено. Но нет поиска места, нет состояния «место не определено» и нет учёта сдвига. Город и автоматическое уточнение группы опираются на точку камеры (`place_selection.py:59`, `owner_group_identity.py`, `_camera_position_verified`).
- Исправление (revision 13, шаг 2a): кнопка «Дом не здесь» запускает Миру в режиме поиска места. Автор голосом описывает место; инструменты Миры `find_place_area` (существующий `_resolve_place_query`) и `focus_owner_map` (`place_map_focus` в истории) переносят карту; дом автор выбирает касанием. «Не знаю, где это» → `place_unknown`; `gps_offset_m` и `location_basis` в выборе; город — по выбранному зданию; для группы после переноса не использовать положение камеры. Старый `resolve_place` не подходит: он запускает G/T/REF.

## 7. Чего не делать

- Не закреплять модель литералом и не сужать пул до одного маршрута.
- Не повторять UNKNOWN на том же маршруте; независимую работу вести на других маршрутах.
- Не поднимать таймаут или число повторов, чтобы «дождаться» одной модели.
- Не добавлять правила в prompt чтения v3; агентному пути схему v3 не навязывать.
- Не сохранять факт агента без цитаты, найденной в загруженной backend копии страницы.
- Не засчитывать гидрированные из памяти POI факты как свежий результат.
- Не возвращать ручную точку камеры, ввод города и любые поля ввода текста автором.
