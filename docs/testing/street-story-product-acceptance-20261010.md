## Map selection acceptance revision14

Этот раздел применяется к текущему owner-selected пути и имеет приоритет над
автоматическим identity/hint сценарием ниже в противоречащей части. Это критерии
проверки, не утверждение об уже прошедшем E2E.

- Читать manifest из проверяемого worktree/SHA, а не из произвольной primary копии.
- Проверить оригинальные файлы и реальный состав корпуса. «20+» не считать
  установленным количеством уникальных фото с GPS. EXIF и GPS учитывать отдельно;
  прежний frozen15 и новые входы146–148 не объединять задним числом в старый benchmark.
- Revision14 imported/shared-photo creation требует EXIF GPS. Отсутствие GPS проверять
  как входное ограничение этого режима, а не запускать неоговорённый no-GPS story flow.
  GPS задаёт старт карты, не гарантирует положение выбранного здания.
- Обязательный сценарий: исходное фото → карта → подтверждение одного контура,
  у которого **нет ни name, ни addr** → получение контекста → исследование без
  обязательного вопроса об адресе → выбор фактов → текст/изображение → штатная
  подтверждённая тестовая публикация → чтение фактических caption и media → reopen.
- Отдельно проверить reverse geocoding с адресом и без адреса. Во втором случае
  исследование выбранного объекта не блокируется; соседний адрес не присваивается
  автоматически. Нехватка исторических источников — отдельный честный исход.
- Exact-контур окончателен без повторного G/T/REF. Approximate-группа не принимается
  за один POI. Отдельный point fallback с голосовым name/address сохраняется.
- Использовать существующий E2E runner в режиме, соответствующем revision14.
  Не подставлять owner_context/name/address из fixture в сценарий без адреса;
  fixture с name=House2 не доказывает отсутствие обоих атрибутов. Scripted author
  turns обозначать как тестовые, не как реальную речь владельца.
- Не заменять продуктовый путь ручной записью фактов, внутренними методами или REST
  обходом Live. Downstream API smoke, Live text и physical microphone иметь отдельные
  статусы покрытия. Исправления Claude проверять по фактическому SHA/receipt.
- Прежние допустимые публикационные полномочия не расширяются: только явно
  разрешённое тестовое назначение, штатные подтверждения и защита от дублей.
  Scheduled/job done не доказывают появление сообщения: нужен фактический readback.
- Финальная матрица включает весь доступный корпус и честно различает usable,
  partial, rejected, blocked, unavailable; fresh/warm/aided и прежний неизменный
  контроль. Один локальный сбой не задерживает независимо пригодные результаты.

### Существующий runner и команда

Исходный manifest raw SHA256: `70ad168a4dd5975cff76a4ce4be4eb9fa672128f795d424129ec7e2d73d9649f`; canonical manifest digest, записанный runner: `35ba39627f13dea9746956d5bad2ff8e4d082986348c1f9ef4857136e227dfb8`. Они различаются из-за представления, не состава фото. Evaluation-ревизия получает собственный digest и явный diff критериев, но оставляет перечисленные input hashes неизменными.

[Существующий `backend/tools/product_recovery_acceptance.py`](https://github.com/onedayonemasterpiece/street-story/blob/e40dba990ff56a989811cdbd43825e146835fa45/backend/tools/product_recovery_acceptance.py) проверен по файлу SHA256 `decda3c4f2d83528b194597f80dc0cbfbcaa57588c6c36a0e2cdcbe60ba7814f`. Использовать его в конечной продуктовой ветке, минимально согласовав критерии/наблюдение с этой ПМИ, не строить новый harness. Пример разрешённого будущего запуска из корня checkout, переменные предварительно заданы исполнителем:

```bash

# EVAL_MANIFEST: явная evaluation-ревизия исходного manifest; OUT: новый managed каталог.
bash scripts/run_backend_python.sh "$PYTHON" tools/product_recovery_acceptance.py \
```

`--messages` обязателен: default runner проверяет только 104. `OUT` — новый каталог в существующем `/home/dev/artifacts/street-story/`, не старый остановленный run и не production DATA_DIR. Runner фиксирует checkout и собственный isolated DATA_DIR; проверить это после адаптации. Секреты не записываются в команду/отчёт. [Python wrapper](https://github.com/onedayonemasterpiece/street-story/blob/e40dba990ff56a989811cdbd43825e146835fa45/scripts/run_backend_python.sh), [имеющийся phone smoke](https://github.com/onedayonemasterpiece/street-story/blob/e40dba990ff56a989811cdbd43825e146835fa45/scripts/phone_live_acceptance.sh) используются в рамках отдельно действующих разрешений на расходы, устройство и установку; smoke сам по себе не доказывает весь сценарий ниже.

**Граница наблюдателя.** В e40 runner заданы CAPS 180/300/480 секунд и `apply_hard_cap` может сам завершить попытку. Это не независимое доказательство того, что backend сам остановился. Отделить observer timeout/intervention от product outcome; для close/reopen проверки нужен не завершающий исследование режим существующего harness либо отдельное клиентское наблюдение над тем же backend job. Не повышать inference budget до 20 минут: backend может закончить раньше, поздний reopen обязан показать сохранённый результат. Любое вмешательство runner в исход явно отражается; ни observation timeout, ни отключение клиента не выдаются за явный owner Stop.


## 2. Порядок

1. На сохранённых ответах проверить изменённые механические границы и отрицательные примеры: canonical normalization, own-source/subject binding, единственный commit, accepted-basis lifetime, Stop/generation/UNKNOWN. Не отправлять новый inference ради воспроизведения уже закрытого ответа.
2. Адресные реальные вызовы проверяют изменённый смысловой путь, затем стабильный интегрированный кандидат проходит **все 15 cold входов** одним зафиксированным протоколом. Не заменять корпус удобным подмножеством, не выполнять три оплачиваемые серии G×15/T×15/REF×15 и не перебирать варианты до PASS.
3. Исправить обнаруженные воспроизводимые причины неверного объекта, отсутствия пригодных фактов, потери результата или недостижимого продолжения. Проверить затронутый путь; итоговый результат корпуса должен относиться к конечному кандидату. Совместимость ранее полученного результата после не затрагивающей его правки обосновывается явно, иначе он помечается устаревшим. Не считать исправленный код доказанным старым прогоном.
4. Отдельно проверить warm: вторая история достоверно того же физического POI использует постоянно сохранённую опору первой разрешённой истории. Cold остаётся изолированным; скрытые expected IDs и тестовые ответы не попадают в runtime. Проверить повторное использование, сохранение источников и отсутствие повторного обязательного semantic review пригодного basis.
5. Отдельно проверить assisted: заранее записанная содержательная подсказка после сохранённого вопроса и истёкшей старой волны. Scripted hint честно обозначается scripted; это не ответ спящего владельца. Один command открывает одну ограниченную identity generation, не снимает Stop и не дублирует UNKNOWN. Assisted не исправляет задним числом cold-auto показатель.
6. Пройти весь пользовательский путь: accepted upload → закрытие клиента до identity → reopen → объект/факты → выбор → замысел/черновик → голосовое уточнение → визуал → повторный reopen с сохранёнными результатами. Prepared audio и эмулятор не доказывают реальный микрофон физического телефона. Внешнюю публикацию выполнять только при отдельном действующем разрешении и разрешённом получателе; иначе проверить доступную подготовку/подтверждение и явно отметить непроверенный внешний шаг.

## 3. Что доказывают методы

Принятое [полное видение G](../design/street-story-spatial-geometry-vision-20261010.md) сохраняет отдельный исторический охват **26 фото: 102,104–112,118–133** и обзор применимости 26/26; у 124/127/128 нет геоопоры для чистого локального G, остальные 23 нельзя молча исключать по сложности. Эти 26 записей уже есть в исходном manifest; это не новый dataset и не замена final15 выше. В методном отчёте отделить применимость/нехватку входа от model uncertain/host reject/правильной identity/полезного сужения. Реальный запуск метода на применимых входах планируется явно в разрешённом бюджете реализации; не выполнять автоматически26 × все провайдеры и не выдавать старый обучавшийся корпус за независимый holdout. Отсутствие необходимых данных не исправлять контрольным GPS/expected ID.


G, T и REF — независимые достаточные пути, а не обязательная последовательность. Существующий corpus pass допускает любой достоверный путь. Методные fixtures/адресные проверки отдельно показывают: достаточный G/T принимает точное тело без обязательного REF; недостаточный G даёт полезное сужение без потери правильной гипотезы; T использует собственный прочитанный body/passages, не заголовок или snippet как proof. REF façade-match с нерешённой привязкой не считается identity. Проверка только «метод вызван» недостаточна. В ранее проверенной frozen-серии самостоятельный G-success не подтверждён; это не доказывает бесполезность всех G-сужений. Новая проверка должна показать фактическую роль G: достоверное самостоятельное принятие там, где оно обосновано, либо измеримое сужение достижимых альтернатив без потери правильного тела. Отключение G с последующим REF-pass не считается доказательством исправления G. Если в корпусе нет подходящего входа для отдельного свойства, использовать уже сохранённый релевантный пример, явно отделив replay от нового runtime доказательства.

В G-проверках сохранить совместную вертикальную морфологию и пространственную комбинацию, а не только primitive validity: узкий высокий объект/широкий сосед, levels отдельно от missing height, complex parts, crop/end-on, отступы и основной/соседний объём. Actual EXIF происхождение не обесценивается до search anchor из-за неизвестной accuracy; 35mm diagonal FOV не считается точным HFOV/дистанцией. Проверить фактически доставленные pixels и читаемость MAP/detail. Сохранённые G-v3 wrong126/130 и132G с OCR/MAP-name из [истории метода](../design/street-story-spatial-geometry-vision-20261010.md) — контрпримеры обещанию «более свободная schema сама исправляет G»; не переносить их как успешные e40 испытания.

Для T добавить адресные контрпримеры изменённого пути: различающее описание находится после нынешнего 12K prefix; выбранная порция содержит больше двух положительных article bindings; текст вместе с SOURCE разрешает тело без предварительного MAP/G принятия; общий текст комплекса не разрешает соседний корпус; невидимый признак не становится противоречием, выдуманная реставрация не оправдывает реальный конфликт. Сохранённые e40/102/104/119 ответы ссылаются на ARTICLE REF; пока полный frozen image input не проверен, не использовать эти строки как доказанный text-only benchmark. В104 сведения о размерах статьи не становятся SOURCE measurement;107/119/120 требуют независимой physical truth, слабое объяснение не маркируется автоматически wrong. Ещё один контроль: полученная Wiki-страница с неразрешённым телом читается как гипотеза, но не принимается до собственного scope evidence. Это минимальные проверки общего контракта, не обязательные новые paid judges. Сохранённый closed replay отличать от нового model run.

Для G/T сохранить реконструируемую цепочку: точный frozen input → raw proposal → нормализованный ответ → конкретный host admission/reject reason → retained active/reserve → следующий T/REF work либо identity commit. Использовать existing operation IDs и snapshot references; предложение G внутри joint SOURCE/T не считать ещё одним provider call. `prepared` не доказывает отправку. Проверить привязку каждого нужного semantic decision к original attempt: нынешний first-in-scope receipt и raw truncation не гарантируют доступность всех ответов. Hash без доступного payload/reference не считается полным replay evidence; gap/truncated указывается явно, старый UNKNOWN сохраняется. Если telemetry части нет, причина/длительность остаётся неизвестной, не восстанавливается догадкой. Закрытые сохранённые ответы достаточны для механического replay границ; новый inference нужен только изменённой смысловой проверке.

Отрицательные контроли: неизвестный primitive ID/hash/устаревшая generation не проходит; неправильный segment relation не становится identity; корректная гипотеза может сохраняться после отвергнутого конкретного доказательства. Не приписывать всякий host reject ложному отказу: две несовместимые physical-link записи или ссылки на соседнее тело — реальная причина отклонения. Проверить условность centroid/first-ray diagnostics на релевантных сохранённых примерах, не объявляя их наблюдаемой частотой ошибок всего корпуса.

## 4. Отчёт и окончание

Одна строка на каждый вход: photo ID/SHA256; run/story и source/runtime SHA; auto/assisted/cold/warm; фактический physical ID и независимое основание правильности либо unresolved; identity method/outcome; список собственных пригодных тезисов с исходными passage/source references; all-source UI/readback; first/useful/terminal времена; итог и конкретная причина ограничения. Expected identity используется только evaluator, не моделью. Отсутствующее независимое truth не превращается в PASS и не заполняется догадкой. PASS_CANDIDATE, число eligible и технический terminal сами по себе не доказывают продукт.

Отдельно: применимые tests/build/CI конечного SHA, доказательства автономности/reopen/выбора/голоса/визуала, точные failures/not-run и последующие исправления. Не суммировать разные SHA/повторные попытки в процент точности. Время useful→terminal может быть хвостом обогащения, а не задержкой первого полезного результата; времена admission/commit не выдумывать, если не записаны.

Задача не завершена одной таблицей исправимых провалов. Допустимая остановка — реальный внешний/авторизационный/безопасностный блокер либо исчерпанные разрешённые ограниченные альтернативы с сохранённым диагнозом; независимая разрешённая работа продолжается. Полезный partial — корректный runtime результат, но не автоматическое завершение реализации. Нет нового произвольного процента точности или требования исчерпать все источники. Согласованные цели сохраняются, фактическое покрытие и ограничения показываются честно.
